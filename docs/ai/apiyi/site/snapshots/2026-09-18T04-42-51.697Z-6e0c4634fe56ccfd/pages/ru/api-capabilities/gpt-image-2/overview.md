# GPT-Image-2.5 / 2 Генерация/редактирование изображений

> Руководство по официальному релею для серии OpenAI GPT-Image 2.5 / 2: gpt-image-2.5-flare (приоритет скорости), gpt-image-2.5-sunburst (приоритет точности редактирования) и gpt-image-2 — все по одинаковой цене и с одинаковыми параметрами. Нативное разрешение любого размера 2K/4K, автоматическая обработка эталонных изображений с высокой точностью, преобразование текста в изображение, редактирование по эталону, объединение нескольких изображений, закрашивание областей по маске.

<Info>
  Все image API являются **синхронными** — здесь нет ID задачи для опроса, и если ваш клиент отключится, результат будет потерян, при этом запрос все равно тарифицируется. Установите достаточно большой timeout для этой модели; см. [Основы и лучшие практики Image API](/ru/api-capabilities/image-api-best-practices).
</Info>

## Обзор

На этой странице рассматривается серия **GPT-Image 2.5 / 2** от OpenAI через официальный релей APIYI: **`gpt-image-2.5-flare`** (с приоритетом скорости), **`gpt-image-2.5-sunburst`** (с приоритетом качества и точности редактирования) и **`gpt-image-2`** предыдущего поколения. Модели 2.5 выпущены 2026-09-08 и обеспечивают более высокое качество по сравнению с gpt-image-2, более точное редактирование и два новых уровня `quality` (`xhigh` / `max`) при **абсолютно тех же цене и параметрах, что и у gpt-image-2**. Для всей серии общими являются: **любое допустимое разрешение (включая 2K / 3840×2160 4K)**, **автоматическое высокоточное качество при работе с эталонными изображениями**, **тарификация по token**. Шлюз APIYI полностью совместим с API изображений OpenAI — укажите `base_url` официального SDK OpenAI здесь для прямого подключения без изменений в коде.

<Note>
  **🎨 Основные преимущества**: нативная поддержка любого допустимого разрешения (максимум 3840×2160 4K) + автоматическое высокоточное качество при редактировании эталонных изображений + нативная поддержка промптов на китайском языке + новые уровни качества `xhigh` / `max` в версии 2.5. **Оптимально для производственных сценариев, требующих точного управления размером и качеством, полной совместимости с официальным API OpenAI или вывода в 4K**; по умолчанию для преобразования текста в изображение используйте `gpt-image-2.5-flare`, а для редактирования — `gpt-image-2.5-sunburst`.
</Note>

Также не отправляйте `input_fidelity`.

Если не удаётся сжать одно изображение, используйте исходное и продолжайте — никогда не прерывайте весь запрос из-за ошибки сжатия.

  4. Уровень качества: всегда отправляйте `quality`, по умолчанию устанавливая `medium`, и добавьте в интерфейс выпадающий список качества (`low` / `medium` / `high` / `xhigh` / `max`; последние два поддерживаются только моделями 2.5 и стоят дороже). Не отправляйте `auto` — это динамический уровень рассуждения, поэтому стоимость и задержка могут изменяться.

  5. В рабочей среде зафиксируйте имя модели на снапшотах с датами `gpt-image-2.5-flare-2026-09-08` / `gpt-image-2.5-sunburst-2026-09-08`, чтобы изменение алиаса не переключило используемую модель.

  6. Получайте ключ из переменной окружения `APIYI_API_KEY` и используйте [https://api.apiyi.com/v1](https://api.apiyi.com/v1) в качестве базового URL. Никогда не встраивайте его в код и не добавляйте в git.

## Тарификация

`gpt-image-2.5-flare` / `gpt-image-2.5-sunburst` / `gpt-image-2` APIYI (группа по умолчанию) **используют единый прайс-лист, который в точности соответствует официальным тарифам OpenAI** — скидка предоставляется за счёт нашего бонуса за пополнение: **пополните счёт на \$100 и получите бонус 10%, вплоть до 20%**. 📖 [Подробнее об акциях пополнения](/ru/faq/recharge-promotions).

### Тарификация по количеству token (как в прайс-листе OpenAI)

Token-metered — один запрос = токены входного текста + входного изображения + выходного изображения:

| Позиция тарификации  | Цена (за 1M tokens)        | Примечания                                                                                           |
| -------------------- | -------------------------- | ---------------------------------------------------------------------------------------------------- |
| Входной текст        | \$5.00                     | Текстовая часть вашего prompt                                                                        |
| Входное изображение  | \$8.00                     | Референсные изображения в запросах редактирования/смешивания, токенизируются по правилам Vision      |
| Выходное изображение | \$30.00                    | **Основная статья затрат** — число token определяется размером × качеством                           |
| Кэшированный ввод    | Text \$1.25 / Image \$2.00 | Настроено, но при высоких параллельных запросах частота попадания в кэш ограничена — см. [ЧЗВ](#faq) |

**Почему входное изображение дороже?** Входное изображение стоит \$8.00 / 1M tokens — **1.6x** ставки \$5.00 / 1M для входного текста (это собственный прайс-лист OpenAI, а не наценка APIYI). Именно поэтому запросы редактирования / fusion с несколькими изображениями заметно дороже по входной части, чем обычная генерация изображений по тексту: референсные изображения токенизируются в большое число image tokens по правилам Vision, и каждый из этих token уже стоит на 60% дороже text token.

### Как несколько входных изображений влияют на цену (проверено в июле 2026)

Частый вопрос от клиентов: «Каждое референсное изображение стоит фиксированную сумму, или большие изображения расходуют больше tokens?» Ответ: **важны оба фактора, и количество изображений суммируется строго линейно**. `gpt-image-2` обрабатывает каждое входное изображение в принудительном режиме высокой детализации (`input_fidelity` не настраивается — при его передаче возвращается 400), и каждое референсное изображение преобразуется в image tokens в зависимости от его размеров и aspect ratio. Контролируемые измерения (эндпоинт edits, 2026-07-15):

| Входное референсное изображение | `image_tokens`        | Стоимость входа (\$8/M) |
| ------------------------------- | --------------------- | ----------------------- |
| 1 × 512×512                     | 1024                  | ≈\$0.0082               |
| 1 × 1024×1024                   | 1024                  | ≈\$0.0082               |
| 1 × 2048×2048                   | 1521                  | ≈\$0.0122               |
| 1 × 4096×4096                   | 1521                  | ≈\$0.0122               |
| 1 × 1024×1536 (портрет)         | 1536                  | ≈\$0.0123               |
| **4 × 1024×1024**               | **4096 (= 4 × 1024)** | ≈\$0.0328               |

Три практических правила:

1. **Количество строго линейно**: N референсных изображений ≈ N × tokens одного изображения. 16 референсных изображений при 1024² ≈ 16384 tokens ≈ \$0.13 — тот же порядок величины, что и один вывод `high` (\$0.211), так что в случае слияния нескольких изображений этим уже нельзя пренебрегать.
2. **Размер имеет и нижний предел, и потолок**: квадратные изображения размером 1024² и меньше тарифицируются как 1024 tokens (уменьшение до 512 **ничего не экономит**); 2048² и 4096² оба стоят 1521 tokens (слишком большие изображения перед преобразованием уменьшаются — **потолок действует**). Одно референсное изображение обычно попадает примерно в диапазон 800-1600 tokens с учетом соотношения сторон.
3. **Tokens определяются размерами в пикселях, а не размером файла**: сжатие до 1.5MB помогает со стабильностью и скоростью загрузки, но **не уменьшает image tokens**; наоборот, загрузка исходника на 50MB тоже не раздует ваш счет (действует потолок).

<Tip>
  Интуитивная оценка стоимости: при выводе `low` (196 tokens ≈ \$0.006) стоимость входа одного референсного изображения (≈\$0.008) фактически превышает стоимость вывода; при выводе `high` (≈\$0.211) одно референсное изображение составляет лишь около 4%. **Размер и качество вывода всегда сильнее всего влияют на цену** — количество референсных изображений стоит на втором месте.
</Tip>

| Качество | 2048×2048 (2K-квадрат) | 2048×1152 (2K-альбомная ориентация) | 3840×2160 / 2160×3840 (4K) |
| -------- | ---------------------- | ----------------------------------- | -------------------------- |
| Низкое   | ≈\$0.024               | ≈\$0.008                            | ≈\$0.026                   |

Размеры выше 2560×1440 при качестве `high` по-прежнему относятся к официальному экспериментальному уровню, поэтому оценки там могут быть менее точными.
</Warning>

### Чем это отличается от SaaS-подписки / тарификации на основе credit

Вендоры инструментов генерации изображений обычно тарифицируют по одной из двух схем:

* **Ежемесячные планы подписки**: фиксированная ежемесячная плата за квоту «N изображений в месяц». Эта квота рассчитывается исходя из **предположения о сверхпродаже** — вендор закладывает ожидание, что большинство пользователей не израсходует весь лимит, поэтому рекламируемая «стоимость за изображение» — это просто цена плана, деленная на верхний предел квоты, а не то, сколько на самом деле стоит сгенерировать для вас одно изображение.
* **Учёт на основе credit / point**: задачи разного качества и размера переводятся в неочевидные «credits». По сути это тарификация по фактическому использованию, просто переупакованная в единицу credit, которая скрывает реальное потребление token.

APIYI работает по модели **официальный релей + фактическая тарификация по token**: без квоты плана, без слоя абстракции в виде credit. Стоимость каждого вызова — это просто фактическое число input/output token × официальный тариф — точный учет по каждому вызову, без сверхпродажи, характерной для подписки, и без динамики «ограничивать, когда вы превысили лимит».

<Tip>
  Компромисс тарификации по фактическому использованию в том, что вам нужно самостоятельно оценивать и отслеживать расход, а не полагаться на фиксированную ежемесячную сумму подписки — зато вы платите только за то, чем реально пользуетесь, без простоя и пустых затрат. Вот как напрямую извлечь реальное число token для каждого вызова из ответа, чтобы вы могли вести такой учет самостоятельно.
</Tip>

### Как проверить фактическое количество token для каждого вызова

И `/v1/images/generations`, и `/v1/images/edits` возвращают поле `usage`, а **token изображений и token текста возвращаются в отдельных полях** — ничего оценивать не нужно, просто считайте их для точного расчёта стоимости каждого вызова. Ниже приведён полный объект `usage` из реального запроса на редактирование с одним эталонным изображением (получен в реальном времени):

```json theme={null}
{
    "data": [ { "b64_json": "..." } ],
    "usage": {
        "input_tokens": 848,
        "input_tokens_details": {
            "image_tokens": 832,
            "text_tokens": 16
        },
        "output_tokens": 196,
        "output_tokens_details": {
            "image_tokens": 196,
            "text_tokens": 0
        },
        "total_tokens": 1044
    }
}
```

| Поле                                      | Значение                                                                                                                                                                                                                                                                                                    |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `usage.input_tokens_details.text_tokens`  | token, использованные в тексте промпта; тарифицируются по \$5.00 / 1 млн                                                                                                                                                                                                                                    |
| `usage.input_tokens_details.image_tokens` | token, в которые преобразуется эталонное изображение согласно правилам Vision; тарифицируются по \$8.00 / 1 млн; всегда равны 0 для обычной генерации изображения из текста без эталонного изображения                                                                                                      |
| `usage.input_tokens`                      | Сумма двух указанных выше полей                                                                                                                                                                                                                                                                             |
| `usage.output_tokens`                     | token для сгенерированного изображения, зависящие от `quality × size` — это **основная часть стоимости**, тарифицируемая по \$30.00 / 1 млн; именно за этим числом следует внимательно следить в запросах 2K/4K (`output_tokens_details.image_tokens` дублирует это значение; `text_tokens` всегда равно 0) |
| `usage.total_tokens`                      | Общая сумма входных и выходных данных                                                                                                                                                                                                                                                                       |

Формула самостоятельного расчёта стоимости (точная):

```
cost ≈ input_tokens_details.text_tokens × \$5.00 / 1,000,000
     + input_tokens_details.image_tokens × \$8.00 / 1,000,000
     + output_tokens × \$30.00 / 1,000,000
```

<Tip>
  Чтобы проверить фактическое использование token и подробности тарификации для прошлых вызовов, откройте в консоли страницу «Журналы»: 📖 [Как просматривать журналы вызовов](/ru/faq/call-logs) — в подробном представлении журнала указаны цены для текста на входе / изображений на входе / выходных данных рядом с соответствующим количеством token, что соответствует `usage.input_tokens_details` / `usage.output_tokens_details` из API.
</Tip>

## Настройка группы

Все три модели GPT-Image 2.5 / 2 используют одни и те же группы официального релея. Переключение выполняется в панели управления → **Настройки token → Группа**:

| Группа             | Тариф       | Когда использовать                                                                                                                            |
| ------------------ | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `Default`          | 1.0x        | Та же цена, что и в списке OpenAI — первый выбор при наличии доступной ёмкости; в часы пик возможны 429 / ограничения на параллельные запросы |
| `image2Enterprise` | 1.2x        | Стабильный резервный вариант, когда стандартная группа перегружена — приоритет по доступной ёмкости                                           |
| `svip`             | См. консоль | Также поддерживает все три модели; тариф отображается на странице token в консоли                                                             |

**Почему 1.2x?** Коэффициент рассчитан исходя из условия «промоакция с разовым пополнением на \$3,000 и бонусом 20% ≈ цена из списка OpenAI» — APIYI не получает маржу с этого направления (за исключением налоговых расходов) и использует его исключительно как канал с приоритетом по доступности. 2. **Обе стороны кратны 16**
3. **Соотношение сторон ≤ 3:1**
4. **Общее число пикселей ∈ \[655,360, 8,294,400]** (\~0.65MP до \~8.3MP)

**Допустимые примеры**: `1600x1200`, `1792x1024`, `2048x1536`, `3200x1800`
**Недопустимые примеры**: `1000x1000` (не кратно 16), `4000x4000` (выше максимума), `3840x1000` (соотношение > 3:1)

<Warning>
  Выводы выше `2560×1440` (\~3.69MP) официально помечены как **экспериментальные** и могут показывать колебания качества. Для production лучше использовать предустановки вроде `2048x1152` / `2048x2048` / `3840x2160`.
</Warning>

## Справочник качества

### Доступные уровни

| качество | Значение                                        | Примечания                                                                                                                               |
| -------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`   | Автоматически (**по умолчанию**)                | Значение, используемое, если `quality` не указано — модель выбирает уровень за вас                                                       |
| `low`    | Низкое качество                                 | Самый быстрый и дешёвый вариант — подходит для черновиков / пакетной обработки                                                           |
| `medium` | Среднее качество                                | Сбалансированный выбор для повседневных задач / финального результата                                                                    |
| `high`   | Высокое качество                                | Текст, мелкие текстуры, печать; высший уровень для `gpt-image-2`                                                                         |
| `xhigh`  | Очень высокое качество (**новое в версии 2.5**) | Поддерживается только `gpt-image-2.5-flare` / `sunburst`; больше выходных токенов, чем у `high`                                          |
| `max`    | Максимальное качество (**новое в версии 2.5**)  | Поддерживается только двумя моделями версии 2.5; максимальные стоимость и задержка, для финальных результатов производственного качества |

<Warning>
  **По умолчанию используется `auto`, а не `medium`.** Опущенный `quality` эквивалентен передаче `"quality": "auto"` — модель автоматически выбирает уровень качества, и **OpenAI не гарантирует, что он соответствует `medium`**. Уровень, к которому разрешается `auto`, непредсказуем и напрямую влияет на стоимость, задержку и стабильность тарификации. **Если вам нужны контроль затрат и предсказуемость, явно передавайте `low` / `medium` / `high` / `xhigh` / `max` вместо того, чтобы полагаться на `auto`.**
</Warning>

<Warning>
  **Не передавайте устаревшие значения DALL·E `standard` / `hd`.** `quality` принимает только шесть официальных значений enum: `low` / `medium` / `high` / `xhigh` / `max` / `auto`, а `xhigh` / `max` поддерживаются только двумя моделями версии 2.5. Устаревшие значения DALL·E 3 `standard` / `hd` ведут себя непоследовательно в разных backend-каналах: иногда они сразу завершаются ошибкой 400 (`invalid_value`), а иногда молча игнорируются, и запрос выполняется с параметром `auto` (непредсказуемая стоимость). Всегда явно передавайте одно из официальных значений.
</Warning>

<Info>
  **`quality` оказывает наибольшее влияние на цену — больше, чем `size`.** Количество токенов выходного изображения определяется параметром `quality × size`, но `quality` имеет гораздо больший вес: при одинаковом размере переход от `low` к `high` может изменить стоимость одного изображения более чем в **30 раз** (см. приведённую выше таблицу «стоимость изображения»: для gpt-image-2 при размере 1024×1024 она варьируется от `low` \$0.006 до `high` \$0.211; для моделей версии 2.5 — от `low` \$0.006 до `max` \$0.211). Сначала оценивайте стоимость по параметру `quality`, а затем учитывайте влияние `size`.
</Info>

## Рекомендации

<Warning>
  **Совет по началу работы: сначала настройте работу API с `low`, а затем масштабируйте**

  Мы видели, как новые интеграторы сразу переходили к `quality=high` + высокому разрешению и в итоге ждали **≈ 235 секунд (\~4 минуты) на изображение** — лишь чтобы заподозрить, что API завис. Режим `high` имеет наивысшую сложность инференса, а 4K может занимать почти 5 минут. **Перед переходом в production сначала выполните сквозную интеграцию с `quality=low`** (аутентификация, SDK, параметры, тайм-ауты, обработка ошибок), а затем переходите к `medium` / `high` только в соответствии с вашими фактическими требованиями к качеству.
</Warning>

<Steps>
  <Step title="Сначала интегрируйте с низким качеством">
    Для новых интеграций **начинайте с `quality=low` + предустановленного размера**, чтобы проверить всю цепочку вызова (аутентификация, параметры, тайм-ауты, обработка ошибок). `low` в несколько раз быстрее `high`, поэтому функциональные проблемы выявляются быстро и не маскируются длительной задержкой.
  </Step>

  <Step title="Предпочитайте предустановленные размеры">
    8 официальных предустановок оптимизированы для стабильной скорости и качества. Используйте пользовательские размеры только для действительно нестандартных соотношений сторон.
  </Step>

  <Step title="Подбирайте качество под сценарий">
    Черновики / пакетная обработка → `low`; повседневное использование / финальная версия → `medium`; текст, мелкие текстуры, печать → `high`. **Обратите внимание, что переход `low` ↔ `high` — это не только визуальная точность, но и скачок сложности инференса**, поэтому задержка масштабируется соответственно.
  </Step>

  <Step title="Выбирайте вывод JPEG">
    Для финального отображения `output_format=jpeg` + `output_compression=85` быстрее PNG и примерно вдвое меньше по размеру.
  </Step>

  <Step title="Фиксируйте высокий уровень для сценариев с текстом">
    Рендеринг текста — ключевое преимущество, но на более низких уровнях текст всё ещё может быть размытым. Фиксируйте `quality=high` для сценариев с вывесками и постерами.
  </Step>

  <Step title="Подготавливайте референсные изображения">
    Каждое изображение — до 50MB (на практике сжимайте до 1.5MB); поддерживаются PNG/JPEG/WebP; до 16 изображений; указывайте порядок референсов как «изображение 1 / изображение 2» в prompt.
  </Step>

  <Step title="Прозрачный фон: передайте параметр и не описывайте сцены в prompt">
    `background: "transparent"` с `png` / `webp` гарантирует только альфа-канал. **Если prompt или референсное изображение описывает полноценную сцену (лес, комнату, улицу), модель рисует эту сцену**, и параметр не остановит её — это основная причина, почему прозрачность «иногда работает», и это не связано с `quality` (измерено 2026-09-11: prompt только с объектом — 16/16 прозрачных, prompt со сценой — 0/3, одинаково для среднего и высокого уровней). Завершайте prompt фразой `isolated subject on a transparent background, no scenery, no ground`; если референсное изображение содержит фон, укажите `remove the background entirely, keep only the subject` в prompt для редактирования. См. [FAQ по прозрачному фону](/ru/faq/image-transparent-background).
  </Step>

  <Step title="Настройте уровни тайм-аута клиента (высокий → страховочная сетка 600s)">
    Два параметра, которые сильнее всего влияют на задержку, — **`quality`** и **`size`** — особенно `quality`. Настройте тайм-ауты клиента для каждого уровня:

    | качество             | Рекомендуемый тайм-аут клиента        | Наблюдаемая задержка                                                                                                               |
    | -------------------- | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
    | `low`                | ≥ **120 секунд**                      | обычно 10–40 секунд                                                                                                                |
    | `medium`             | ≥ **240 секунд**                      | обычно 30–90 секунд                                                                                                                |
    | `high`               | ≥ **600 секунд** (страховочная сетка) | запуски gpt-image-2 2K/4K занимают 3–5 минут, наблюдался длинный хвост 235+ секунд; для моделей 2.5 при 1024² измерено 21–42 с     |
    | `xhigh` (только 2.5) | ≥ **300 секунд**                      | при 1024² измерено 31–60 с (2026-09-09); больше для 2K/4K                                                                          |
    | `max` (только 2.5)   | ≥ **600 секунд** (страховочная сетка) | при 1024² измерено 45–142 с; то же количество token, что у gpt-image-2 `high`, поэтому планируйте 2K/4K как для gpt-image-2 `high` |

    **Для режима `high` установите 600s в качестве страховочного тайм-аута**, чтобы учесть очередь, вариативность длинного хвоста и нестабильность upstream. Отображайте прогресс в UI; рассмотрите очередь задач на стороне сервера.
  </Step>

  <Step title="Примечания по миграции">
    При миграции с `gpt-image-1.5`: удалите `input_fidelity` (принудительное высокое качество, при передаче вызовет ошибку); `background: transparent` продолжает работать без изменений. При миграции с устаревшего кода DALL·E 2/3: **удалите `response_format`** (модели GPT Image отклоняют его с ошибкой 400 `Unknown parameter: 'response_format'`; вывод всегда `b64_json`).
  </Step>
</Steps>

  * Для службы поддержки записывайте заголовок `x-request-id`
</Info>

## Часто задаваемые вопросы

<AccordionGroup>
  <Accordion title="Как исправить ошибку 400 Unknown parameter: 'response_format'?">
    **Удалите параметр `response_format` — сейчас это наиболее распространённая ошибка 400.** `gpt-image-2` (как и вся серия GPT Image) **не поддерживает** `response_format`: формат вывода фиксирован как `b64_json` и не может быть изменён. Его передача возвращает:

    ```json theme={null}
    {
      "error": {
        "message": "Unknown parameter: 'response_format'.",
        "type": "invalid_request_error",
        "param": "response_format",
        "code": "unknown_parameter"
      }
    }
    ```

    Этот параметр — **наследие эпохи DALL·E 2/3** (где поддерживались `url` / `b64_json`), и множество старых примеров кода и некоторые сторонние библиотеки по-прежнему добавляют его по умолчанию. При переходе на `gpt-image-2` удалите это поле и считывайте `data[0].b64_json` напрямую (исходная строка base64 — декодируйте её, чтобы получить файл изображения). Ошибка возвращается на этапе проверки входных данных и **не тарифицируется**.

    Если в вашем рабочем процессе действительно нужен **URL изображения**, а не base64:

    * Официальный `gpt-image-2` не поддерживает вывод URL — декодируйте base64 и загрузите файл в собственное объектное хранилище
    * Либо переключитесь на реверс-инжиниринговый [`gpt-image-2-all`](/ru/api-capabilities/gpt-image-2-all/overview), который поддерживает `response_format: "url"` и возвращает CDN-ссылку, действительную в течение 24 часов
  </Accordion>

  <Accordion title="Нужно ли добавлять префикс data:image/png;base64, к b64_json?">
    **Да**. `gpt-image-2` возвращает **исходную строку base64** (без префикса), в отличие от `gpt-image-2-all`. Два варианта для клиента:

    * **Запись в файл**: `base64.b64decode(b64_str)` → запись на диск
    * **Отображение в браузере**: `img.src = 'data:image/png;base64,' + b64_str` (добавьте префикс вручную)

    Если ваш код предполагает поведение эпохи 1.5, когда префикс уже был добавлен, вы получите повреждённый URL данных — обработайте этот случай явно.
  </Accordion>

  <Accordion title="Почему передача input_fidelity возвращает ошибку 400?">
    `gpt-image-2` **принудительно** включает высокоточную обработку референсных изображений и больше не принимает `input_fidelity`. При переходе с версии 1.5 просто удалите это поле — замена не требуется.
  </Accordion>

  <Accordion title="Что делать, если нужен прозрачный фон?">
    Просто передайте `background: "transparent"`, установив `output_format` в значение `png` или `webp`. В результате будет получено настоящее изображение с альфа-каналом — дополнительная постобработка для удаления фона не требуется. Это поддерживается и для преобразования текста в изображение, и для редактирования изображений.

    Есть два ограничения: `jpeg` не имеет альфа-канала и несовместим с прозрачностью (возвращает ошибку 400); кроме того, на эндпоинте редактирования прозрачность означает **перерисовку**, а не точное обведение исходного контура, поэтому детали объекта могут измениться. Для попиксельного извлечения самостоятельно запустите `rembg` / `PIL` / `sharp`.

    Третье ограничение часто упускают: **если промпт или референсное изображение описывает сцену, модель рисует сцену** — параметр не может это переопределить, и увеличение `quality` не поможет. Описывайте только объект и завершайте запрос фразой `isolated subject on a transparent background, no scenery, no ground`.

    Полные сведения и поддержка по каждой модели: [Как генерировать изображения с прозрачным фоном](/ru/faq/image-transparent-background).
  </Accordion>

  <Accordion title="Сколько изображений можно получить за один вызов?">
    1 изображение (`n=1`). Для N изображений отправьте N параллельных запросов. Каждый запрос тарифицируется отдельно по количеству token.
  </Accordion>

  <Accordion title="Почему 2K/4K работает так медленно?">
    Более высокое разрешение и качество требуют большего количества выходных token изображения, поэтому обработка естественным образом занимает больше времени. **В реальных интеграциях клиентов мы наблюдали, что `quality=high` + высокое разрешение занимают ≈ 235 секунд (около 4 минут) на изображение**, а длинный хвост задержки для `3840×2160` + `high` может приближаться к 5 минутам. Рекомендации:

    * **Сначала интегрируйте `quality=low`**, чтобы проверить цепочку вызовов, а затем повышайте параметры по мере появления реальной потребности в качестве
    * Установите тайм-аут клиента в зависимости от качества: `low` ≥ **120 с** / `medium` ≥ **240 с** / **`high` ≥ 600 с** (запас безопасности)
    * Показывайте в интерфейсе статус «генерация»
    * Используйте пресеты 1K с разрешением 1024×1024 / 1536×1024, если 4K не требуется
  </Accordion>

  <Accordion title="Действительно ли я получу выгоду от тарификации кэшированных входных данных?">
    **Кэширование настроено, но не закладывайте скидки за кэш в бюджет.** Официальные тарифы для кэшированных входных данных составляют \$1.25 за текст / \$2.00 за изображение на 1 млн token, а в канале APIYI настроено кэширование — если запрос попадает в кэш, он тарифицируется по ставке для кэшированных данных.

    Есть важная оговорка: для поддержания высокой параллельной нагрузки APIYI распределяет запросы между несколькими аккаунтами OpenAI (один аккаунт OpenAI уровня Tier-5 допускает только 250 RPM). Кэш промптов OpenAI не переносится между аккаунтами, поэтому при высокой параллельной нагрузке запросы с одинаковым префиксом могут попасть на разные аккаунты — **попадания в кэш может просто не произойти**.

    Хорошая новость: влияние невелико. Основную часть стоимости генерации изображений составляют выходные token изображения (\$30 за 1 млн); скидка за кэш применяется только к входной части, поэтому почти не влияет на итоговую стоимость изображения. Планируйте бюджет исходя из **полной цены входных данных**, а любые попадания в кэш рассматривайте как дополнительную экономию.
  </Accordion>

  <Accordion title="Почему запросы на редактирование стоят дороже, чем преобразование текста в изображение?">
    Поскольку `gpt-image-2` автоматически включает высокоточную обработку референсных изображений, сами референсы преобразуются в большое количество входных token по правилам тарификации Vision. Редактирование требует заметно больше входных token, чем преобразование текста в изображение — учитывайте это при планировании бюджета.
  </Accordion>

  <Accordion title="Одинаковый размер и одинаковые референсные изображения — почему каждый вызов всё равно стоит по-разному?">
    **Корневая причина: для `quality` было задано значение `auto` (или параметр был опущен).** Клиенты сообщали: «размер, разрешение и референсные изображения одинаковы, но цена то растёт, то снижается». При проверке выяснилось, что и `size`, и `quality` имели значение `auto`.

    **Причина — `quality: auto`**: в автоматическом режиме модель **интерпретирует запрос и на лету выбирает разные уровни качества** для каждой генерации. Другой уровень означает другое количество выходных token изображения, а значит, и другую цену. Ниже приведены три реальных записи тарификации с **одинаковыми входными данными (по 1061 входному token в каждой)**, но стоимостью, отличающейся в несколько раз:

    | Задержка | Входные token | Выходные token | Стоимость вызова |
    | -------- | ------------- | -------------- | ---------------- |
    | 53 с     | 1061          | 1286           | \$0.055082       |
    | 135 с    | 1061          | **5146**       | **\$0.194042**   |
    | 68 с     | 1061          | 1287           | \$0.055118       |

    Во втором вызове `auto` выбрал более высокий уровень качества, количество выходных token выросло до 5146, а цена увеличилась примерно в 3,5 раза.

    **Исправление: не оставляйте `quality` со значением `auto` — явно передавайте `low` / `medium` / `high`.** При фиксированном уровне количество выходных token и цена для одинаковых входных данных становятся стабильными и предсказуемыми. См. раздел «Справочник по качеству» выше.
  </Accordion>

  <Accordion title="Каковы ограничения на количество и размер изображений для эндпоинта редактирования?">
    Эндпоинт редактирования изображений `gpt-image-2` (`/v1/images/edits`) поддерживает до **16** референсных изображений:

    * **Загрузка файла через multipart/form-data**: размер каждого изображения должен быть **менее 50 МБ**, форматы `png` / `jpg` / `webp`
    * **URL данных base64**: ограничение длины поля составляет около **20 МиБ** (схема `maxLength: 20971520` — это ограничение строкового поля, **не совпадающее** с ограничением 50 МБ для multipart), поэтому исходные изображения должны быть размером не более **15 МБ**
    * **Файл маски**: отдельное ограничение — **PNG менее 4 МБ**

    Практический совет: не отправляйте одновременно несколько изображений большого размера — слишком объёмные тела запросов часто завершаются ошибкой на уровне шлюза или тайм-аута. Наиболее надёжный вариант — сжать каждое изображение до **1,5 МБ или меньше**; качество результата не связано с размером входного файла.
  </Accordion>

  <Accordion title="Эндпоинт редактирования возвращает ошибку 400 «Invalid image file or mode for image 1» — что делать?">
    Эта ошибка (`code: invalid_image_file`) означает: **N-е референсное изображение не является стандартным файлом png / jpg / webp** (нумерация начинается с 1 — используйте индекс, чтобы найти проблемное изображение).

    Наиболее распространённая причина — **формат MPO** в камерах телефонов: файлы `.jpg`, полученные непосредственно с телефонов серии Huawei Mate, содержат встроенный дополнительный кадр HDR gain-map и фактически являются много кадровыми контейнерами JPEG (MPO). Заголовок имеет тот же `FFD8`, а расширение и команда `file` сообщают о формате JPEG — визуально это невозможно определить. Проверено в июле 2026 года: файлы MPO всегда отклоняются, а те же изображения, перекодированные в стандартный JPEG/PNG, успешно обрабатываются **в полном исходном разрешении** (это не связано с размерами, именем поля `image[]` или параметрами `quality`/`size`). Ошибка возвращается на этапе проверки входных данных и **не тарифицируется**.

    **Исправление**: перекодируйте изображение с помощью Pillow перед загрузкой (если `Image.open(f).format` возвращает `"MPO"`, требуется конвертация):

    ```python theme={null}
    from PIL import Image
    im = Image.open("photo.jpg")
    im.load()                          # for MPO, keeps only the first frame
    im.convert("RGB").save("photo_fixed.jpg", quality=92)
    ```

    Полные сведения и способ обнаружения: [Image Edit API — требования к формату и предварительной обработке референсных изображений](/ru/api-capabilities/gpt-image-2/image-edit#reference-image-format-requirements-and-preprocessing).
  </Accordion>

  <Accordion title="Как подготовить файл маски?">
    * **Тот же размер**, что и у исходного изображения, **формат PNG**, **менее 4 МБ**
    * **Должен иметь альфа-канал**: прозрачная область (alpha=0) = область для закрашивания, непрозрачная = сохранить
    * Применяется только к первому изображению
    * Маска — это «мягкая направляющая»: модель может расширить или сузить область вокруг замаскированного участка
  </Accordion>

  <Accordion title="gpt-image-2 и gpt-image-2-all: что выбрать?">
    | Выберите                                                       | Когда использовать                                                                                                                                                                                             |
    | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | **gpt-image-2.5-flare / sunburst / gpt-image-2** (официальные) | Нужен точный контроль размера и качества, требуется полное соответствие официальному OpenAI, нужен вывод 4K или рисование по маске; flare — самая быстрая из трёх моделей, sunburst — наиболее точный редактор |
    | **gpt-image-2-all** (реверс)                                   | Нужна фиксированная цена \$0.03 за изображение, генерация за 30–60 с, минимум параметров, высокая согласованность или качественная генерация китайского текста                                                 |
  </Accordion>

  <Accordion title="Можно ли напрямую использовать официальный SDK OpenAI?">
    Да — изменения в коде не требуются. Укажите для `base_url` значение `https://api.apiyi.com/v1`, а для `api_key` задайте свой token APIYI:

    ```python theme={null}
    from openai import OpenAI
    client = OpenAI(api_key="sk-your-key", base_url="https://api.apiyi.com/v1")
    resp = client.images.generate(model="gpt-image-2.5-flare", prompt="...", size="2048x1152", quality="high")
    ```
  </Accordion>

  <Accordion title="Можно ли отменить выполняющуюся генерацию?">
    **Нет**. `gpt-image-2` использует официальный синхронный эндпоинт OpenAI — после отправки запроса он выполняется до конца, без сигнала «отмена». Даже если клиент отключится, сервер всё равно завершит генерацию и выполнит обычную тарификацию. Тщательно настройте тайм-ауты на стороне клиента — не предполагайте, что «отключение = отсутствие платы».
  </Accordion>

  <Accordion title="Есть ли лимит запросов (RPM)?">
    По умолчанию — **100 RPM** (100 запросов в минуту). Фактически доступный RPM также динамически регулируется **общим количеством параллельных запросов на платформе**. Если вашей рабочей нагрузке требуется больше, свяжитесь с нами, указав предполагаемые QPS / RPM, и мы сможем предоставить дополнительную ёмкость.
  </Accordion>

  <Accordion title="Поддерживается ли асинхронный вызов?">
    **Нет**. `gpt-image-2` строго повторяет официальный API OpenAI и работает только синхронно. Запрос блокируется до возврата результата (`high` + 4K — в реальных условиях 1–2 минуты). Если вам нужна асинхронная очередь или механизм обратного вызова:

    * Реализуйте его самостоятельно на уровне бизнес-логики с помощью очереди задач (Celery / BullMQ и т. п.)
    * Либо используйте [`gpt-image-2-all`](/ru/api-capabilities/gpt-image-2-all/overview) — генерация занимает 30–60 с, а опрос из клиентской части выполнять проще
  </Accordion>

  <Accordion title="Есть ли ограничение на длину промпта? Почему в веб-приложение ChatGPT можно вставить больше текста?">
    Да: **32 000 символов** — ограничение провайдера OpenAI Images API, подсчитываемое в символах, а не в token; официальный шлюз APIYI его не ужесточает. Веб-приложение кажется неограниченным только потому, что чат-модель считывает вставленный текст, а затем сама формирует короткий промпт для инструмента изображений, поэтому модель изображений никогда не видит исходный материал. Для больших материалов, таких как брендбуки или спецификации упаковки, сначала сократите их с помощью текстовой модели до структурированного промпта длиной от 1K до 3K символов; см. раздел [Длинные промпты](/ru/api-capabilities/image-long-prompt).
  </Accordion>

  <Accordion title="Ошибка 400 с safety_violations=[sexual] для промпта без явного содержания. Что делать?">
    Большинство таких блокировок происходит **после рендеринга изображения**: изображение генерируется, а затем отклоняется классификатором на стороне результата, поэтому неудачный вызов занимает столько же времени, сколько успешный, а один и тот же промпт иногда проходит, а иногда отклоняется. `moderation: low` лишь снижает модерацию на стороне промпта и здесь не помогает. Наиболее распространённая причина — персонаж описан через настроение, но без одежды, поэтому модель импровизирует и переходит допустимую границу: **сначала добавьте одну явную фразу об одежде** (оставив всё остальное без изменений), и только затем удаляйте по одному слову. Полный разбор случая и журнал из 20 вызовов: [Отклонения по требованиям безопасности](/ru/api-capabilities/image-safety-troubleshooting).
  </Accordion>

  <Accordion title="Тарифицируются ли неудачные генерации?">
    **Нет**. Встроенная модерация контента OpenAI отклоняет небезопасные или некорректно сформированные запросы с ошибкой `400`, и **плата не взимается**. Типичный ответ:

    ```json theme={null}
    {
      "status_code": 400,
      "error": {
        "message": "Your request was rejected by the safety system. ...",
        "type": "shell_api_error",
        "code": "moderation_blocked"
      }
    }
    ```

    Другие ошибки без тарификации: `401` (недействительный token), `429` (лимит запросов). **Тарификация по количеству token начинается только после фактического перехода запроса к этапу генерации моделью (то есть после получения `200` + `b64_json`).**
  </Accordion>
</AccordionGroup>
