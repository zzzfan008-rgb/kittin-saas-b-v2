# GPT-Image-2.5 / 2 이미지 생성/편집

> OpenAI의 GPT-Image 2.5 / 2 시리즈를 위한 공식 릴레이 가이드입니다. gpt-image-2.5-flare(속도 우선), gpt-image-2.5-sunburst(편집 정밀도 우선), gpt-image-2를 모두 동일한 가격과 매개변수로 사용할 수 있습니다. 기본 2K/4K 임의 해상도, 자동 고충실도 참조 이미지, 텍스트-이미지 변환, 참조 이미지 편집, 다중 이미지 융합, 마스크 인페인팅을 지원합니다.

<Info>
  모든 이미지 API는 **동기식**입니다 — 폴링할 task ID가 없으며, 클라이언트 연결이 끊기면 요청은 계속 과금되는 상태에서 결과가 유실됩니다. 이 모델에는 넉넉한 timeout을 설정하십시오. [이미지 API 필수 사항 및 모범 사례](/ko/api-capabilities/image-api-best-practices)를 참조하십시오.
</Info>

## 개요

이 페이지에서는 APIYI의 공식 릴레이를 통해 OpenAI의 **GPT-Image 2.5 / 2 시리즈**를 다룹니다: **`gpt-image-2.5-flare`**(속도 우선), **`gpt-image-2.5-sunburst`**(품질 및 편집 정밀도 우선), 그리고 이전 세대의 \*\*`gpt-image-2`\*\*입니다. 2.5 모델은 2026-09-08에 출시되었으며, gpt-image-2보다 높은 품질, 더 정밀한 편집, 두 가지 새로운 `quality` 등급(`xhigh` / `max`)을 제공하면서도 **gpt-image-2와 가격 및 파라미터가 정확히 동일합니다**. 시리즈 공통 기능: **모든 유효 해상도 지원(2K / 3840×2160 4K 포함)**, **참조 이미지 자동 고충실도 처리**, **token 단위 과금**. APIYI의 게이트웨이는 OpenAI Images API와 완벽하게 호환됩니다. 코드 변경 없이 직접 연결하려면 공식 OpenAI SDK의 `base_url`를 여기로 지정하면 됩니다.

<Note>
  **🎨 주요 특징**: 모든 유효 해상도(최대 3840×2160 4K) 네이티브 지원 + 참조 이미지 편집 시 자동 고충실도 처리 + 네이티브 중국어 prompt 지원 + 2.5의 새로운 `xhigh` / `max` 품질 등급. **정밀한 크기/품질 제어가 필요하거나, OpenAI 공식 API와 완전히 동일해야 하거나, 4K 출력이 필요한 프로덕션 시나리오에 가장 적합**합니다. 기본 텍스트-이미지는 `gpt-image-2.5-flare`, 편집은 `gpt-image-2.5-sunburst`를 사용합니다.
</Note>

<Prompt description="코딩 에이전트가 GPT-Image 2.5 / 2 시리즈의 텍스트-이미지 및 이미지 편집을 통합하거나 문제를 해결하도록 하십시오. Codex, Claude Code, Cursor 및 유사한 도구에 복사하여 붙여 넣으십시오." icon="bot" actions={["copy"]}>
  이 프로젝트에서 GPT-Image 2.5 시리즈의 텍스트-이미지 및 이미지 편집을 통합하거나 문제를 해결하십시오. 텍스트-이미지에는 `gpt-image-2.5-flare`을 사용하고 이미지 편집에는 `gpt-image-2.5-sunburst`을 사용하십시오(둘 다 `gpt-image-2`과 가격 및 매개변수를 공유하므로 모델 이름은 쉽게 전환할 수 있도록 구성 값으로 만드십시오).

  코드를 수정하기 전에 문서를 읽으십시오. 이 페이지의 일반 텍스트 버전을 가져오려면 [https://docs.apiyi.com/en/api-capabilities/gpt-image-2/overview.md](https://docs.apiyi.com/en/api-capabilities/gpt-image-2/overview.md) 를 가져오십시오. 더 자세한 매개변수 정보가 필요하면 같은 방식으로 텍스트-이미지 및 이미지 편집 페이지에 `.md`을 추가하십시오.

  요구사항:

  1. 타임아웃: 클라이언트 타임아웃을 360초로 늘리십시오. 이미지 API는 동기식이므로 작업 ID가 없습니다. 따라서 클라이언트 연결이 끊기면 요청에 대한 과금이 계속되는 동안 결과가 손실됩니다. 너무 일찍 타임아웃하지 말고 기다리십시오. 리버스 프록시, 게이트웨이 및 서버리스 실행 제한도 모두 늘려야 합니다. 생성 시간보다 짧은 계층이 하나라도 있으면 요청이 중단됩니다.

  2. 응답 렌더링: `/v1/images/generations`은 항상 base64(`b64_json`이며 `data:` 접두사가 없음)를 반환하고 URL은 반환하지 않습니다. 프런트엔드는 해당 base64를 이미지로 렌더링하고 디스크에 저장하는 작업을 제공해야 합니다. `response_format`을 전송하지 마십시오. 400 오류가 반환됩니다. `input_fidelity`도 전송하지 마십시오.

  3. 업로드 전 압축: `/v1/images/edits`을 호출하기 전에(멀티파트, 참조 이미지 최대 16개) 각 참조 이미지를 압축하십시오. 1.5MB를 초과하는 파일만 처리하고, 가로세로 비율을 유지하면서 긴 변을 2048px로 줄이십시오(작은 이미지는 절대 확대하지 마십시오). 품질 0.9로 다시 인코딩하되 원래 형식을 유지하십시오. 여러 이미지를 요청하는 경우 합산 크기를 6MB 미만으로 유지하십시오. 이미지 하나의 압축에 실패하면 원본으로 대체하여 계속 진행하십시오. 압축 실패 때문에 전체 요청을 중단해서는 안 됩니다.

  4. 품질 등급: 항상 `quality`을 전송하고 기본값은 `medium`으로 설정하십시오. 또한 UI에 품질 드롭다운을 추가하십시오(`low` / `medium` / `high` / `xhigh` / `max`. 마지막 두 항목은 2.5 모델에서만 허용되며 비용이 더 높습니다). 2.5에서 등급이 다시 조정되었다는 점에 유의하십시오. 2.5 `high`은 `gpt-image-2` `medium`에만 해당하므로 `gpt-image-2`에서 마이그레이션할 때 `quality`을 그대로 가져오지 마십시오. 동일한 예산에는 `max`을 전송하십시오. `auto`은 동적 추론 등급이므로 전송하지 마십시오. 비용과 지연 시간이 변동합니다.

  5. 프로덕션에서는 모델 별칭이 변경되어도 모델이 바뀌지 않도록 날짜가 지정된 스냅샷 `gpt-image-2.5-flare-2026-09-08` / `gpt-image-2.5-sunburst-2026-09-08`에 모델 이름을 고정하십시오.

  6. `APIYI_API_KEY` 환경 변수에서 키를 읽고 [https://api.apiyi.com/v1](https://api.apiyi.com/v1) 을 기본 URL로 사용하십시오. 키를 하드코딩하거나 git에 커밋하지 마십시오.

  7. 완료되면 실제로 텍스트-이미지 호출을 한 번, 이미지 편집 호출을 한 번 실행한 다음 결과와 두 호출의 비용을 보여주십시오.
</Prompt>

## 모델 선택: flare / sunburst / gpt-image-2

2026-09-08부터 이 문서 그룹에서는 세 가지 OpenAI GPT-Image 2.5 / 2 모델을 다룹니다. **세 모델은 모두 동일한 가격, 매개변수, 그룹 및 엔드포인트를 공유**하며, 전환은 한 필드 `model`만 변경하면 됩니다.

| 항목                          | `gpt-image-2.5-flare`                                                 | `gpt-image-2.5-sunburst`                  | `gpt-image-2`                      |
| --------------------------- | --------------------------------------------------------------------- | ----------------------------------------- | ---------------------------------- |
| 포지셔닝                        | 속도 우선 소형 모델, OpenAI가 권장하는 일상적인 기본값                                    | 품질 우선 기본 모델, 현재 OpenAI의 가장 강력한 생성 / 편집 모델 | 이전 세대 단일 플래그십으로, 여전히 사용 가능         |
| 품질                          | gpt-image-2보다 높음                                                      | 세 모델 중 가장 높음                              | 기준 수준                              |
| 지연 시간(1024², 2026-09-09 측정) | `low` 10초 / `high` 21초 / `max` 45초; OpenAI 기준 gpt-image-2보다 최대 50% 낮음 | `low` 14초 / `high` 42초 / `max` 142초       | `low` 21초 / `high` 224초            |

</Tip>

### 2.5 모델의 품질 단계 및 측정된 비용 (측정일: 2026-09-09)

**동일한 티어 이름이 2.5와 gpt-image-2에서 동일한 token 수를 의미하지는 않습니다**: 2.5에서는 품질 단계가 다시 분류됩니다. `low`는 변경되지 않고, 2.5의 `high`는 gpt-image-2의 `medium`와 같으며, 2.5의 `max`는 gpt-image-2의 `high`와 같습니다. 표에는 `usage.output_tokens` 및 1024×1024 텍스트-이미지 변환의 \$30 / 1M 기준 출력 비용이 표시되어 있으며, 동일한 prompt로 각각 한 번씩 순차 실행한 결과입니다(flare와 sunburst는 티어별 token 수가 동일하고 지연 시간만 다릅니다).

| 품질       | gpt-image-2                    | gpt-image-2.5-flare           | gpt-image-2.5-sunburst         |
| -------- | ------------------------------ | ----------------------------- | ------------------------------ |
| `low`    | 196 tokens ≈ \$0.006 (21 s)    | 196 tokens ≈ \$0.006 (10 s)   | 196 tokens ≈ \$0.006 (14 s)    |
| `medium` | 1,756 tokens ≈ \$0.053 (63 s)  | 439 tokens ≈ \$0.013 (10 s)   | 439 tokens ≈ \$0.013 (19 s)    |
| `high`   | 7,024 tokens ≈ \$0.211 (224 s) | 1,756 tokens ≈ \$0.053 (21 s) | 1,756 tokens ≈ \$0.053 (42 s)  |
| `xhigh`  | ❌ 400                          | 3,122 tokens ≈ \$0.094 (31 s) | 3,122 tokens ≈ \$0.094 (60 s)  |
| `max`    | ❌ 400                          | 7,024 tokens ≈ \$0.211 (45 s) | 7,024 tokens ≈ \$0.211 (142 s) |

<Warning>
  **gpt-image-2에서 마이그레이션할 때 `quality`를 그대로 가져오지 마십시오**: 동일한 `high`를 사용하면 2.5에서는 출력 token 수가 4분의 1이 되고 품질 단계에서 더 낮은 단계로 매핑됩니다. gpt-image-2의 `high`와 token 예산을 맞추려면 2.5에서 `max`을 전송하십시오. 반대로 2.5의 `high` / `xhigh`을 사용하면 동일한 예산으로 더 저렴한 중간 단계 두 개를 이용할 수 있습니다. 자체 prompt를 한 번 실행하고 프로덕션에 적용하기 전에 `usage.output_tokens`를 확인하십시오. 2K / 4K는 픽셀 비율을 기준으로 추정하십시오.
</Warning>

### 여러 입력 이미지가 가격에 미치는 영향(2026년 7월 검증됨)

많은 고객이 묻는 질문입니다. "참조 이미지마다 정액 요금이 적용되나요, 아니면 더 큰 이미지일수록 더 많은 tokens가 드나요?" 답은 **둘 다 영향을 미치며, 이미지 수는 엄격하게 선형적으로 누적됩니다**. `gpt-image-2`는 모든 입력 이미지를 강제 고해상도로 처리하며(`input_fidelity`는 조정할 수 없습니다. 이를 전달하면 400이 반환됩니다), 각 참조 이미지는 크기와 종횡비에 따라 image token으로 변환됩니다. 통제된 측정값(편집 endpoint, 2026-07-15):

| 참조 이미지 입력           | `image_tokens`        | 입력 비용 (\$8/M) |
| ------------------- | --------------------- | ------------- |
| 1 × 512×512         | 1024                  | ≈\$0.0082     |
| 1 × 1024×1024       | 1024                  | ≈\$0.0082     |
| 1 × 2048×2048       | 1521                  | ≈\$0.0122     |
| 1 × 4096×4096       | 1521                  | ≈\$0.0122     |
| 1 × 1024×1536 (세로형) | 1536                  | ≈\$0.0123     |
| **4 × 1024×1024**   | **4096 (= 4 × 1024)** | ≈\$0.0328     |

세 가지 경험칙입니다.

1. **개수는 엄격하게 선형입니다**: N개의 참조 이미지는 대략 N × 단일 이미지 tokens입니다. 1024² 해상도의 참조 이미지 16장은 ≈ 16384 tokens ≈ \$0.13으로, 하나의 `high` 출력(\$0.211)과 같은 자릿수이므로 여러 이미지 융합에서는 더 이상 무시할 수 없습니다.
2. **크기에는 하한과 상한이 모두 있습니다**: 1024² 이하의 정사각형 이미지는 모두 1024 tokens로 과금됩니다(512로 줄여도 **절약되는 것은 없습니다**). 2048²와 4096²는 모두 1521 tokens가 듭니다(과도하게 큰 이미지는 변환 전에 축소되므로 **상한이 적용됩니다**). 단일 참조 이미지는 종횡비를 포함해 대략 800\~1600 token 범위에 들어갑니다.
3. **tokens는 파일 크기가 아니라 픽셀 크기로 결정됩니다**: 1.5MB로 압축하면 업로드 안정성과 속도는 좋아지지만 **image tokens는 줄지 않습니다**. 반대로 50MB 원본을 올려도 요금이 폭증하지는 않습니다(상한이 적용됩니다).

<Tip>
  비용 감각: `low` 출력(196 tokens ≈ \$0.006)에서는 참조 이미지 1장의 입력 비용(≈\$0.008)이 실제로 출력보다 더 큽니다. `high` 출력(≈\$0.211)에서는 참조 이미지 1장이 약 4%에 불과합니다. **출력 크기와 품질이 언제나 가장 큰 가격 레버입니다** — 참조 이미지 수는 그다음입니다.
</Tip>

### 2K/4K 비용 추정치(픽셀 비율 외삽, ⚠️ 공식 고정 가격 아님)

OpenAI는 1K 크기에 대해서만 이미지당 고정 가격표를 공개합니다 — **2K/4K에 대한 공식적인 크기별 가격은 없습니다**. 아래 표는 위의 1K 공식 요율을 기준으로 픽셀 수에 따라 스케일링한 APIYI의 자체 외삽이며, 예산 산정용일 뿐입니다:

| 품질 | 2048×2048 (2K 정사각형) | 2048×1152 (2K 가로형) | 3840×2160 / 2160×3840 (4K) |
| -- | ------------------- | ------------------ | -------------------------- |
| 낮음 | ≈\$0.024            | ≈\$0.008           | ≈\$0.026                   |
| 중간 | ≈\$0.212            | ≈\$0.062           | ≈\$0.216                   |
| 높음 | ≈\$0.844            | ≈\$0.248           | ≈\$0.870                   |

<Warning>
  **이것은 추정치이며, 공식 가격표가 아닙니다.** 방법: 같은 종횡비의 1K 공식 행을 기준선으로 사용한 뒤, 목표 크기의 픽셀 수를 해당 기준선 대비 비율로 선형 스케일링합니다(예: 2048×2048은 1024×1024보다 픽셀이 4배이므로 추정 비용도 ×4입니다). 실제 출력 image token 수는 콘텐츠 복잡도에 따라 모델이 동적으로 결정하며, 엄밀히 선형적이지는 않으므로 **실제 응답의 `usage.output_tokens`을 기준으로 삼으십시오**(아래의 "각 호출의 실제 token 수를 확인하는 방법" 참조). `high` 품질에서 2560×1440을 초과하는 크기는 여전히 공식 실험 단계이므로, 그 구간의 추정치는 정확도가 떨어질 수 있습니다.
</Warning>

### SaaS 구독 / 크레딧 기반 과금과의 차이

이미지 생성 도구 제공업체는 일반적으로 두 가지 방식으로 과금합니다.

* **월간 구독 요금제**: 월 정액으로 “월 N개 이미지” 쿼터를 제공하는 방식입니다. 이 쿼터는 **과대 판매 가정**을 바탕으로 가격이 책정됩니다. 즉, 제공업체는 대부분의 사용자가 할당량을 모두 사용하지 않을 것이라는 기대를 가격에 반영하므로, 광고되는 “이미지당 비용”은 실제로 개별 이미지를 생성하는 데 드는 비용이 아니라 요금제 가격을 쿼터 상한으로 나눈 값에 불과합니다.
* **크레딧 / 포인트 기반 계량**: 품질이나 크기가 다른 작업을 불투명한 “크레딧”으로 환산합니다. 이는 사실상 내부적으로는 사용량 기반 과금이지만, 실제 token 소비를 가리는 크레딧 단위 뒤에 다시 포장한 것에 불과합니다.

APIYI는 **공식 릴레이 + 실제 token 계량 과금** 모델로 운영됩니다. 요금제 쿼터도 없고, 크레딧 추상화 계층도 없습니다. 각 호출의 비용은 단순히 실제 입력/출력 token × 공식 요율이며, 구독의 과대 판매나 한도를 초과했을 때의 차단 동작 없이 호출 단위로 정확하게 계산됩니다.

<Tip>
  사용량 기반 과금의 트레이드오프는 구독처럼 월 고정 총액의 확실성을 얻는 대신 사용량을 직접 추정하고 모니터링해야 한다는 점입니다. 장점은 실제로 사용한 만큼만 지불하므로 유휴 낭비가 없다는 것입니다. 아래 방법을 사용하면 응답에서 각 호출의 실제 token 수를 바로 추출하여 직접 정산할 수 있습니다.
</Tip>

### 각 호출의 실제 token 수를 확인하는 방법

`/v1/images/generations`과 `/v1/images/edits` 모두 `usage` 필드를 반환하며, **이미지 입력 token과 텍스트 입력 token은 별도의 필드로 반환됩니다**. 추정할 필요 없이 해당 값을 읽으면 호출별 정확한 비용을 확인할 수 있습니다. 다음은 참조 이미지 한 장을 포함한 실제 편집 요청에서 실시간으로 캡처한 전체 `usage` 객체입니다.

```json theme={null}
{
    "data": [ { "b64_json": "..." } ],
    "usage": {
        "input_tokens": 848,
        "input_tokens_details": {
            "image_tokens": 832,
            "text_tokens": 16
        },
        "output_tokens": 196,
        "output_tokens_details": {
            "image_tokens": 196,
            "text_tokens": 0
        },
        "total_tokens": 1044
    }
}
```

| 필드                                        | 의미                                                                                                                                                                                                  |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `usage.input_tokens_details.text_tokens`  | 프롬프트 텍스트에 사용된 token으로, 1M당 \$5.00의 요율로 과금됩니다                                                                                                                                                        |
| `usage.input_tokens_details.image_tokens` | Vision 규칙에 따라 참조 이미지에서 변환된 token으로, 1M당 \$8.00의 요율로 과금됩니다. 참조 이미지가 없는 일반 텍스트-이미지 변환에서는 항상 0입니다                                                                                                      |
| `usage.input_tokens`                      | 위 두 필드의 합계입니다                                                                                                                                                                                       |
| `usage.output_tokens`                     | 생성된 이미지에 사용된 token으로, `quality × size`에 따라 결정됩니다. 이는 **주요 비용**이며 1M당 \$30.00의 요율로 과금됩니다. 2K/4K 요청에서 특히 주의해서 확인해야 하는 수치입니다(`output_tokens_details.image_tokens`에도 이 값이 반영되며, `text_tokens`는 항상 0입니다) |
| `usage.total_tokens`                      | 입력과 출력을 합산한 값입니다                                                                                                                                                                                    |

셀프서비스 비용 계산식(정확한 계산식):

```
cost ≈ input_tokens_details.text_tokens × \$5.00 / 1,000,000
     + input_tokens_details.image_tokens × \$8.00 / 1,000,000
     + output_tokens × \$30.00 / 1,000,000
```

<Tip>
  과거 호출의 실제 token 사용량과 과금 세부 정보를 검토하려면 콘솔의 “로그” 페이지를 확인하십시오: 📖 [호출 로그를 확인하는 방법](/ko/faq/call-logs) — 로그 세부 정보 화면에는 API의 `usage.input_tokens_details` / `usage.output_tokens_details`와 일치하는 텍스트 입력 / 이미지 입력 / 출력 가격과 해당 token 수가 함께 표시됩니다.
</Tip>

## 크기 참조

### 사전 설정된 크기

| size        | 의미       | Pixels    |
| ----------- | -------- | --------- |
| `auto`      | 적응형(기본값) | 모델이 결정합니다 |
| `1024x1024` | 정사각형 1:1 | 1K        |
| `1536x1024` | 가로형 3:2  | 1K        |
| `1024x1536` | 세로형 2:3  | 1K        |
| `2048x2048` | 정사각형 1:1 | 2K        |
| `2048x1152` | 가로형 16:9 | 2K        |
| `3840x2160` | 가로형 16:9 | 4K        |
| `2160x3840` | 세로형 9:16 | 4K        |

### 사용자 지정 크기 제약

`gpt-image-2`은 다음 조건을 모두 만족하는 유효한 크기라면 무엇이든 허용합니다.

1. **최대 변 ≤ 3840px**
2. **양쪽 변이 모두 16의 배수**
3. **가로세로 비율 ≤ 3:1**
4. **총 픽셀 수 ∈ \[655,360, 8,294,400]** (\~0.65MP to \~8.3MP)

**유효한 예시**: `1600x1200`, `1792x1024`, `2048x1536`, `3200x1800`
**유효하지 않은 예시**: `1000x1000` (16의 배수가 아님), `4000x4000` (최대값 초과), `3840x1000` (비율 > 3:1)

<Warning>
  `2560×1440`을 초과하는 출력은 (\~3.69MP) 공식적으로 **실험적**으로 표시되며 품질 변동이 있을 수 있습니다. 프로덕션에서는 `2048x1152` / `2048x2048` / `3840x2160` 같은 사전 설정을 사용하는 것이 좋습니다.
</Warning>

## 품질 참고

### 사용 가능한 티어

| 품질       | 의미                          | 참고                                                                     |
| -------- | --------------------------- | ---------------------------------------------------------------------- |
| `auto`   | 자동 (**기본값**)                | `quality`이 생략될 때 사용되는 값입니다 — 모델이 티어를 자동으로 선택합니다                        |
| `low`    | 낮은 품질                       | 가장 빠르고 저렴합니다 — 초안 / 배치에 적합합니다                                          |
| `medium` | 중간 품질                       | 일상적인 사용 / 최종 출력에 균형 잡힌 선택입니다                                           |
| `high`   | 높은 품질                       | 텍스트, 세밀한 텍스처, 인쇄에 적합합니다. `gpt-image-2`에 가장 높은 티어입니다                    |
| `xhigh`  | 매우 높은 품질 (**2.5에서 새로 추가됨**) | `gpt-image-2.5-flare` / `sunburst`에서만 허용됩니다. `high`보다 출력 token 수가 많습니다 |
| `max`    | 최고 품질 (**2.5에서 새로 추가됨**)    | 2.5 모델 두 개에서만 허용됩니다. 비용과 지연 시간이 가장 높으며, 프로덕션 수준의 최종 출력에 적합합니다          |

<Warning>
  **기본값은 `auto`이며 `medium`이 아닙니다.** `quality`을 생략하는 것은 `"quality": "auto"`을 전달하는 것과 같습니다 — 모델이 품질 티어를 자동으로 선택하며, **OpenAI는 이것이 `medium`에 매핑된다고 보장하지 않습니다.** `auto`가 확인하는 티어는 예측할 수 없으며 비용, 지연 시간, 과금 안정성에 직접적인 영향을 줍니다. **비용을 제어하고 예측 가능성을 확보해야 하는 경우에는 `auto`에 의존하지 말고 `low` / `medium` / `high` / `xhigh` / `max` 중 하나를 명시적으로 전달해야 합니다.**
</Warning>

<Warning>
  **레거시 DALL·E 값인 `standard` / `hd`은 전달하지 마십시오.** `quality`은 공식 enum 값 6개인 `low` / `medium` / `high` / `xhigh` / `max` / `auto`만 허용하며, `xhigh` / `max`는 2.5 모델 두 개에서만 허용됩니다. 레거시 DALL·E 3 값인 `standard` / `hd`은 백엔드 채널에 따라 일관되지 않게 동작합니다. 경우에 따라 400(`invalid_value`) 오류와 함께 즉시 실패하며, 경우에 따라 조용히 무시되고 요청이 `auto`에서 실행됩니다(예측할 수 없는 비용). 항상 공식 값 중 하나를 명시적으로 전달해야 합니다.
</Warning>

<Info>
  **`quality`는 가격에 가장 큰 영향을 미치며, `size`보다도 영향이 큽니다.** 이미지 출력 token 수는 `quality × size`에 의해 결정되지만 `quality`의 영향이 훨씬 큽니다. 동일한 크기에서 `low`에서 `high`로 변경하면 이미지당 비용이 **30배 이상** 달라질 수 있습니다(위의 "이미지당 비용" 표를 참조하십시오. 1024×1024에서 gpt-image-2는 `low` \$0.006부터 `high` \$0.211까지이며, 2.5 모델은 `low` \$0.006부터 `max` \$0.211까지입니다). 먼저 `quality`로 비용을 추정한 다음 `size`의 영향을 반영하십시오.
</Info>

## 모범 사례

<Warning>
  **온보딩 팁: 먼저 `low`로 API가 작동하도록 만든 다음 확장하십시오**

  신규 연동 사용자가 곧바로 `quality=high` + 고해상도로 시작했다가 \*\*이미지당 약 235초(약 4분)\*\*를 기다린 뒤 API가 멈췄다고 의심하는 사례를 보았습니다. `high` 모드는 추론 복잡도가 가장 높으며, 4K에서는 거의 5분까지 늘어날 수 있습니다. **프로덕션으로 전환하기 전에 먼저 `quality=low`로 엔드투엔드 연동을 완료하십시오**(인증, SDK, 파라미터, 타임아웃, 오류 처리). 이후 실제 품질 요구 사항에 따라 필요한 경우에만 `medium` / `high`로 올리십시오.
</Warning>

<Steps>
  <Step title="낮은 설정으로 먼저 연동">
    새 연동의 경우, 전체 호출 체인(인증, 파라미터, 타임아웃, 오류 처리)을 검증하기 위해 **`quality=low` + 사전 설정 크기**로 시작하십시오. `low`는 `high`보다 몇 배 더 빠르므로, 긴 지연 시간에 가려지지 않고 기능 문제를 빠르게 확인할 수 있습니다.
  </Step>

  <Step title="사전 설정 크기 우선 사용">
    공식 사전 설정 8개는 안정적인 속도와 품질에 맞게 조정되어 있습니다. 실제로 특이한 화면 비율이 필요한 경우에만 사용자 지정 크기를 사용하십시오.
  </Step>

  <Step title="시나리오에 맞는 품질 선택">
    초안 / 배치 작업 → `low`, 일상 작업 / 최종 결과물 → `medium`, 텍스트·미세 질감·인쇄 → `high`. **`low` ↔ `high`는 단순한 시각적 충실도 차이 이상이며, 추론 복잡도도 단계적으로 증가합니다**. 따라서 지연 시간도 그에 따라 증가합니다.
  </Step>

  <Step title="JPEG 출력 선택">
    최종 표시용으로는 `output_format=jpeg` + `output_compression=85`가 PNG보다 빠르고 크기도 대략 절반입니다.
  </Step>

  <Step title="텍스트 시나리오에서는 고품질 고정">
    텍스트 렌더링은 핵심 강점이지만, 낮은 등급에서는 여전히 흐려질 수 있습니다. 간판 및 포스터 시나리오에서는 `quality=high`를 고정하십시오.
  </Step>

  <Step title="참조 이미지 준비">
    이미지당 최대 50MB입니다(실무에서는 1.5MB 이내로 압축). PNG/JPEG/WebP를 지원하며, 최대 16개 이미지를 사용할 수 있습니다. prompt에서 ‘이미지 1 / 이미지 2’와 같이 참조 순서를 지정하십시오.
  </Step>

  <Step title="투명 배경: 파라미터를 전달하고 prompt에서 장면을 제외">
    `background: "transparent"`와 `png` / `webp`는 알파 채널만 보장합니다. **prompt 또는 참조 이미지가 완전한 장면(숲, 방, 거리)을 설명하면 모델은 해당 장면을 그립니다**. 이 파라미터는 이를 막지 못하며, 이것이 투명 배경이 ‘가끔 작동하는’ 주된 이유입니다. `quality`와는 관련이 없습니다(2026-09-11 측정: 피사체만 있는 prompt는 16/16 투명, 장면 prompt는 0/3, 중간 및 고품질 모두 동일). prompt 끝에 `isolated subject on a transparent background, no scenery, no ground`를 추가하십시오. 참조 이미지에 배경이 있으면 편집 prompt에서 `remove the background entirely, keep only the subject`라고 명시하십시오. [투명 배경 FAQ](/ko/faq/image-transparent-background)를 참조하십시오.
  </Step>

  <Step title="클라이언트 타임아웃을 등급별로 설정(고품질 → 600초 안전망)">
    지연 시간을 좌우하는 두 파라미터는 **`quality`** 및 \*\*`size`\*\*이며, 특히 `quality`의 영향이 큽니다. 등급별로 클라이언트 타임아웃을 설정하십시오.

    | 품질               | 권장 클라이언트 타임아웃   | 관측된 지연 시간                                                                                           |
    | ---------------- | --------------- | --------------------------------------------------------------------------------------------------- |
    | `low`            | ≥ **120초**      | 일반적으로 10\~40초                                                                                       |
    | `medium`         | ≥ **240초**      | 일반적으로 30\~90초                                                                                       |
    | `high`           | ≥ **600초**(안전망) | gpt-image-2 2K/4K 실행은 3~~5분, 긴 꼬리 지연은 235초 이상으로 관측됨. 2.5 모델은 1024²에서 21~~42초로 측정됨                   |
    | `xhigh` (2.5 전용) | ≥ **300초**      | 1024²에서 31\~60초로 측정됨(2026-09-09), 2K/4K에서는 더 길어짐                                                    |
    | `max` (2.5 전용)   | ≥ **600초**(안전망) | 1024²에서 45\~142초로 측정됨. gpt-image-2 `high`와 token 수가 같으므로, 2K/4K는 gpt-image-2 `high`와 동일하게 예산을 잡으십시오 |

    **`high` 모드에서는 큐 대기, 긴 꼬리 변동, 업스트림 지터를 흡수할 수 있도록 안전망 타임아웃을 600초로 설정하십시오.** UI에 진행 상태를 표시하고 서버 측 작업 큐를 고려하십시오.
  </Step>

  <Step title="마이그레이션 참고 사항">
    `gpt-image-1.5`에서 마이그레이션하는 경우: `input_fidelity`를 제거하십시오(고충실도를 강제하며, 전달하면 오류가 발생합니다). `background: transparent`는 변경 없이 그대로 작동합니다. 레거시 DALL·E 2/3 코드에서 마이그레이션하는 경우: **`response_format`를 제거하십시오**(GPT Image 모델은 이를 400 `Unknown parameter: 'response_format'`로 거부하며, 출력은 항상 `b64_json`입니다).
  </Step>
</Steps>

## 오류 및 재시도

| 상태                                | 의미                                                                                         | 권장 조치                                                                                                                                                                                                                                                                                                                                         |
| --------------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `400`                             | 잘못된 매개변수(크기 제약 위반, 지원되지 않는 필드 등)                                                           | 크기 제약 조건에 따라 검증합니다. `response_format` / `input_fidelity`를 **전달하지 마십시오**. `background: transparent`를 `output_format: jpeg`과 함께 사용해도 400을 반환합니다(jpeg에는 알파 채널이 없음). 대신 `png` / `webp`을 사용합니다. `Unknown parameter: 'response_format'`인 경우 해당 매개변수만 제거하면 됩니다([FAQ](#faq) 참조). 편집 엔드포인트의 `invalid_image_file`은 일반적으로 MPO 휴대폰 사진입니다([FAQ](#faq) 참조). |
| `413`                             | 요청 본문이 너무 큼(여러 이미지 편집 또는 지나치게 큰 PNG. 약 80MB 이상의 요청 본문부터 관찰되었으며, 해당 크기의 모든 호출에서 발생하는 것은 아님) | 본문을 읽는 중 `message: openai_error, code: bad_response_status_code`이(가) 발생합니다. 제공업체 측 체인에서 발생하는 문제이며 게이트웨이는 재시도하지 않습니다. 참조 이미지를 각각 10MB 미만, 전체 50MB 미만으로 압축합니다(제공업체의 이미지당 제한은 50MB). 이렇게 하면 업로드 대기 시간도 수 분에서 수 초로 줄어듭니다.                                                                                                                         |
| `401`                             | 유효하지 않은 token                                                                              | Bearer Token을 확인합니다.                                                                                                                                                                                                                                                                                                                          |
| `400` + `safety_violations=[...]` | 콘텐츠 조정 차단(관찰된 상태는 403이 아니라 400임)                                                           | 일반적으로 이미지가 렌더링된 후에 발생하므로 동일한 prompt가 어떤 때는 통과하고 어떤 때는 실패합니다. `moderation: low`은 prompt 측 콘텐츠 조정에만 영향을 줍니다. 먼저 캐릭터의 의상을 명시적으로 추가한 다음, 한 번에 한 단어씩 변경합니다. [안전성 거부](/ko/api-capabilities/image-safety-troubleshooting)를 참조합니다.                                                                                                                    |
| `429`                             | 요청 제한 / 잔액 부족                                                                              | 지수 백오프를 사용합니다.                                                                                                                                                                                                                                                                                                                                |
| `5xx`                             | 게이트웨이 / 백엔드 오류                                                                             | 1\~2회 재시도합니다.                                                                                                                                                                                                                                                                                                                                 |
| 타임아웃                              | 긴 꼬리 지연                                                                                    | `quality`에 따라 클라이언트 타임아웃을 등급별로 설정합니다. `low` ≥ **120초** / `medium` ≥ **240초** / `high` ≥ **600초**(고해상도 + 2K/4K 실행은 3\~5분이 걸리며, 235초 이상에서 긴 꼬리 지연이 관찰됨)                                                                                                                                                                                         |

<Info>
  **클라이언트 권장 사항**:

  * `quality`에 따라 요청 타임아웃을 등급별로 설정합니다. `low` ≥ **120초** / `medium` ≥ **240초** / **`high` ≥ 600초**(안전망 — 3\~5분이 관찰되었으며, 약 120초/360초로 구성하면 많은 오탐 타임아웃이 발생함)
  * 먼저 **`quality=low`과 통합**한 다음, 실제 품질 요구 사항에 따라 `medium` / `high`로 높입니다.
  * 5xx 및 타임아웃에는 지수 백오프를 사용합니다(2회 재시도 권장).
  * 지원을 위해 `x-request-id` 헤더를 기록합니다.
</Info>

## FAQ

<AccordionGroup>
  <Accordion title="400 Unknown parameter: 'response_format' 오류를 어떻게 해결합니까?">
    **`response_format` 매개변수를 제거하십시오. 현재 가장 흔한 400 오류입니다.** `gpt-image-2` (전체 GPT Image 시리즈)는 **`response_format`를 허용하지 않습니다**. 출력 형식은 `b64_json`으로 고정되어 변경할 수 없습니다. 이를 전달하면 다음이 반환됩니다.

    ```json theme={null}
    {
      "error": {
        "message": "Unknown parameter: 'response_format'.",
        "type": "invalid_request_error",
        "param": "response_format",
        "code": "unknown_parameter"
      }
    }
    ```

    이 매개변수는 **DALL·E 2/3 시대의 레거시**(`url` / `b64_json`를 제공하던 시기)이며, 오래된 샘플 코드와 일부 서드파티 라이브러리에는 여전히 기본값으로 포함되어 있습니다. `gpt-image-2`로 마이그레이션할 때는 해당 필드를 삭제하고 `data[0].b64_json`를 직접 읽으십시오(원시 base64이며, 디코딩하여 이미지 파일을 가져옵니다). 이 오류는 입력 검증 단계에서 반환되며 **과금되지 않습니다**.

    워크플로에서 base64 대신 **이미지 URL**이 실제로 필요한 경우:

    * 공식 `gpt-image-2`에는 URL 출력이 없습니다. base64를 디코딩한 후 자체 오브젝트 스토리지에 업로드하십시오.
    * 또는 `response_format: "url"`를 지원하고 24시간 동안 유효한 CDN 링크를 반환하는 리버스 엔지니어링 [`gpt-image-2-all`](/ko/api-capabilities/gpt-image-2-all/overview)으로 전환하십시오.
  </Accordion>

  <Accordion title="b64_json에 data:image/png;base64, 접두사를 추가해야 합니까?">
    **예.** `gpt-image-2`은 `gpt-image-2-all`과 달리 **원시 base64 문자열**(접두사 없음)을 반환합니다. 클라이언트에서 사용하는 두 가지 패턴은 다음과 같습니다.

    * **파일 쓰기**: `base64.b64decode(b64_str)` → 디스크에 쓰기
    * **브라우저 렌더링**: `img.src = 'data:image/png;base64,' + b64_str` (수동으로 앞에 추가)

    코드가 1.5 시대의 “이미 접두사가 추가된” 동작을 가정하면 손상된 데이터 URL을 얻게 됩니다. 이를 명시적으로 처리하십시오.
  </Accordion>

  <Accordion title="input_fidelity를 전달하면 왜 400 오류가 반환됩니까?">
    `gpt-image-2`은 참조 이미지에 대한 고충실도 처리를 **강제**하며 더 이상 `input_fidelity`을 허용하지 않습니다. 1.5에서 마이그레이션할 때는 이 필드를 제거하기만 하면 되며, 대체 항목은 필요하지 않습니다.
  </Accordion>

  <Accordion title="투명한 배경이 필요하면 어떻게 합니까?">
    `background: "transparent"`를 전달하고 `output_format`을 `png` 또는 `webp`로 설정하면 됩니다. 반환되는 결과는 실제 알파 채널 이미지이므로 별도의 누끼 후처리가 필요하지 않습니다. 텍스트-이미지 생성과 이미지 편집 모두 이를 지원합니다.

    두 가지 제한 사항이 있습니다. `jpeg`에는 알파 채널이 없으며 투명도와 함께 사용할 수 없어 400 오류가 반환됩니다. 또한 편집 엔드포인트에서 투명도는 원본 윤곽선을 정밀하게 추적하는 작업이 아니라 **다시 그리는 작업**이므로 피사체의 세부 사항이 달라집니다. 픽셀 단위로 정확한 추출이 필요하면 `rembg` / `PIL` / `sharp`를 직접 실행하십시오.

    사람들이 자주 놓치는 세 번째 제한 사항은 다음과 같습니다. **prompt 또는 참조 이미지가 장면을 설명하면 모델은 해당 장면을 그립니다.** 매개변수로 이를 덮어쓸 수 없으며 `quality`을 높여도 도움이 되지 않습니다. 피사체만 설명하고 마지막에 `isolated subject on a transparent background, no scenery, no ground`을 추가하십시오.

    전체 세부 정보와 모델별 지원 여부는 [투명한 배경으로 이미지를 생성하려면 어떻게 해야 합니까?](/ko/faq/image-transparent-background)를 참조하십시오.
  </Accordion>

  <Accordion title="호출당 이미지는 몇 장입니까?">
    이미지 1장입니다(`n=1`). N장의 이미지가 필요하면 N개의 병렬 요청을 보내십시오. 각 요청은 독립적으로 token 과금됩니다.
  </Accordion>

  <Accordion title="2K/4K가 왜 이렇게 느립니까?">
    해상도와 품질이 높을수록 더 많은 출력 이미지 token이 필요하므로 자연스럽게 시간이 더 오래 걸립니다. 실제 고객 통합 환경에서 \*\*`quality=high` + 고해상도는 이미지당 약 235초(약 4분)\*\*가 걸리는 사례를 확인했으며, `3840×2160` + `high`의 롱테일 지연은 5분에 가까워질 수 있습니다. 권장 사항은 다음과 같습니다.

    * **먼저 `quality=low`으로 통합**하여 호출 체인을 검증한 후, 실제 품질 요구에 따라 상위 단계로 이동하십시오.
    * 품질별로 클라이언트 타임아웃을 설정하십시오: `low` ≥ **120초** / `medium` ≥ **240초** / **`high` ≥ 600초**(안전망)
    * UI에 “생성 중” 진행 상태를 표시하십시오.
    * 4K가 필요하지 않으면 1024×1024 / 1536×1024 1K 프리셋을 사용하십시오.
  </Accordion>

  <Accordion title="캐시된 입력 요금의 실제 혜택을 받을 수 있습니까?">
    **설정되어 있지만, 비용 예산에 캐시 할인을 반영하지는 마십시오.** 공식 캐시 입력 요율은 텍스트 \$1.25 / 이미지 \$2.00(1M token당)이며, APIYI 채널에는 캐싱이 설정되어 있습니다. 요청이 캐시에 적중하면 캐시 요율로 과금됩니다.

    한 가지 솔직한 제한 사항이 있습니다. 높은 동시 실행 수를 유지하기 위해 APIYI는 여러 upstream OpenAI 계정에 요청을 분산합니다(단일 OpenAI Tier-5 계정은 250 RPM만 허용). OpenAI의 prompt 캐시는 계정 간에 공유되지 않으므로, 동시 실행 수가 높을 때 동일한 접두사를 공유하는 요청이 같은 계정에 도달하지 않을 수 있습니다. **따라서 캐시에 적중하지 않을 수도 있습니다.**

    다행히 영향은 작습니다. 이미지 생성에서 지배적인 비용은 출력 이미지 token(\$30 / 1M)이며, 캐시 할인은 입력 측에만 적용되므로 이미지당 총 비용에는 거의 영향을 주지 않습니다. **전체 입력 요금**을 기준으로 예산을 책정하고, 캐시 적중은 추가 절감액으로 간주하십시오.
  </Accordion>

  <Accordion title="편집 요청이 텍스트-이미지 생성보다 비싼 이유는 무엇입니까?">
    `gpt-image-2`이 참조 이미지의 고충실도 처리를 자동으로 활성화하기 때문입니다. 참조 이미지 자체가 Vision 요금 규칙에 따라 많은 입력 token으로 변환됩니다. 편집 입력 token은 텍스트-이미지 생성보다 눈에 띄게 많으므로 이에 맞춰 예산을 책정하십시오.
  </Accordion>

  <Accordion title="크기와 참조 이미지가 같은데도 호출마다 비용이 다른 이유는 무엇입니까?">
    **근본 원인: `quality`이 `auto`로 설정되었거나 생략되었습니다.** “크기, 해상도, 참조 이미지가 동일한데도 가격이 오르내린다”고 보고한 고객이 있었습니다. 조사 결과 `size`과 `quality`가 모두 `auto`로 설정되어 있었습니다.

    **원인은 `quality: auto`입니다.** 자동 모드에서는 모델이 **요청을 해석하고 각 생성마다 다른 품질 티어를 즉석에서 선택합니다.** 티어가 달라지면 출력 이미지 token 수가 달라지고, 그에 따라 가격도 달라집니다. 아래는 \*\*입력이 동일한 실제 과금 기록 3건(각각 입력 token 1061개)\*\*이며 비용은 몇 배까지 차이 납니다.

    | 지연 시간 | 입력 token | 출력 token | 호출당 비용         |
    | ----- | -------- | -------- | -------------- |
    | 53초   | 1061     | 1286     | \$0.055082     |
    | 135초  | 1061     | **5146** | **\$0.194042** |
    | 68초   | 1061     | 1287     | \$0.055118     |

    두 번째 호출에서는 `auto`이 더 높은 품질 티어로 결정되어 출력 token이 5146개로 증가했고, 가격은 약 3.5배 상승했습니다.

    **해결 방법: `quality`을 `auto`로 두지 말고 `low` / `medium` / `high`를 명시적으로 전달하십시오.** 티어를 고정하면 동일한 입력에 대한 출력 token 수와 가격이 안정적이고 예측 가능해집니다. 위의 “품질 참조” 섹션을 참조하십시오.
  </Accordion>

  <Accordion title="편집 엔드포인트의 이미지 수와 크기 제한은 어떻게 됩니까?">
    `gpt-image-2` 이미지 편집 엔드포인트(`/v1/images/edits`)는 최대 **16장**의 참조 이미지를 지원합니다.

    * **multipart/form-data 파일 업로드**: 각 이미지는 **50MB 미만**이어야 하며, 형식은 `png` / `jpg` / `webp`입니다.
    * **base64 데이터 URL**: 필드 길이 제한은 약 **20MiB**입니다(스키마 `maxLength: 20971520` — 50MB multipart 제한과 동일하지 않은 문자열 필드 제한). 따라서 원본 이미지는 **15MB 이내**로 유지하십시오.
    * **마스크 파일**: 별도로 **4MB 미만의 PNG**로 제한됩니다.

    실용적인 조언: 여러 장의 대용량 이미지를 한 번에 한도까지 사용하지 마십시오. 지나치게 큰 요청 본문은 게이트웨이 / 타임아웃 계층에서 실패하는 경향이 있습니다. 각 이미지를 **1.5MB 이내**로 압축하는 것이 가장 안정적이며, 출력 품질은 입력 파일 크기와 관련이 없습니다.
  </Accordion>

  <Accordion title="편집 엔드포인트에서 400 'Invalid image file or mode for image 1'이 반환됩니다. 어떻게 해야 합니까?">
    이 오류(`code: invalid_image_file`)는 **N번째 참조 이미지가 표준 png / jpg / webp 파일이 아님**을 의미합니다(1부터 인덱싱되므로 해당 인덱스를 사용해 문제의 이미지를 찾으십시오).

    가장 흔한 원인은 휴대폰 카메라에서 생성되는 **MPO 형식**입니다. `.jpg` 파일은 Huawei Mate 시리즈 휴대폰에서 바로 가져온 경우 HDR 게인 맵 하위 프레임이 포함되어 있으며, 실제로는 다중 프레임 JPEG 컨테이너(MPO)입니다. 헤더는 동일한 `FFD8`이고, 확장자와 `file` 명령 모두 JPEG으로 표시하므로 육안으로 식별하기 어렵습니다. 2026년 7월 검증 결과 MPO 파일은 항상 거부되며, 동일한 이미지를 표준 JPEG/PNG로 다시 인코딩하면 **원본 해상도 그대로** 성공합니다(크기, `image[]` 필드명 또는 `quality`/`size` 매개변수와는 관련이 없습니다). 이 오류는 입력 검증 단계에서 반환되며 **과금되지 않습니다**.

    **해결 방법**: 업로드 전에 Pillow로 다시 인코딩하십시오(`Image.open(f).format`이 `"MPO"`을 반환하면 변환이 필요합니다).

    ```python theme={null}
    from PIL import Image
    im = Image.open("photo.jpg")
    im.load()                          # for MPO, keeps only the first frame
    im.convert("RGB").save("photo_fixed.jpg", quality=92)
    ```

    전체 세부 정보와 감지 방법은 [이미지 편집 API — 참조 이미지 형식 요구 사항 및 전처리](/ko/api-capabilities/gpt-image-2/image-edit#reference-image-format-requirements-and-preprocessing)를 참조하십시오.
  </Accordion>

  <Accordion title="마스크 파일은 어떻게 준비합니까?">
    * 원본과 **동일한 크기**, **PNG 형식**, **4MB 미만**
    * **알파 채널 필수**: 투명(alpha=0) = 인페인팅 영역, 불투명 = 보존
    * 첫 번째 이미지에만 적용됩니다.
    * 마스크는 “부드러운 가이드”이므로 모델이 마스크 영역 주변을 확장하거나 축소할 수 있습니다.
  </Accordion>

  <Accordion title="gpt-image-2와 gpt-image-2-all 중 무엇을 선택해야 합니까?">
    | 선택                                                    | 사용 시점                                                                                                                         |
    | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
    | **gpt-image-2.5-flare / sunburst / gpt-image-2** (공식) | 크기/품질을 정밀하게 제어해야 하거나, OpenAI 공식과 정확히 일치해야 하거나, 4K 출력이 필요하거나, 마스크 인페인팅이 필요한 경우. flare는 세 모델 중 가장 빠르고, sunburst는 가장 정밀한 편집기입니다. |
    | **gpt-image-2-all** (리버스)                             | 이미지당 \$0.03의 고정 요금, 30–60초 렌더링, 최소한의 매개변수, 강력한 일관성 / 중국어 텍스트가 필요한 경우                                                          |
  </Accordion>

  <Accordion title="공식 OpenAI SDK를 직접 사용할 수 있습니까?">
    예. 코드를 변경할 필요가 없습니다. `base_url`을 `https://api.apiyi.com/v1`로 지정하고 `api_key`을 APIYI token으로 설정하십시오.

    ```python theme={null}
    from openai import OpenAI
    client = OpenAI(api_key="sk-your-key", base_url="https://api.apiyi.com/v1")
    resp = client.images.generate(model="gpt-image-2.5-flare", prompt="...", size="2048x1152", quality="high")
    ```
  </Accordion>

  <Accordion title="진행 중인 생성을 취소할 수 있습니까?">
    **아니요.** `gpt-image-2`는 OpenAI의 공식 동기식 엔드포인트를 사용하므로 요청이 제출되면 “취소” 신호 없이 완료될 때까지 실행됩니다. 클라이언트 연결이 끊겨도 서버는 생성을 계속 완료하며 정상적으로 과금합니다. 클라이언트 측 타임아웃을 신중하게 구성하고, “연결 끊김 = 과금 없음”이라고 가정하지 마십시오.
  </Accordion>

  <Accordion title="요청 제한(RPM)이 있습니까?">
    기본값은 **100 RPM**(분당 100개 요청)입니다. 실제 사용 가능한 RPM은 **전체 플랫폼 동시 실행 수**에 따라 동적으로 조정됩니다. 더 많은 처리량이 필요하면 예상 QPS / RPM과 함께 문의해 주십시오. 추가 용량을 프로비저닝할 수 있습니다.
  </Accordion>

  <Accordion title="비동기 호출을 지원합니까?">
    **아니요.** `gpt-image-2`는 OpenAI 공식 API를 엄격하게 미러링하며 동기식만 지원합니다. 결과가 반환될 때까지 요청이 차단됩니다(`high` + 4K는 실제로 1\~2분). 비동기 큐 또는 콜백 메커니즘이 필요한 경우:

    * 비즈니스 계층에서 직접 작업 큐(Celery / BullMQ 등)로 래핑하십시오.
    * 또는 [`gpt-image-2-all`](/ko/api-capabilities/gpt-image-2-all/overview)을 사용하십시오. 30\~60초 안에 생성되며 프런트엔드에서 폴링하기 쉽습니다.
  </Accordion>

  <Accordion title="prompt 길이 제한이 있습니까? ChatGPT 웹 앱에는 왜 더 많은 내용을 붙여 넣을 수 있습니까?">
    예. **32,000자**이며, OpenAI Images API 제공업체의 제한입니다. token이 아니라 문자 수로 계산되며 APIYI의 공식 릴레이가 이를 더 엄격하게 제한하지는 않습니다. 웹 앱이 무제한처럼 보이는 이유는 채팅 모델이 붙여 넣은 내용을 읽은 다음 이미지 도구를 위한 자체적인 짧은 prompt를 작성하기 때문입니다. 따라서 이미지 모델은 해당 자료를 직접 확인하지 않습니다. 브랜드 가이드나 패키징 사양과 같은 긴 자료는 먼저 텍스트 모델을 사용해 1K\~3K자의 구조화된 prompt로 요약하고, [긴 Prompt](/ko/api-capabilities/image-long-prompt)를 참조하십시오.
  </Accordion>

  <Accordion title="명시적인 내용이 아닌 prompt에서 400 safety_violations=[sexual]이 반환됩니다. 이제 어떻게 해야 합니까?">
    이러한 차단의 대부분은 **이미지가 렌더링된 후** 발생합니다. 이미지가 생성된 다음 출력 측 분류기에 의해 거부되므로, 실패한 호출도 성공한 호출만큼 오래 걸리며 동일한 prompt가 때로는 통과하고 때로는 실패합니다. `moderation: low`는 prompt 측 검토만 완화할 뿐 이 문제에는 도움이 되지 않습니다. 가장 흔한 원인은 옷차림은 설명하지 않고 분위기로만 인물을 묘사하여 모델이 임의로 보완하다가 경계를 넘는 경우입니다. **먼저 명시적인 옷차림 문구 하나를 추가하고**(나머지는 모두 그대로 두십시오), 그 후에 한 번에 한 단어씩 제거해 보십시오. 전체 사례와 20회 호출 기록은 [안전성 거부](/ko/api-capabilities/image-safety-troubleshooting)를 참조하십시오.
  </Accordion>

  <Accordion title="실패한 생성도 과금됩니까?">
    **아니요.** OpenAI의 기본 콘텐츠 검토는 안전하지 않거나 잘못된 요청을 `400` 오류로 거부하며, **요금이 청구되지 않습니다**. 일반적인 응답은 다음과 같습니다.

    ```json theme={null}
    {
      "status_code": 400,
      "error": {
        "message": "Your request was rejected by the safety system. ...",
        "type": "shell_api_error",
        "code": "moderation_blocked"
      }
    }
    ```

    그 밖의 비용이 발생하지 않는 오류로는 `401`(유효하지 않은 token), `429`(요청 제한)이 있습니다. **token 과금은 요청이 실제로 모델 생성 단계에 도달한 후에만 시작됩니다(즉, `200` + `b64_json`을 수신한 경우).**
  </Accordion>
</AccordionGroup>
