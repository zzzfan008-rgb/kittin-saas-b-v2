# GPT-Image-2.5 / 2 画像生成/編集

> OpenAIのGPT-Image 2.5 / 2シリーズ向け公式リレーガイド：gpt-image-2.5-flare（速度優先）、gpt-image-2.5-sunburst（編集精度優先）、gpt-image-2。すべて同一価格・同一パラメータです。任意の2K/4K解像度のネイティブ対応、高忠実度参照画像の自動処理、テキストから画像への生成、参照編集、複数画像の融合、マスクによるインペインティングに対応しています。

<Info>
  すべての画像 API は **同期型** です — ポーリングするための task ID はなく、クライアントが切断されると、リクエストは課金されたまま結果は失われます。このモデルでは十分に長いタイムアウトを設定してください。[画像 API の基本とベストプラクティス](/ja/api-capabilities/image-api-best-practices)をご覧ください。
</Info>

## 概要

このページでは、APIYIの公式リレーを介したOpenAIの**GPT-Image 2.5 / 2シリーズ**について説明します。対象は、**`gpt-image-2.5-flare`**（速度重視）、**`gpt-image-2.5-sunburst`**（品質と編集精度重視）、および旧世代の\*\*`gpt-image-2`**です。2.5モデルは2026-09-08にリリースされ、gpt-image-2より高品質で、より精密な編集に対応し、2つの新しい**`quality`**ティア（`xhigh` / `max`）を備えています。価格とパラメータは**gpt-image-2と完全に同一\*\*です。シリーズ共通の特長は、**有効な任意の解像度（2K / 3840×2160 4Kを含む）**、**参照画像での自動高忠実度処理**、**token単位の課金**です。APIYIのゲートウェイはOpenAI Images APIと完全互換です。公式OpenAI SDKの`base_url`をここに指定するだけで、コード不要で直接接続できます。

<Note>
  **🎨 主な特長**: 有効な任意の解像度（最大3840×2160 4K）をネイティブサポート + 参照画像編集での自動高忠実度処理 + 中国語promptのネイティブサポート + 2.5で新たに追加された`xhigh` / `max`品質ティア。**正確なサイズや品質の制御が必要な本番シナリオ、OpenAI公式APIとの完全な一致が必要なケース、または4K出力が必要なケースに最適**です。デフォルトではテキストから画像への生成に`gpt-image-2.5-flare`、編集に`gpt-image-2.5-sunburst`を使用します。
</Note>

<Prompt description="コーディングエージェントに GPT-Image 2.5 / 2 シリーズのテキストから画像生成と画像編集を統合またはトラブルシューティングさせます。Codex、Claude Code、Cursor などのツールにコピーして貼り付けてください。" icon="bot" actions={["copy"]}>
  このプロジェクトで GPT-Image 2.5 シリーズのテキストから画像生成と画像編集を統合 / トラブルシューティングしてください。テキストから画像生成には `gpt-image-2.5-flare`、画像編集には `gpt-image-2.5-sunburst` を使用してください（いずれも `gpt-image-2` と価格およびパラメーターを共有します。モデル名は設定値にして、簡単に切り替えられるようにしてください）。

  コードに触れる前にドキュメントを読んでください。このページのプレーンテキスト版を取得するには、[https://docs.apiyi.com/en/api-capabilities/gpt-image-2/overview.md](https://docs.apiyi.com/en/api-capabilities/gpt-image-2/overview.md) をフェッチしてください。より詳細なパラメーターについては、同じ方法でテキストから画像生成と画像編集のページに `.md` を追加してください。

  要件：

  1. タイムアウト：クライアントのタイムアウトを360秒に延長してください。画像 API は同期処理で、タスク ID はありません。そのため、リクエストの処理中にクライアントが切断されると、リクエストは課金されたまま結果が失われます。早めにタイムアウトせず待機してください。リバースプロキシ、ゲートウェイ、サーバーレス実行の制限も同様に延長する必要があります。生成時間より短いレイヤーが1つでもあると、リクエストは途中で切断されます。

  2. レスポンスのレンダリング：`/v1/images/generations` は常に base64（`b64_json`、`data:` のプレフィックスなし）を返し、URL は返しません。フロントエンドでは、その base64 を画像としてレンダリングし、ディスクに保存する操作を提供してください。`response_format` は送信しないでください。400 が返されます。`input_fidelity` も送信しないでください。

  3. アップロード前に圧縮：`/v1/images/edits` を呼び出す前に（multipart、参照画像は最大16枚）、各参照画像を圧縮してください。1.5MBを超えるファイルのみ処理し、アスペクト比を維持したまま長辺を2048pxに縮小してください（小さい画像は決して拡大しないでください）。品質0.9で再エンコードし、元の形式を維持してください。複数画像のリクエストでは、合計サイズを6MB未満にしてください。いずれかの画像の圧縮に失敗した場合は、元の画像にフォールバックして処理を続行してください。圧縮の失敗だけを理由にリクエスト全体を中止してはいけません。

  4. 品質ティア：常に `quality` を送信し、デフォルトは `medium` にしてください。また、UI に品質ドロップダウンを追加してください（`low` / `medium` / `high` / `xhigh` / `max`。最後の2つは2.5モデルでのみ受け付けられ、料金も高くなります）。2.5ではティアが再調整されている点に注意してください。2.5 `high` は `gpt-image-2` `medium` としか等価ではないため、`gpt-image-2` から移行する際に `quality` をそのまま引き継がないでください。同じ予算にするには `max` を送信してください。`auto` は送信しないでください。これは動的な推論ティアであるため、コストとレイテンシーが変動します。

  5. 本番環境では、モデル名を日付付きスナップショット `gpt-image-2.5-flare-2026-09-08` / `gpt-image-2.5-sunburst-2026-09-08` に固定し、エイリアスの変更によって使用モデルが変わらないようにしてください。

  6. `APIYI_API_KEY` 環境変数からキーを読み取り、ベース URL には [https://api.apiyi.com/v1](https://api.apiyi.com/v1) を使用してください。ハードコードしたり、git にコミットしたりしてはいけません。

  7. 完了したら、実際にテキストから画像生成の呼び出しを1回、画像編集の呼び出しを1回実行し、結果とその2回の呼び出しにかかった料金を示してください。
</Prompt>

## モデル選択: flare / sunburst / gpt-image-2

2026-09-08以降、このドキュメントグループでは3つのOpenAI GPT-Image 2.5 / 2モデルを扱います。**3つとも価格、パラメータ、グループ、エンドポイントは同じ**で、切り替えは1フィールドの`model`変更だけです。

| 項目                        | `gpt-image-2.5-flare`                                              | `gpt-image-2.5-sunburst`               | `gpt-image-2`                      |
| ------------------------- | ------------------------------------------------------------------ | -------------------------------------- | ---------------------------------- |
| 位置づけ                      | 速度優先の小型モデル、OpenAIが推奨する日常用途のデフォルト                                   | 品質優先のベースモデル、現在OpenAIで最も高性能な生成 / 編集モデル  | 旧世代の単一フラッグシップ、引き続き利用可能             |
| 品質                        | gpt-image-2より高い                                                    | 3つの中で最高                                | ベースライン                             |
| レイテンシ（1024²、2026-09-09測定） | `low` 10秒 / `high` 21秒 / `max` 45秒。OpenAIによると、gpt-image-2より最大50%低い | `low` 14秒 / `high` 42秒 / `max` 142秒    | `low` 21秒 / `high` 224秒            |
| 編集とマルチターンの一貫性             | 改善                                                                 | さらに改善: 被写体の保持とマルチターンメモリが向上             | —                                  |
| `quality`ティア              | 6つ、`xhigh` / `max`を追加                                              | 6つ、`xhigh` / `max`を追加                  | `low` / `medium` / `high` / `auto` |
| 現在のスナップショット               | `gpt-image-2.5-flare-2026-09-08`                                   | `gpt-image-2.5-sunburst-2026-09-08`    | `gpt-image-2-2026-04-21`           |
| 最適な用途                     | バッチ生成、ソーシャルコンテンツ、商品画像、レイテンシが重視される処理                                | マルチターンのレタッチ、本番品質のキャンペーンクリエイティブ、複数画像の融合 | 変更したくない既存の統合                       |

<Tip>
  **選び方**: デフォルトのテキストから画像生成には`gpt-image-2.5-flare`を使用し、編集と複数画像の融合には`gpt-image-2.5-sunburst`を使用してください。本番環境では日付付きのスナップショットを固定し、エイリアスが変更されてもモデルが移行されないようにします。既存の`gpt-image-2`コードはモデル名を1か所変更するだけでアップグレードでき、その他すべてのパラメータ、価格、タイムアウトに関する知見をそのまま引き継げます。リリース記事: [GPT-image-2.5のリリース: Flareは高速、Sunburstは高精細](/en/news/gpt-image-2-5-launch)。
</Tip>

## 料金

APIYIの`gpt-image-2.5-flare` / `gpt-image-2.5-sunburst` / `gpt-image-2`（デフォルトグループ）は、**OpenAIの公式料金と完全に一致する1つの料金表を共有しています**。割引は代わりにチャージボーナスとして適用されます。**\$100をチャージすると10%のボーナスを獲得でき、最大20%です**。📖 [チャージキャンペーンについて](/ja/faq/recharge-promotions)。

### トークンレート（OpenAI の価格表と同じ）

トークン課金制 — 1 回のリクエスト = 入力テキスト + 入力画像 + 出力画像 token:

| 課金項目    | 価格（1M tokens あたり）       | 備考                                                     |
| ------- | ----------------------- | ------------------------------------------------------ |
| テキスト入力  | \$5.00                  | prompt のテキスト部分                                         |
| 画像入力    | \$8.00                  | 編集／融合リクエスト内の参照画像。Vision ルールに従って token 化されます            |
| 画像出力    | \$30.00                 | **最も大きいコスト** — token 数はサイズ × 品質で決まります                  |
| キャッシュ入力 | テキスト \$1.25 / 画像 \$2.00 | 設定はされていますが、同時実行数が高い場合はヒット率が限られます — [FAQ](#faq) をご覧ください |

**なぜ画像入力のほうが高いのですか？** 画像入力は \$8.00 / 1M tokens で、テキスト入力の \$5.00 / 1M の **1.6 倍** です（これは APIYI の上乗せではなく、OpenAI 自身の標準価格です）。そのため、編集 / 複数画像融合リクエストは、単純なテキストから画像への生成よりも入力側のコストがかなり高くなります。参照画像は Vision ルールによって大量の画像 token に token 化され、それぞれの token はすでにテキスト token より 60% 高く設定されています。

### 画像あたりの料金リファレンス（公式表、gpt-image-2）

1Kプリセットサイズにおける`gpt-image-2`の一般的な画像あたりの料金（2.5モデルでは同じティア名でも異なる token 数が使用されます。次のセクションを参照してください）：

| 品質 | 1024×1024 | 1024×1536 | 1536×1024 |
| -- | --------- | --------- | --------- |
| 低  | \$0.006   | \$0.005   | \$0.005   |
| 中  | \$0.053   | \$0.041   | \$0.041   |
| 高  | \$0.211   | \$0.165   | \$0.165   |

<Info>
  **料金に関する注意事項**:

  * 単価はOpenAIのリスト価格と同じです。[チャージボーナス](/ja/faq/recharge-promotions)（\$100で10%、最大20%）を加算すると、実質コストは直接利用するより低くなります
  * 2K / 4Kには画像あたりの固定料金はなく、実際の入力 + 出力 token 数に基づいて課金されます
  * 編集リクエストでは、高い忠実度が強制されるため、text-to-imageより入力 token 数が大幅に多くなります
  * ストリーミング（`stream: true` + `partial_images: N`）では、部分結果ごとに出力画像 token がさらに100加算されます
  * 同じサイズと品質の`gpt-image-1.5`と比較すると、`gpt-image-2`は約20～30%安価です
</Info>

### 2.5モデルの品質ティアと測定コスト（2026-09-09測定）

**同じティア名でも、2.5とgpt-image-2で同じtoken数を意味するわけではありません**：2.5では品質の段階が再調整されています。`low`は変更されず、2.5の`high`はgpt-image-2の`medium`に相当し、2.5の`max`はgpt-image-2の`high`に相当します。表は`usage.output_tokens`と、1024×1024のテキストから画像への変換における\$30 / 1Mでの出力コストを示しています。同じpromptを使用し、それぞれ1回ずつシリアル実行しています（flareとsunburstではティアごとのtoken数は同一で、異なるのはレイテンシのみです）。

| 品質       | gpt-image-2                  | gpt-image-2.5-flare         | gpt-image-2.5-sunburst       |
| -------- | ---------------------------- | --------------------------- | ---------------------------- |
| `low`    | 196 tokens ≈ \$0.006（21秒）    | 196 tokens ≈ \$0.006（10秒）   | 196 tokens ≈ \$0.006（14秒）    |
| `medium` | 1,756 tokens ≈ \$0.053（63秒）  | 439 tokens ≈ \$0.013（10秒）   | 439 tokens ≈ \$0.013（19秒）    |
| `high`   | 7,024 tokens ≈ \$0.211（224秒） | 1,756 tokens ≈ \$0.053（21秒） | 1,756 tokens ≈ \$0.053（42秒）  |
| `xhigh`  | ❌ 400                        | 3,122 tokens ≈ \$0.094（31秒） | 3,122 tokens ≈ \$0.094（60秒）  |
| `max`    | ❌ 400                        | 7,024 tokens ≈ \$0.211（45秒） | 7,024 tokens ≈ \$0.211（142秒） |

<Warning>
  **gpt-image-2から移行する際に`quality`をそのまま引き継がないでください**：同じ`high`でも、2.5では出力tokensが4分の1になり、品質段階の下位にマッピングされます。gpt-image-2の`high`と同じtoken予算に合わせるには、2.5で`max`を送信してください。逆に、2.5の`high` / `xhigh`を使用すると、同じ予算でより安価な中間ステップを2つ利用できます。本番環境に移行する前に、自分のpromptを一度実行して`usage.output_tokens`を確認してください。2K / 4Kについてはピクセル比で外挿してください。
</Warning>

### 複数の入力画像が価格に与える影響（2026年7月検証済み）

よくあるお客様の質問: 「参照画像ごとに一律料金なのか、それとも大きい画像ほど消費する token が増えるのか？」答えは、**どちらも影響し、画像枚数は厳密に線形で加算されます**。`gpt-image-2` はすべての入力画像を強制的な高忠実度（`input_fidelity` は調整できません。渡すと 400 が返ります）で処理し、各参照画像はその寸法とアスペクト比に基づいて画像 token に変換されます。実測値（edits エンドポイント、2026-07-15）:

| 参照画像の入力             | `image_tokens`        | 入力コスト (\$8/M) |
| ------------------- | --------------------- | ------------- |
| 1 × 512×512         | 1024                  | ≈\$0.0082     |
| 1 × 1024×1024       | 1024                  | ≈\$0.0082     |
| 1 × 2048×2048       | 1521                  | ≈\$0.0122     |
| 1 × 4096×4096       | 1521                  | ≈\$0.0122     |
| 1 × 1024×1536 (縦向き) | 1536                  | ≈\$0.0123     |
| **4 × 1024×1024**   | **4096 (= 4 × 1024)** | ≈\$0.0328     |

3つの目安:

1. **個数は厳密に線形です**: N 枚の参照画像 ≈ N × 1枚分の token。1024² の参照画像 16 枚 ≈ 16384 tokens ≈ \$0.13 — これは `high` の出力 1 回分（\$0.211）と同じ桁なので、複数画像の融合ではもはや無視できません。
2. **サイズには下限と上限の両方があります**: 1024² 以下の正方形画像はすべて 1024 tokens として課金されます（512 に縮小しても **何も節約できません**）。2048² と 4096² はどちらも 1521 tokens です（大きすぎる画像は変換前に縮小されるため、**上限がかかります**）。参照画像 1 枚あたりは、アスペクト比込みでおおむね 800〜1600 token の範囲に収まります。
3. **token 数はファイルサイズではなくピクセル寸法で決まります**: 1.5MB まで圧縮するとアップロードの安定性と速度は向上しますが、**画像 token は減りません**。逆に、50MB のオリジナルをアップロードしても請求額が跳ね上がることはありません（上限が適用されます）。

<Tip>
  コスト感覚: `low` の出力（196 tokens ≈ \$0.006）では、参照画像 1 枚の入力コスト（≈\$0.008）のほうが実際には出力より高くなります。`high` の出力（≈\$0.211）では、参照画像 1 枚は約 4% にすぎません。**出力サイズと品質は、常に価格を左右する最大の要因です** — 参照画像の枚数はその次です。
</Tip>

### 2K/4K のコスト見積もり（ピクセル比による外挿、⚠️ 公式の固定価格ではありません）

OpenAI は 1K サイズについてのみ、画像ごとの固定価格表を公開しています — **2K/4K のサイズ別価格については公式のものがありません**。以下の表は、予算見積もり目的のみで、上の 1K の公式レートを基準にピクセル数でスケーリングした、APIYI 独自の外挿です。

| 品質 | 2048×2048（2K 正方形） | 2048×1152（2K 横長） | 3840×2160 / 2160×3840（4K） |
| -- | ----------------- | ---------------- | ------------------------- |
| 低  | ≈\$0.024          | ≈\$0.008         | ≈\$0.026                  |
| 中  | ≈\$0.212          | ≈\$0.062         | ≈\$0.216                  |
| 高  | ≈\$0.844          | ≈\$0.248         | ≈\$0.870                  |

<Warning>
  **これは見積もりであり、公式の価格表ではありません。** 方法: 同じアスペクト比の 1K の公式行を基準値として取り、その後、対象サイズのピクセル数をその基準値に対して線形にスケーリングします（たとえば、2048×2048 は 1024×1024 の 4 倍のピクセル数なので、見積もりコストも 4 倍になります）。実際の出力画像 token 数は、コンテンツの複雑さに基づいてモデルが動的に決定するため、厳密には線形ではありません。そのため、**実際のレスポンスにある `usage.output_tokens` を唯一の基準として扱ってください**（下の「各呼び出しの実際の token 数を確認する方法」を参照してください）。`high` 品質で 2560×1440 を超えるサイズは、引き続き公式の実験的な階層であるため、そこでは見積もりの精度がやや低くなる場合があります。
</Warning>

### SaaS サブスクリプション / クレジットベース課金との違い

画像生成ツールのベンダーは、通常 2 つの方式のどちらかで課金します。

* **月額サブスクリプションプラン**: 「月間 N 枚」のクォータに対して定額の月額料金を支払う方式です。このクォータは **過剰販売前提** を織り込んだ価格設定になっており、ベンダーは大半のユーザーが付与上限を使い切らないことを前提にしています。そのため、広告される「1 枚あたりのコスト」は、単にプラン料金をクォータ上限で割ったものにすぎず、実際に各画像を生成するのにあなたにとって本当にいくらかかるかを示すものではありません。
* **クレジット / ポイントベースの計測**: 品質やサイズの異なるジョブを、正体の分かりにくい「クレジット」に変換します。これは実態としては従量課金であり、実際の token 消費を隠すクレジット単位の背後に再パッケージされているだけです。

APIYI は **公式リレー + 実際の token 従量課金** モデルで動作します。プランのクォータもクレジットの抽象化レイヤーもありません。各呼び出しのコストは、単純にその実際の入力 / 出力 token 数 × 公式レートです。サブスクリプションにありがちな過剰販売や、上限超過時にスロットリングされるような動きは一切なく、呼び出しごとに正確に算出できます。

<Tip>
  従量課金のトレードオフは、サブスクリプションのような毎月固定額の確実性ではなく、自分で使用量を見積もり / 監視する必要があることです。その代わり、使った分だけ支払えばよく、遊休分の無駄はありません。以下では、各呼び出しの実際の token 数をレスポンスから直接取り出し、その計算を自分で行う方法を説明します。
</Tip>

### 各呼び出しの実際の token 数を確認する方法

`/v1/images/generations`と`/v1/images/edits`はいずれも`usage`フィールドを返し、**画像入力 token とテキスト入力 token は別々のフィールドとして返されます**。推定は不要で、各呼び出しの正確なコストを確認するには、それらを読み取るだけです。以下は、1枚の参照画像を使用した実際の編集リクエストから取得した完全な`usage`オブジェクトです（実行時に取得）：

```json theme={null}
{
    "data": [ { "b64_json": "..." } ],
    "usage": {
        "input_tokens": 848,
        "input_tokens_details": {
            "image_tokens": 832,
            "text_tokens": 16
        },
        "output_tokens": 196,
        "output_tokens_details": {
            "image_tokens": 196,
            "text_tokens": 0
        },
        "total_tokens": 1044
    }
}
```

| フィールド                                     | 意味                                                                                                                                                                           |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `usage.input_tokens_details.text_tokens`  | プロンプトテキストで消費された token。100万 token あたり \$5.00 で課金                                                                                                                              |
| `usage.input_tokens_details.image_tokens` | Vision ルールに基づいて参照画像から変換された token。100万 token あたり \$8.00 で課金。参照画像を使用しない通常のテキストから画像への生成では常に 0                                                                                   |
| `usage.input_tokens`                      | 上記2フィールドの合計                                                                                                                                                                  |
| `usage.output_tokens`                     | 生成画像の token。`quality × size`によって決まり、**コストの大部分を占めます**。100万 token あたり \$30.00 で課金され、2K/4Kリクエストでは特に注意すべき数値です（`output_tokens_details.image_tokens`もこの値を反映します。`text_tokens`は常に 0） |
| `usage.total_tokens`                      | 入力 + 出力の合計                                                                                                                                                                   |

自分で確認できる正確なコスト計算式：

```
cost ≈ input_tokens_details.text_tokens × \$5.00 / 1,000,000
     + input_tokens_details.image_tokens × \$8.00 / 1,000,000
     + output_tokens × \$30.00 / 1,000,000
```

<Tip>
  過去の呼び出しの実際の token 使用量と課金の詳細を確認するには、コンソールの「ログ」ページを開いてください：📖 [呼び出しログの表示方法](/ja/faq/call-logs) — ログの詳細画面には、token 数とともにテキスト入力・画像入力・出力の価格が表示され、API の`usage.input_tokens_details` / `usage.output_tokens_details`と一致します。
</Tip>

### カスタムサイズの制約

`gpt-image-2` は、以下をすべて満たす **任意の有効なサイズ** を受け付けます:

1. **最大辺 ≤ 3840px**
2. **両方の辺が 16 の倍数**
3. **アスペクト比 ≤ 3:1**
4. **総ピクセル数 ∈ \[655,360, 8,294,400]**（約0.65MP～約8.3MP）

**有効な例**: `1600x1200`, `1792x1024`, `2048x1536`, `3200x1800`
**無効な例**: `1000x1000`（16 の倍数ではない）, `4000x4000`（最大値を超過）, `3840x1000`（比率 > 3:1）

<Warning>
  `2560×1440` を超える出力（約3.69MP）は公式に **実験的** とされ、品質が変動する場合があります。本番環境では、`2048x1152` / `2048x2048` / `3840x2160` のようなプリセットを推奨します。
</Warning>

## 品質リファレンス

### 利用可能なティア

| 品質       | 意味                 | 備考                                                                      |
| -------- | ------------------ | ----------------------------------------------------------------------- |
| `auto`   | 自動（**デフォルト**）      | `quality` を省略した場合に使用される値です — モデルがティアを自動選択します                            |
| `low`    | 低品質                | 最も高速かつ低コストです — 下書き／バッチ処理に適しています                                         |
| `medium` | 中品質                | 日常利用／最終出力向けのバランスの取れた選択肢です                                               |
| `high`   | 高品質                | テキスト、細かなテクスチャ、印刷向けです。`gpt-image-2` における最上位ティアです                         |
| `xhigh`  | 超高品質（**2.5 で新登場**） | `gpt-image-2.5-flare`／`sunburst` のみで受け付けられます。`high` より出力 token 数が多くなります |
| `max`    | 最高品質（**2.5 で新登場**） | 2.5 の 2 つのモデルのみで受け付けられます。コストとレイテンシーが最も高く、本番品質の最終出力向けです                  |

<Warning>
  **デフォルトは `auto` であり、`medium` ではありません。** `quality` を省略することは `"quality": "auto"` を渡すことと同じです — モデルが品質ティアを自動選択しますが、**OpenAI はそれが `medium` に対応することを保証していません。** `auto` が解決するティアは予測できず、コスト、レイテンシー、課金の安定性に直接影響します。**コスト管理と予測可能性が必要な場合は、`auto` に頼るのではなく、`low`／`medium`／`high`／`xhigh`／`max` のいずれかを明示的に渡してください。**
</Warning>

<Warning>
  **従来の DALL·E の値 `standard`／`hd` は渡さないでください。** `quality` は 6 つの公式 enum 値 `low`／`medium`／`high`／`xhigh`／`max`／`auto` のみを受け付け、`xhigh`／`max` は 2.5 の 2 つのモデルでのみ受け付けられます。従来の DALL·E 3 の値 `standard`／`hd` はバックエンドチャネルによって動作が一貫しません。400（`invalid_value`）で即座に失敗する場合もあれば、無視されたままリクエストが `auto` で実行される場合もあります（コストは予測不能です）。必ず公式値のいずれか 1 つを明示的に渡してください。
</Warning>

<Info>
  **価格への影響が最も大きいのは `quality` であり、`size` よりも大きな影響があります。** 出力画像の token 数は `quality × size` によって決まりますが、`quality` の影響ははるかに大きくなります。同じサイズの場合、`low` から `high` に変更すると、画像 1 枚あたりのコストが **30 倍以上** 変わる可能性があります（上記の「画像 1 枚あたりのコスト」表を参照してください。1024×1024 の gpt-image-2 は `low` \$0.006 から `high` \$0.211 の範囲で、2.5 のモデルは `low` \$0.006 から `max` \$0.211 の範囲です）。まず `quality` に基づいてコストを見積もり、その後 `size` の影響を加味してください。
</Info>

## ベストプラクティス

<Warning>
  **オンボーディングのヒント：まず `low` で API を動作させてからスケールアップ**

  新規統合者がいきなり `quality=high` + 高解像度に進み、\*\*画像 1 枚あたり約 235 秒（約 4 分）\*\*待つことになり、API が停止したのではないかと疑うケースを見てきました。`high` モードは推論の複雑さが最も高く、4K では 5 分近くかかる場合があります。**本番運用に移行する前に、まず `quality=low` でエンドツーエンドの統合を行ってください**（認証、SDK、パラメータ、タイムアウト、エラーハンドリング）。その後、実際に必要な品質に応じてのみ `medium` / `high` へ移行してください。
</Warning>

<Steps>
  <Step title="まず低品質で統合する">
    新しい統合では、まず **`quality=low` + プリセットサイズ**から開始し、呼び出しチェーン全体（認証、パラメータ、タイムアウト、エラーハンドリング）を検証してください。`low` は `high` より数倍高速なため、長いレイテンシによって隠されることなく、機能上の問題を迅速に特定できます。
  </Step>

  <Step title="プリセットサイズを優先する">
    8 つの公式プリセットは、安定した速度と品質に調整されています。カスタムサイズは、本当に特殊なアスペクト比が必要な場合に限定してください。
  </Step>

  <Step title="用途に品質を合わせる">
    下書き / バッチ → `low`、日常利用 / 最終版 → `medium`、テキスト・細かなテクスチャ・印刷 → `high`。**`low` ↔ `high` は見た目の忠実度だけの違いではなく、推論の複雑さも段階的に変化します**。そのため、レイテンシもそれに応じて増加します。
  </Step>

  <Step title="JPEG 出力を選択する">
    最終表示用途では、`output_format=jpeg` + `output_compression=85` は PNG より高速で、サイズはおよそ半分です。
  </Step>

  <Step title="テキスト用途では high に固定する">
    テキストレンダリングは主要な強みですが、低いティアではぼやける場合があります。看板やポスターの用途では `quality=high` に固定してください。
  </Step>

  <Step title="参照画像を準備する">
    各画像は最大 50MB（実運用では 1.5MB 以内に圧縮）。PNG/JPEG/WebP をサポートし、最大 16 枚まで使用できます。prompt 内では「画像 1 / 画像 2」のように参照順を指定してください。
  </Step>

  <Step title="透明背景：パラメータを渡し、prompt からシーンを除外する">
    `background: "transparent"` と `png` / `webp` を指定しても、保証されるのはアルファチャンネルのみです。**prompt または参照画像に完全なシーン（森、部屋、通り）が記述されている場合、モデルはそのシーンを描画します**。パラメータによって阻止されることはありません。これが透明化が「時々うまくいく」主な理由であり、`quality` とは無関係です（2026-09-11 測定：被写体のみの prompt は 16/16 で透明、シーンありの prompt は 0/3。medium と high は同様）。prompt の末尾に `isolated subject on a transparent background, no scenery, no ground` を追加してください。参照画像に背景がある場合は、編集 prompt で `remove the background entirely, keep only the subject` と指定してください。[透明背景 FAQ](/ja/faq/image-transparent-background)を参照してください。
  </Step>

  <Step title="クライアントのタイムアウトをティアごとに設定する（high → 600 秒の安全域）">
    レイテンシを支配する 2 つのパラメータは **`quality`** と **`size`** であり、特に `quality` が重要です。ティアごとにクライアントのタイムアウトを設定してください。

    | 品質              | 推奨クライアントタイムアウト   | 観測レイテンシ                                                                                       |
    | --------------- | ---------------- | --------------------------------------------------------------------------------------------- |
    | `low`           | ≥ **120 秒**      | 通常 10～40 秒                                                                                    |
    | `medium`        | ≥ **240 秒**      | 通常 30～90 秒                                                                                    |
    | `high`          | ≥ **600 秒**（安全域） | gpt-image-2 の 2K/4K は 3～5 分、長いテールでは 235 秒超を観測。2.5 モデルは 1024² で 21～42 秒を測定                     |
    | `xhigh`（2.5 のみ） | ≥ **300 秒**      | 1024² で 31～60 秒を測定（2026-09-09）。2K/4K ではより長くなります                                               |
    | `max`（2.5 のみ）   | ≥ **600 秒**（安全域） | 1024² で 45～142 秒を測定。gpt-image-2 `high` と同じ token数のため、2K/4K は gpt-image-2 `high` と同様に見積もってください |

    **`high` モードでは、安全域となるタイムアウトを 600 秒に設定してください**。これにより、キューイング、長いテールの変動、上流のジッターを吸収できます。UI で進捗を表示し、サーバー側のタスクキューも検討してください。
  </Step>

  <Step title="移行に関する注意事項">
    `gpt-image-1.5` から移行する場合：`input_fidelity` を削除してください（高忠実度が強制され、渡すとエラーになります）。`background: transparent` はそのまま動作するため、変更は不要です。旧来の DALL·E 2/3 コードから移行する場合：**`response_format` を削除してください**（GPT Image モデルはこれを 400 `Unknown parameter: 'response_format'` で拒否します。出力は常に `b64_json` です）。
  </Step>
</Steps>

## エラーとリトライ

| ステータス                             | 意味                                                                                                | 推奨アクション                                                                                                                                                                                                                                                                                                                                                          |
| --------------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `400`                             | パラメータが無効です（サイズ制約違反、サポートされていないフィールドなど）                                                             | サイズ制約に対して検証します。`response_format` / `input_fidelity` は**渡さないでください**。`background: transparent` と `output_format: jpeg` を組み合わせても 400 が返ります（jpeg にはアルファチャンネルがありません）。代わりに `png` / `webp` を使用します。`Unknown parameter: 'response_format'` の場合は、そのパラメータを削除するだけです。[よくある質問](#faq) を参照してください。編集エンドポイントの `invalid_image_file` は通常、MPO 形式のスマートフォン写真です。[よくある質問](#faq) を参照してください |
| `413`                             | リクエストボディが大きすぎます（複数画像の編集 / サイズ超過の PNG。およそ 80MB 以上のリクエストボディで確認されていますが、そのサイズのすべての呼び出しで発生するわけではありません） | ボディの内容は `message: openai_error, code: bad_response_status_code` です。これはプロバイダー側の処理チェーンに起因するもので、ゲートウェイはリトライしません。参照画像を 1 枚あたり 10MB 未満、合計 50MB 未満に圧縮してください（プロバイダーの画像 1 枚あたりの上限は 50MB です）。これにより、アップロードの待ち時間も数分から数秒に短縮できます                                                                                                                                              |
| `401`                             | token が無効です                                                                                       | Bearer トークンを確認してください                                                                                                                                                                                                                                                                                                                                             |
| `400` + `safety_violations=[...]` | コンテンツモデレーションによるブロック（確認されたステータスは 403 ではなく 400 です）                                                  | 通常、画像のレンダリング後に発生するため、同じ prompt でも通過する場合と失敗する場合があります。`moderation: low` は prompt 側のモデレーションにのみ影響します。まずキャラクターの服装を明示し、その後は一度に 1 語ずつ変更してください。[安全性による拒否](/ja/api-capabilities/image-safety-troubleshooting) を参照してください                                                                                                                                                   |
| `429`                             | レート制限 / 残高不足                                                                                      | 指数バックオフ                                                                                                                                                                                                                                                                                                                                                          |
| `5xx`                             | ゲートウェイ / バックエンドエラー                                                                                | 1～2 回リトライします                                                                                                                                                                                                                                                                                                                                                     |
| タイムアウト                            | ロングテール                                                                                            | `quality` に基づいてクライアントのタイムアウトをプラン別に設定します。`low` ≥ **120 秒** / `medium` ≥ **240 秒** / `high` ≥ **600 秒**（高品質 + 2K/4K の実行は 3～5 分かかり、235 秒超のロングテールが確認されています）                                                                                                                                                                                                          |

<Info>
  **クライアントに関する推奨事項**:

  * `quality` に基づいてリクエストのタイムアウトをプラン別に設定します。`low` ≥ **120 秒** / `medium` ≥ **240 秒** / **`high` ≥ 600 秒**（安全策です。3～5 分が確認されており、120 秒 / 360 秒前後に設定すると誤ったタイムアウトが多数発生します）
  * **まず `quality=low` と統合し**、実際に必要な品質に応じて `medium` / `high` に移行します
  * 5xx とタイムアウトには指数バックオフを使用します（2 回のリトライを推奨します）
  * サポートに問い合わせる際は `x-request-id` ヘッダーを記録します
</Info>

## よくある質問

<AccordionGroup>
  <Accordion title="400 Unknown parameter: 'response_format' を修正するにはどうすればよいですか？">
    **`response_format` パラメータを削除してください。現在、最も一般的な400エラーです。** `gpt-image-2`（および GPT Image シリーズ全体）は `response_format` **を受け付けません**。出力形式は `b64_json` に固定されており、変更できません。これを渡すと、次のエラーが返されます。

    ```json theme={null}
    {
      "error": {
        "message": "Unknown parameter: 'response_format'.",
        "type": "invalid_request_error",
        "param": "response_format",
        "code": "unknown_parameter"
      }
    }
    ```

    このパラメータは、**DALL·E 2/3時代の名残**（`url` / `b64_json` を提供していた時代）であり、多くの古いサンプルコードや一部のサードパーティーライブラリには、今でもデフォルトで含まれています。`gpt-image-2` に移行する場合は、フィールドを削除し、`data[0].b64_json` を直接読み取ってください（raw base64 です。画像ファイルを取得するにはデコードします）。このエラーは入力検証段階で返されるため、**課金されません**。

    base64ではなく、実際に**画像URL**が必要なワークフローの場合：

    * 公式 `gpt-image-2` にはURL出力がないため、base64をデコードして、自分のオブジェクトストレージにアップロードします
    * または、リバースエンジニアリング版の[`gpt-image-2-all`](/ja/api-capabilities/gpt-image-2-all/overview)に切り替えます。`response_format: "url"` をサポートしており、24時間有効なCDNリンクを返します
  </Accordion>

  <Accordion title="b64_json に data:image/png;base64, プレフィックスを追加する必要はありますか？">
    **はい**。`gpt-image-2` は **raw base64文字列**（プレフィックスなし）を返します。これは `gpt-image-2-all` とは異なります。クライアント側では次の2つのパターンがあります。

    * **ファイルに書き込む**：`base64.b64decode(b64_str)` → ディスクに書き込みます
    * **ブラウザーで表示する**：`img.src = 'data:image/png;base64,' + b64_str`（手動で先頭に追加します）

    コードが1.5時代の「すでにプレフィックスが付いている」動作を前提としている場合、壊れたデータURLになります。この点を明示的に処理してください。
  </Accordion>

  <Accordion title="input_fidelity を渡すと400になるのはなぜですか？">
    `gpt-image-2` は参照画像の高忠実度処理を **強制**するため、`input_fidelity` を受け付けなくなりました。1.5から移行する場合は、このフィールドを削除するだけでよく、代替は必要ありません。
  </Accordion>

  <Accordion title="透明な背景が必要な場合はどうすればよいですか？">
    `background: "transparent"` を渡し、`output_format` を `png` または `webp` に設定してください。返されるのは実際のアルファチャンネル画像であり、切り抜きの後処理は必要ありません。テキストからの画像生成と画像編集の両方でサポートされています。

    注意点は2つあります。`jpeg` にはアルファチャンネルがなく、透明化とは併用できません（400を返します）。また、編集エンドポイントでの透明化は**元の輪郭を正確にトレースする処理ではなく再描画**であるため、被写体の細部が変化します。ピクセル単位で正確に抽出するには、`rembg` / `PIL` / `sharp` を自分で実行してください。

    もう1つ、見落とされがちな注意点があります。**prompt または参照画像がシーンを表している場合、モデルはそのシーンを描画します**。パラメータでこれを上書きすることはできず、`quality` を大きくしても解決しません。被写体だけを説明し、最後に `isolated subject on a transparent background, no scenery, no ground` を付けてください。

    詳細およびモデルごとのサポート状況については、[透明な背景で画像を生成するにはどうすればよいですか](/ja/faq/image-transparent-background)を参照してください。
  </Accordion>

  <Accordion title="1回の呼び出しで何枚の画像を生成できますか？">
    1枚です（`n=1`）。N枚必要な場合は、N個の並列リクエストを発行してください。それぞれ個別にtoken課金されます。
  </Accordion>

  <Accordion title="2K/4Kが非常に遅いのはなぜですか？">
    高解像度および高品質では、より多くの出力画像tokenが必要になるため、当然ながら時間がかかります。実際の顧客統合環境では、\*\*`quality=high` + 高解像度で、画像1枚あたり約235秒（約4分）\*\*かかるケースを確認しています。また、`3840×2160` + `high` のロングテールでは、5分近くまで延びることがあります。推奨事項：

    * **まず `quality=low` と統合して**呼び出しチェーンを検証し、実際に品質が必要になった段階で上位へ移行する
    * 品質ごとにクライアントのタイムアウトを分ける：`low` ≥ **120秒** / `medium` ≥ **240秒** / **`high` ≥ 600秒**（安全策）
    * UIに「生成中」の進捗を表示する
    * 4Kが不要な場合は、1024×1024 / 1536×1024の1Kプリセットを使用する
  </Accordion>

  <Accordion title="キャッシュされた入力の料金によるメリットは実際に得られますか？">
    **設定はされていますが、コスト予算にキャッシュ割引を組み込まないでください。** 公式のキャッシュ済み入力料金は、テキストが100万tokenあたり \$1.25、画像が100万tokenあたり \$2.00です。APIYIチャネルではキャッシュが設定されており、リクエストがキャッシュにヒットした場合は、キャッシュ済み料金で課金されます。

    正直な注意点が1つあります。高い同時実行数を維持するため、APIYIは複数の上流OpenAIアカウントにリクエストを分散しています（単一のOpenAI Tier-5アカウントでは250 RPMしか許可されません）。OpenAIのprompt cacheはアカウント間で共有されないため、高い同時実行数では、同じプレフィックスを共有するリクエストが同じアカウントに到達するとは限らず、**キャッシュにヒットしない可能性があります**。

    良い点として、影響は小さいです。画像生成の支配的なコストは出力画像token（100万tokenあたり \$30）であり、キャッシュ割引は入力側にのみ適用されるため、画像1枚あたりの合計額はほとんど変わりません。**入力料金を全額で**予算化し、キャッシュヒットは追加の節約分として扱ってください。
  </Accordion>

  <Accordion title="編集リクエストがテキストからの画像生成より高額なのはなぜですか？">
    `gpt-image-2` は参照画像の高忠実度処理を自動的に有効にするため、Visionの料金ルールにより、参照画像自体が大量の入力token数に変換されます。編集の入力tokenはテキストからの画像生成より明らかに多いため、それを考慮して予算を組んでください。
  </Accordion>

  <Accordion title="サイズと参照画像が同じなのに、呼び出しごとの料金が異なるのはなぜですか？">
    **根本原因は、`quality` が `auto` に設定されていた（または省略されていた）ことです。**「サイズ、解像度、参照画像が同一なのに、料金が上下する」という報告が顧客から寄せられています。調査したところ、`size` と `quality` の両方が `auto` に設定されていました。

    **原因は `quality: auto` です**。自動モードでは、モデルが**リクエストを解釈し、生成ごとに異なる品質ティアをその場で選択します**。ティアが異なれば出力画像token数も異なり、料金も異なります。以下は、\*\*入力が同一（各1061入力token）\*\*でありながら、コストが数倍異なる実際の課金記録3件です。

    | レイテンシ | 入力token | 出力token  | 1回あたりのコスト      |
    | ----- | ------- | -------- | -------------- |
    | 53秒   | 1061    | 1286     | \$0.055082     |
    | 135秒  | 1061    | **5146** | **\$0.194042** |
    | 68秒   | 1061    | 1287     | \$0.055118     |

    2回目の呼び出しでは、`auto` がより高い品質ティアに解決され、出力tokenが5146まで増加し、料金が約3.5倍になりました。

    **修正方法：`quality` を `auto` のままにせず、`low` / `medium` / `high` を明示的に渡してください。** ティアを固定すれば、同一入力に対する出力token数と料金が安定し、予測可能になります。上記の「品質リファレンス」セクションを参照してください。
  </Accordion>

  <Accordion title="編集エンドポイントの画像枚数とサイズの制限はどうなっていますか？">
    `gpt-image-2`画像編集エンドポイント（`/v1/images/edits`）は、最大 **16枚**の参照画像をサポートします。

    * **multipart/form-dataファイルアップロード**：各画像は**50MB未満**で、形式は `png` / `jpg` / `webp`
    * **base64データURL**：フィールド長の上限は約 **20MiB**（スキーマ `maxLength: 20971520`。文字列フィールドの上限であり、50MBのmultipart上限とは異なります）なので、元画像は**15MB以内**にしてください
    * **マスクファイル**：個別に**4MB未満のPNG**に制限されます

    実用上のアドバイスとして、複数の大きな画像を一度に上限まで設定しないでください。大きすぎるリクエストボディは、ゲートウェイ / タイムアウト層で失敗しやすくなります。各画像を**1.5MB以内**に圧縮するのが最も確実であり、出力品質は入力ファイルサイズとは関係ありません。
  </Accordion>

  <Accordion title="編集エンドポイントが400「Invalid image file or mode for image 1」を返します。どうすればよいですか？">
    このエラー（`code: invalid_image_file`）は、**N番目の参照画像が標準的なpng / jpg / webpファイルではない**ことを意味します（インデックスは1始まりです。番号を使って問題の画像を特定してください）。

    最も一般的な根本原因は、スマートフォンのカメラが生成する **MPO形式**です。Huawei Mateシリーズのスマートフォンから直接取得した `.jpg` ファイルにはHDRゲインマップのサブフレームが埋め込まれており、実際にはマルチフレームJPEGコンテナ（MPO）です。ヘッダーは `FFD8` と同じで、拡張子と `file` コマンドの両方がJPEGと報告するため、目視では判別できません。2026年7月に検証した結果、MPOファイルは常に拒否され、同じ画像を標準的なJPEG/PNGとして再エンコードすれば、**元の解像度のまま**成功します（寸法、`image[]` フィールド名、または `quality`/`size` パラメータとは無関係です）。このエラーは入力検証段階で返されるため、**課金されません**。

    **修正方法**：アップロード前にPillowで再エンコードします（`Image.open(f).format` が `"MPO"` を返す場合は変換が必要です）。

    ```python theme={null}
    from PIL import Image
    im = Image.open("photo.jpg")
    im.load()                          # for MPO, keeps only the first frame
    im.convert("RGB").save("photo_fixed.jpg", quality=92)
    ```

    詳細および検出方法については、[画像編集API — 参照画像の形式要件と前処理](/ja/api-capabilities/gpt-image-2/image-edit#reference-image-format-requirements-and-preprocessing)を参照してください。
  </Accordion>

  <Accordion title="マスクファイルはどのように準備すればよいですか？">
    * 元画像と**同じサイズ**で、**PNG形式**、**4MB未満**
    * **アルファチャンネルが必須**：透明（alpha=0）= インペイント領域、不透明 = 保持
    * 最初の画像にのみ適用されます
    * マスクは「ソフトガイド」です。モデルはマスク領域の周囲を拡張または縮小する場合があります
  </Accordion>

  <Accordion title="gpt-image-2 と gpt-image-2-all：どちらを選ぶべきですか？">
    | 選択肢                                                  | 適した用途                                                                                              |
    | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
    | **gpt-image-2.5-flare / sunburst / gpt-image-2**（公式） | サイズや品質を正確に制御したい、OpenAI公式と完全に一致させる必要がある、4K出力が必要、マスクインペイントが必要な場合。flareは3つの中で最速、sunburstは最も精密なエディターです |
    | **gpt-image-2-all**（リバース）                            | 画像1枚あたり一律 \$0.03、30～60秒のレンダリング、最小限のパラメータ、強い一貫性 / 中国語テキストを求める場合                                     |
  </Accordion>

  <Accordion title="公式のOpenAI SDKを直接使用できますか？">
    はい。コードの変更は不要です。`base_url` を `https://api.apiyi.com/v1` に指定し、`api_key` をAPIYIのtokenに設定してください。

    ```python theme={null}
    from openai import OpenAI
    client = OpenAI(api_key="sk-your-key", base_url="https://api.apiyi.com/v1")
    resp = client.images.generate(model="gpt-image-2.5-flare", prompt="...", size="2048x1152", quality="high")
    ```
  </Accordion>

  <Accordion title="進行中の生成をキャンセルできますか？">
    **いいえ**。`gpt-image-2` はOpenAIの公式同期エンドポイントを使用しています。リクエストが送信されると、キャンセルシグナルなしで完了まで実行されます。クライアントが切断しても、サーバーは生成を完了し、通常どおり課金します。クライアント側のタイムアウトは慎重に設定し、「切断 = 無料」と考えないでください。
  </Accordion>

  <Accordion title="レート制限（RPM）はありますか？">
    デフォルトは **100 RPM**（1分あたり100リクエスト）です。実際に利用可能なRPMは、**プラットフォーム全体の同時実行数**によっても動的に調整されます。より多く必要な場合は、推定QPS / RPMを添えてお問い合わせください。追加のキャパシティを提供できます。
  </Accordion>

  <Accordion title="非同期呼び出しに対応していますか？">
    **いいえ**。`gpt-image-2` はOpenAI公式APIを厳密にミラーリングしており、同期のみです。結果が返されるまでリクエストはブロックされます（`high` + 4Kでは、現実的には1～2分）。非同期キューまたはコールバック機構が必要な場合：

    * ビジネス層でタスクキュー（Celery / BullMQなど）を使って自分でラップする
    * または [`gpt-image-2-all`](/ja/api-capabilities/gpt-image-2-all/overview) を使用する。30～60秒で生成でき、フロントエンドから簡単にポーリングできます
  </Accordion>

  <Accordion title="promptの長さに制限はありますか？ChatGPTのWebアプリには、なぜもっと長い内容を貼り付けられるのですか？">
    はい。**32,000文字**です。これはOpenAI Images APIプロバイダーの制限で、token数ではなく文字数で数えられます。APIYIの公式リレーがこの制限をさらに厳しくすることはありません。Webアプリが無制限に見えるのは、チャットモデルが貼り付けた内容を読み取り、画像ツール用の短いpromptを自分で作成するためです。そのため、画像モデルがその内容自体を見ることはありません。ブランドブックやパッケージ仕様などの長い素材については、まずテキストモデルで1K～3K文字の構造化されたpromptに要約してください。[長いprompt](/ja/api-capabilities/image-long-prompt)を参照してください。
  </Accordion>

  <Accordion title="明示的ではないpromptで safety_violations=[sexual] の400が発生しました。どうすればよいですか？">
    これらのブロックの多くは**画像のレンダリング後**に発生します。画像が生成された後、出力側の分類器によって拒否されるため、失敗した呼び出しにも成功時と同じ程度の時間がかかり、同じpromptでも通る場合と失敗する場合があります。`moderation: low` はprompt側のモデレーションを弱めるだけで、ここでは役に立ちません。最も一般的な原因は、衣服について説明せず、気分だけで人物を描写していることです。そのためモデルが独自に補完し、境界を越えてしまいます。**まず衣服を明示するフレーズを1つ追加し**（それ以外はすべて変更しない）、その後に一度に1語ずつ削除して試してください。完全な事例と20回の呼び出しログについては、[安全性による拒否](/ja/api-capabilities/image-safety-troubleshooting)を参照してください。
  </Accordion>

  <Accordion title="失敗した生成にも課金されますか？">
    **いいえ**。OpenAI組み込みのコンテンツモデレーションが安全でない、または不正なリクエストを `400` エラーで拒否し、**料金は発生しません**。典型的なレスポンス：

    ```json theme={null}
    {
      "status_code": 400,
      "error": {
        "message": "Your request was rejected by the safety system. ...",
        "type": "shell_api_error",
        "code": "moderation_blocked"
      }
    }
    ```

    その他の無料エラー：`401`（無効なtoken）、`429`（レート制限）。**token課金が開始されるのは、リクエストが実際にモデル生成段階に到達した場合（つまり、`200` + `b64_json` が返された場合）のみです。**
  </Accordion>
</AccordionGroup>
