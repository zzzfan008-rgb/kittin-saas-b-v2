# GPT-Image-2.5-All 画像生成/編集

> GPT 画像生成リバースエンジニアリングモデル gpt-image-2-all（ChatGPT Web系統）。1回の呼び出しにつき一律 $0.025/枚の価格設定、約30〜60秒で生成します。テキストからの画像生成、複数画像の合成編集、自然言語編集に対応し、高いテキストレンダリング精度を誇り、中国語 prompt にも適しています。

<Info>
  すべての画像APIは**同期型**です。ポーリングするためのタスクIDはなく、クライアントが切断されると、リクエストが処理中でも結果は失われ、課金は発生します。このモデルでは十分に長いtimeoutを設定してください。詳細は [Image API Essentials & Best Practices](/ja/api-capabilities/image-api-best-practices) をご覧ください。
</Info>

## 概要

**gpt-image-2.5-all** および **gpt-image-2-all** は、APIYIの **GPT 画像生成リバースエンジニアリングモデル**（ChatGPT Web系統）です。ChatGPT Webアプリ全体がImages 2.5に移行したため、`gpt-image-2-all` はすでに2.5画像を生成します。新しい `gpt-image-2.5-all` という名称は、そのアップグレードを明確にしたものに過ぎません。**両名称は価格と挙動が共通しており、相互に互換性があります**。新規プロジェクトでは `gpt-image-2.5-all` をご使用ください。1回の呼び出しあたり **\$0.025/image** という極めて競争力の高い価格設定（2026-10-10に\$0.03から値下げ）で、**約30〜60秒**で画像を生成し、**テキスト画像生成 / 単一画像編集 / 複数画像合成 / 自然言語編集**をサポートしています。テキストレンダリングの再現性が高く、中国語のpromptもネイティブにサポートしています。

<Note>
  **🎨 主な特徴**: 一律 \$0.025/image のレートで利用できる、信頼性の高いリバースエンジニアリングチャネルです。size、quality、n などのパラメータを気にする必要はなく、prompt内でサイズやスタイルを指定するだけです。OpenAI Images APIの標準エンドポイントである `/v1/images/generations`（テキスト画像生成）および `/v1/images/edits`（画像編集）を使用します。

  **出力サイズや4Kを固定する必要がありますか？** 姉妹モデルの[`gpt-image-2-vip`](/ja/api-capabilities/gpt-image-2-vip/overview)に切り替えてください。呼び出し形式は同一で、`size` フィールドが1つ追加されるだけです。
</Note>

## AI エージェントに統合作業を任せる

<Note>
  Codex / Claude Code / Cursor で構築している場合は、下のプロンプトをコピーしてエージェントに渡してください。まずこのページのプレーンテキスト版を取得し（任意の docs URL に `.md` を付けてください）、その後はあなたのプロジェクトのスタックでコードを書きます。タイムアウト、base64 レンダリング、アップロード圧縮、このモデルが拒否するパラメータは、すでに要件に組み込まれています。
</Note>

<Prompt description="Codex、Claude Code、Cursor などのツールに貼り付けて、gpt-image-2-all のテキストから画像生成と画像編集を統合またはトラブルシュートしてください。" icon="bot" actions={["copy"]}>
  このプロジェクトで gpt-image-2-all のテキストから画像生成と画像編集を統合またはトラブルシュートしてください。

  コードに触る前にドキュメントを読んでください。このページのプレーンテキスト版として [https://docs.apiyi.com/en/api-capabilities/gpt-image-2-all/overview.md](https://docs.apiyi.com/en/api-capabilities/gpt-image-2-all/overview.md) を取得してください。パラメータの詳細をさらに確認したい場合は、テキストから画像生成ページと image-edit ページにも同じように `.md` を追加してください。

  要件:

  1. タイムアウト: クライアントのタイムアウトを 360 秒に引き上げてください。画像 API は同期処理であり、task ID はありません。したがって、クライアントが切断されると、リクエストは課金されたまま結果が失われます。早くタイムアウトさせるのではなく、待機してください。リバースプロキシ、ゲートウェイ、サーバーレス実行制限もすべて拡張する必要があります。生成時間より短いレイヤーが 1 つでもあると、リクエストはそこで切断されます。

  2. レスポンスのレンダリング: デフォルトは base64（`b64_json`、`data:` プレフィックスなし）です。代わりに `response_format` を url に設定すると、CDN リンクを取得することもできます。**デフォルトに頼らず、常に `response_format` を明示的に送信してください** — 以前、グループや負荷によってデフォルト動作が変わったことがあります。base64 を受け取った場合は、それをレンダリングしてディスクへの保存アクションを用意してください。URL を受け取った場合は、約 24 時間で期限切れになるため、すぐにダウンロードしてサーバー側で再ホストしてください。`data[]` の各エントリには 2 つのフィールドのうち 1 つしか入っていないため、どちらにも対応できるように防御的にパースしてください。

  3. アップロード前に圧縮する: `/v1/images/edits`（multipart）を呼び出す前に、各参照画像を圧縮してください。1.5MB を超えるファイルのみ処理し、縦横比を維持したまま長辺を 2048px に縮小し（小さい画像は決して拡大しない）、品質 0.9 で再エンコードし、元の形式を保持します。複数画像リクエストでは合計サイズを 6MB 未満に保ち、単一画像は 10MB を超えないようにしてください。1 枚の画像の圧縮に失敗した場合は、元画像にフォールバックして処理を続けてください。圧縮失敗を理由にリクエスト全体を中止してはいけません。

  4. パラメータの禁止事項: このモデルは `size`、`quality`、`n`、`aspect_ratio` を **受け付けません**。どれも送信しないでください。特に注意すべき 2 つの落とし穴があります。`n` を 3 にすると 3 画像分の課金になりますが、返ってくるのは 1 枚だけです。また、OpenAI SDK のメソッド `client.images.generate()` は既定で `size` と `n` を送信するため、**ここでは生の HTTP リクエストを送るほうが安全です**。出力寸法は代わりに prompt プレフィックスで制御します（たとえば、prompt の先頭に横長 16:9 の指示を入れます）。このページには、検証済みの prompt から解像度への対応表があります。それに従ってください。

  5. `APIYI_API_KEY` 環境変数からキーを読み取り、[https://api.apiyi.com/v1](https://api.apiyi.com/v1) を base URL として使用してください。ハードコードしてはいけませんし、git にコミットしてもいけません。

  6. 完了したら、実際に 1 回のテキストから画像生成呼び出しと 1 回の画像編集呼び出しを実行し、その結果とそれぞれのコストを見せてください。
</Prompt>

<Accordion title="このプロンプトで防げること">
  | 要件 | 防げる落とし穴 |
  | - | - |
  | タイムアウトを 360 秒に引き上げる | 主流の HTTP クライアントは既定で 30〜60 秒のタイムアウトになっており、サーバーが通常どおり生成中でもリクエストを切ってしまいます。さらに、**切断されたリクエストでも課金は発生します**。 [Image API Essentials & Best Practices](/ja/api-capabilities/image-api-best-practices) を参照してください |

</Accordion>

## 料金

| モデル | 課金方式 | 料金 | 出力 |
| - | - | - | - |
| `gpt-image-2-all` | 呼び出しごと | **\$0.025 / 画像** | 1回の呼び出しにつき1枚 |
| `gpt-image-2.5-all` | 呼び出しごと | **\$0.025 / 画像** (-all と同一) | 1回の呼び出しにつき1枚（GPT-Image 2.5 準拠） |

<Info>
  **課金に関する注意事項**:

  * 一律料金です。解像度、品質、prompt の長さによる料金設定の違いはありません
  * 失敗したリクエスト（認証エラー、パラメータ検証エラー）には課金されません
  * N枚の画像が必要な場合は、API を並行して N 回呼び出してください
</Info>

<Note>モデルの料金は公式のものと連動しており、プロバイダーによる改定時に変更される場合があります。上記の表は参考用です。正式な情報については、上部ナビゲーションの**モデル料金**タブをご確認ください: [モデル料金](/en/models/index)。</Note>

<Tip>
  **2026-10-10からの値下げ: \$0.03 → \$0.025/画像**（`gpt-image-2-all` と `gpt-image-2.5-all` の両方に適用）。

  * **理由**: -all シリーズは単体でも高い画像品質を提供し、-vip シリーズよりも安定しています。-vip はプロバイダー側のリスク管理の影響をより受けやすい傾向にあります（メンテナンスおよび容量追加は継続しており、-vip も引き続きご利用いただけます）。この値下げは、日常的な画像生成において -all を手軽なデフォルトの選択肢としていただくことを目的としています。
  * **唯一のトレードオフ**: 出力解像度は 1K〜1.5K であり、2K / 4K には対応していません。日常的な生成にはこれで十分対応可能です。固定サイズや 4K が必要な場合は、-vip または公式リレーをご利用ください。
  * **実際にはさらに安価**: \$0.025 は割引前の価格です。チャージボーナス（10%〜20% の追加クレジット）と組み合わせることで、実質的なコストをさらに抑えることができます。
</Tip>

<Tip>
  **姉妹モデル**: [`gpt-image-2-vip`](/ja/api-capabilities/gpt-image-2-vip/overview)（Adobe リバース回線（Firefly））— \$0.03/画像、30種類の明示的なサイズに対応（4K を含む）、同一の呼び出し形式です。出力サイズを固定したい場合や 4K が必要な場合は、こちらに切り替えてください。
</Tip>

## グループの設定

`gpt-image-2-all`は`Default`グループに存在するため、**追加のグループは不要です**。リバースチャネルは現在安定して供給されているため、公式リレーの`gpt-image-2`のようなエンタープライズグループへのフォールバック構成は存在しません。

| モデル | グループ | 備考 |
| - | - | - |
| `gpt-image-2-all` | `Default` | ChatGPT-webリバース、一律\$0.025/画像、約30〜60秒 |
| `gpt-image-2.5-all` | `Default` | 同じラインのGPT-Image 2.5バージョン、一律\$0.025/画像、-allと同じグループ |
| `gpt-image-2-all` | `image2_OSS` | **1倍レート倍率（追加料金なし）**、確定的なURL出力 — デフォルトグループの負荷が高い場合でもbase64にフォールバックしません |

### 確定的なURL出力が必要な場合 → `image2_OSS`グループへの切り替え

デフォルトグループにおいて2026年7月時点で計測された結果では、`response_format`を省略した場合、`gpt-image-2-all`（および`gpt-image-2-vip`）は`b64_json`を返します。画像のURLを取得するには明示的に`response_format: "url"`を渡してください。デフォルトグループの出力形式は**保証されていません** — これまではデフォルトで`url`となり、高負荷時には`b64_json`へフォールバックしていましたが、チャネルのバージョンによって変更されてきました。

業務が**URL出力に依存している**場合（データベースへのURLの直接書き込み、URLによるフロントエンド描画、base64が許容されない場合など）、tokenのグループを\*\*`image2_OSS`**に切り替えてください。これは**確定的なURL出力\*\*のために特別に構築されたグループであり、\*\*1倍レート倍率（追加料金なし）\*\*で、両方のリバースモデル`gpt-image-2-all`および`gpt-image-2-vip`に有効です。レスポンスに常に画像URLが含まれ、base64にフォールバックしないことが保証されます。

<Tip>
  **高度な設定（`gpt-image-2-vip`および公式リレーの`gpt-image-2`も併用する場合）**：tokenで3つのモデルすべてをカバーする場合は、tokenのグループ優先度を次のように設定してください。

  * **第一優先**：`image2Enterprise`（1.2倍エンタープライズグループ、公式リレー専用の安定レーン）
  * **デフォルトフォールバック**：`Default`（両方のリバースモデルがここに属し、モデルごとにルーティングされます）

  結果：公式リレーの`gpt-image-2`は安定性のためにエンタープライズレーンを利用し、2つのリバースモデルはデフォルトグループにとどまります — 1つのtokenで3つすべてをカバーし、互いに干渉しません。
</Tip>

| 属性 | 値 |

| **オプションの形式** | `url`（R2 CDN高速化リンク、**有効期間は約1日**、明示的な`response_format: "url"`の指定が必要） |

<Warning>
  このモデルは**出力サイズがアダプティブ**であり、公式の`gpt-image-2` APIと同等ではありません。出力サイズを厳密に固定したい場合や4Kが必要な場合は、[`gpt-image-2-vip`](/ja/api-capabilities/gpt-image-2-vip/overview)（Adobeリバース回線（Firefly）、4Kを含む30種類の明示的なサイズに対応）をご利用ください。公式APIと完全な互換性が必要な場合は、[`gpt-image-2`](/ja/api-capabilities/gpt-image-2/overview)をご利用ください。
</Warning>

<Warning>
  **⏰ 画像URLの有効期間：約1日（デフォルト）**

  `url`モードのレスポンスにおける`url`フィールドはR2 CDNリンクであり、**約24時間で失効します**（それ以降のリクエストは404エラーになります）。長期保存が必要な画像（商品画像、ユーザー作品、履歴レコードなど）については、生成後**できるだけ早くダウンロードし、ご自身のストレージに永続化してください**。

  一般的な2つのアプローチ：

  * **サーバー側でのダウンロード**：レスポンスを受信したらすぐに、`requests` / `fetch`を使用して画像を取得し、S3 / OSS / R2 / ローカルディスクに保存します
  * **`b64_json`レスポンス形式の使用**：base64データとして画像を直接取得できるため、追加のクロスオリジンダウンロードを省略できます。フロントエンドでのレンダリングやファイルへの直接書き込みに最適です
</Warning>

## エンドポイント

| エンドポイント | 用途 | Content-Type | 最適な用途 |
| - | - | - | - |
| `POST /v1/images/generations` | テキストから画像生成 | `application/json` | OpenAI Images API標準フォーマット — 同じコードで公式チャンネルとリバースチャンネルの両方を呼び出し可能 |
| `POST /v1/images/edits` | 画像編集（単一/複数） | `multipart/form-data` | OpenAI Images API標準フォーマット — 同じコードで公式チャンネルとリバースチャンネルの両方を呼び出し可能 |

<Tip>
  **OpenAI Images APIを使用してください**（`/v1/images/generations` + `/v1/images/edits`）。理由は2点あります：

  1. **より安定**: Images APIチャンネルは上流リソースの供給がより豊富なため、呼び出し成功率が高くなります
  2. **公式リレーと互換性があり簡単に切り替え可能**: 呼び出し方法や`size`などのパラメータは公式リレーの[`gpt-image-2`](/ja/api-capabilities/gpt-image-2/overview)と完全に互換性があります — リバースチャンネルでリスクコントロールによる不安定化が発生しても、コードを一切変更することなく\*\*`model`名を差し替えるだけ\*\*で対応可能です

  また、チャットベースのエンドポイント（`/v1/chat/completions`、現在は非推奨）もあります — 詳細は以下のFAQをご確認ください。
</Tip>

<Tip>
  **ドメインオプション**: `api.apiyi.com`がメインドメインです。`b.apiyi.com`などの代替ゲートウェイドメインを使用することもできます。レスポンスの挙動は同一です。
</Tip>

<Info>
  **`size`パラメータで出力サイズを固定したいですか？** 姉妹モデルの[`gpt-image-2-vip`](/ja/api-capabilities/gpt-image-2-vip/overview)をご利用ください — エンドポイントは同一で、追加の`size`フィールドが1つあるだけです（4Kを含む30種類の明示的なサイズに対応）。
</Info>

## サイズとアスペクト比の制御（prompt 内に記述）

`gpt-image-2-all` には `size` パラメータがありません。サイズは prompt に記述します。出力サイズを厳密に固定したい場合（EC のヒーロー画像、ポスターテンプレート、4K 壁紙など）は、代わりに [`gpt-image-2-vip`](/ja/api-capabilities/gpt-image-2-vip/overview) を使用してください。

### 検証済みの「prompt の表現 → 実際の解像度」表

以下の 8 つの表現は、実際に安定して再現されることが確認済みです。第 1 列の表現を prompt の **先頭** に置くと、第 2 列に示した解像度が得られます（いずれの出力もおよそ 1.5K ピクセル帯です）。

| Prompt の表現（そのまま記述） | 検証済みの解像度 | おおよそのサイズ | 実際の比率 |
| - | - | - | - |
| `横版 16:9` (Landscape 16:9) | 1672 × 941 | 約 1.9 MB | 16:9 |
| `竖屏 9:16` (Portrait 9:16) | 941 × 1672 | 約 2.1 MB | 9:16 |
| `4:3` | 1448 × 1086 | 約 2.3 MB | 4:3 |
| `3:4` | 1086 × 1448 | 約 2.5 MB | 3:4 |
| `3:2 尺寸` (3:2 size) | 1536 × 1024 | 約 2.9 MB | 3:2 |
| `2:3 尺寸` (2:3 size) | 1024 × 1536 | 約 3.0 MB | 2:3 |
| `2:5 竖屏` (2:5 portrait) | 793 × 1983 | 約 1.9 MB | 2:5 |
| `5:2 横屏` (5:2 landscape) | 1983 × 793 | 約 1.9 MB | 5:2 |

<Info>
  **注記**:

  * すべての出力は **約 1.5K ピクセル帯**（長辺 1500〜2000 px）です。これはモデルの実質的な上限であり、本当に「任意の解像度」ではありません。
  * prompt に表の表現以外を **入れない** ときが、再現性が最も高くなります。ほかの構図に関する語を混ぜると、ずれが生じます。
  * 中国語の文字列は実際に送信する値です。翻訳せず、そのまま使うことをおすすめします。
</Info>

### スタイル用の表現（固定解像度なし）

以下の表現には検証済みの解像度がありません。上の表と組み合わせて、スタイル修飾子としてのみ使用してください。

| 必要なもの | 表現（スタイルのガイダンスのみ — 解像度の保証なし） |
| - | - |
| 正方形 | `1024×1024 square` / `1:1 square composition` |
| 超横長バナー | `Banner 21:9 ultra-widescreen` |
| スタイル修飾子 | `cinematic` / `phone poster` / `square composition` |

<Tip>
  **ヒント**: サイズや構図を表す語は、prompt の **先頭** に置くとより反映されやすくなります。
</Tip>

### この表をエンドユーザーに公開する

`gpt-image-2-all` には `size` パラメータがありませんが、ユーザーに「サイズ / アスペクト比」ドロップダウンを用意して、**公式の `size` フィールドのように見せる** ことはできます。

* 上の表にある prompt の表現を、オプションの `value` として使用します（例: `横版 16:9`）
* ユーザーが何を得られるか分かるように、オプションラベルに **予想解像度** を表示します（例: `Landscape 16:9 (1672×941)`）
* バックエンドでは、選択された表現をユーザーの元の prompt の先頭に付けてから API に送信します

```js theme={null}
const SIZE_OPTIONS = [
  { label: "Landscape 16:9 (1672×941)", prefix: "横版 16:9" },
  { label: "Portrait 9:16 (941×1672)",  prefix: "竖屏 9:16" },
  { label: "4:3 (1448×1086)",           prefix: "4:3" },
  { label: "3:4 (1086×1448)",           prefix: "3:4" },
  { label: "3:2 (1536×1024)",           prefix: "3:2 尺寸" },
  { label: "2:3 (1024×1536)",           prefix: "2:3 尺寸" },
  { label: "2:5 portrait (793×1983)",   prefix: "2:5 竖屏" },
  { label: "5:2 landscape (1983×793)",  prefix: "5:2 横屏" },
];

const finalPrompt = `${selected.prefix}, ${userPrompt}`;
```

<Warning>
  基盤モデルは引き続き **適応的** です。ピクセル単位のわずかなずれは正常です。エンドユーザーに対して、完全一致の出力を約束しないでください。**出力サイズを厳密に固定したい場合**（EC のヒーロー画像、ポスターテンプレート、4K 壁紙など）は、姉妹モデル [`gpt-image-2-vip`](/ja/api-capabilities/gpt-image-2-vip/overview) を使用してください。価格は同じ、呼び出しコードも同じで、追加の `size` フィールドが 1 つあるだけです。
</Warning>

## エラーコードと再試行

| Status | 意味 | 推奨 |
| - | - | - |
| `401` | 無効な token | Bearer Token を確認してください |
| `429` | rate limit / quota 超過 | 指数バックオフで再試行 |
| `5xx` | 一時的な gateway/backend エラー | 1〜2回再試行 |
| タイムアウト | リバースチャネルのピーク + 画像のアップロード/ダウンロードのロングテール | クライアントのタイムアウトを **≥ 300s** に設定してください（保守的） |

<Info>
  **クライアントの推奨事項**:

  * リクエストタイムアウトは **300秒から** に設定してください（保守的。一般的には 30〜60s ですが、画像のアップロード / ダウンロードとリバースチャネルのピークテールにより変動が大きく、120s では誤タイムアウトが頻発します）
  * 5xx とタイムアウトには **指数バックオフ** を使用してください（2〜3回の再試行を推奨）
  * デバッグのために `request-id` レスポンスヘッダーをログに記録してください
</Info>

## FAQ

<AccordionGroup>
  <Accordion title="gpt-image-2-all と gpt-image-2-vip の両方がありますが、どちらを選ぶべきですか？">
    どちらも**同じ呼び出し形式**を持つリバースエンジニアリングチャネルです。-all は1回あたり \$0.025、-vip は1回あたり \$0.03 です。違いは `size` のサポート、生成時間、安定性です：

    * **厳密なサイズ制御が不要で、より高速かつ安定した出力を求める場合** → `gpt-image-2-all`（約30〜60秒、プロンプト内でサイズを指定、1K〜1.5K出力）。
    * **出力サイズを固定したい、または4Kが必要な場合** → [`gpt-image-2-vip`](/ja/api-capabilities/gpt-image-2-vip/overview)（約90〜150秒、4Kを含む30種類の明示的なサイズ）。
    * **`quality` の調整機能や OpenAI API との完全なフィールド互換性が必要な場合** → 公式の [`gpt-image-2`](/ja/api-capabilities/gpt-image-2/overview) をご利用ください。
  </Accordion>

  <Accordion title="一度に複数の画像を生成できますか？">
    いいえ。このモデルは1回の呼び出しにつき1枚の画像を返します。N枚の画像が必要な場合は、APIを並行してN回呼び出してください。各呼び出しはそれぞれ \$0.025 で個別に課金されます。
  </Accordion>

  <Accordion title="n パラメータはサポートされていますか？n=3 を渡すとどうなりますか？">
    \*\*いいえ。\*\*このモデルは1回の呼び出しにつき1枚の画像を返します。複数の画像が必要な場合は、**繰り返しの呼び出しまたは並行呼び出し**を使用してください。

    ⚠️ **重要**：リクエストで `n=3` を渡すと、**課金は 0.025 × 3 = \$0.075 になります**が、**実際に返される画像は1枚のみです**。無駄な課金を避けるため、リクエストから `n` フィールドを必ず削除してください。
  </Accordion>

  <Accordion title="コンテンツが拒否されたり、モデルが「I can't do that」と返答した場合、課金されますか？">
    これは**同期的なチャット形式のレスポンス**を使用するリバースエンジニアリングチャネルです。結果は**課金ルールの異なる**2つのケースに分かれます：

    **1) HTTP 5xx が返された場合 → 課金されません**

    上流のコンテンツポリシーによってリクエストがハードブロックされると、次のようなレスポンスが返されます：

    ```json theme={null}
    {
      "error": {
        "message": "Image was not generated as expected. Please adjust the prompt and retry (traceid: 0672821c6951af183dbf847130caaf16)",
        "localized_message": "Unknown error",
        "type": "invalid_request_error",
        "param": "",
        "code": null
      }
    }
    ```

    これらのハードエラーは**課金されません**。ユーザーにプロンプトを調整して再試行するよう促してください。

    **2) テキストによる「ソフトな拒否」を含む HTTP 200 → 課金されます**

    会話内でモデルがソフトな拒否を行った場合（例：「I can't do that」、「申し訳ありませんが、このリクエストには…が含まれています」など）、プロトコルレベルでは通常の chat completion として扱われるため、**課金されます**。リバースチャネルでは、プロトコル層で「拒否テキスト」と「画像出力」を確実に区別することができません。

    **ソフトな拒否を単純に免除できない理由**

    すべてのソフトな拒否を自動的に免除すると、プラットフォームが上流の失敗したすべての呼び出しコストを負担することになります。さらに重要なこととして、**上流のコンテンツセーフティを頻繁にトリガーすると、サプライヤーのアカウントが利用停止（BAN）されるリスクも高まります**。これは、完全には排除できない供給側の実質的なコストです。

    **インテグレーターへの推奨事項**

    * ✅ **事前フィルタリングとユーザーへの警告**：フロントエンドまたはゲートウェイでキーワード/シナリオのフィルター（実在の人物名、著作権のあるキャラクター、センシティブなトピック）を追加し、「有名人やIP関連のトピックは失敗する可能性があり、その場合でも上流ポリシーにより課金される場合があります」といったUIヒントを表示します。これにより、無駄な課金を大幅に削減できます。
    * ✅ **消費者向けプロダクト向けの月次返金**：一般ユーザー向けプロダクトではユーザー入力を完全に制限できないことを理解しています。月間の利用額が十分に大きい場合（**月額 \$1000 以上**）、**ログを月単位でまとめて**（レイテンシが短い呼び出しは通常ソフトな拒否に該当します）、サポートにお問い合わせいただくことで、一括の手動クレジット付与を受けることができます。呼び出しごとに異議申し立てを行う必要はありません。

    📖 関連：[500 エラーは通常コンテンツポリシーの抵触です（課金されません）](/en/live/2026-04/gpt-image-2-all-500-content-policy)
  </Accordion>

  <Accordion title="b64_json に data:image/png;base64, プレフィックスを追加する必要がありますか？">
    \*\*まず判定してから処理してください。\*\*2026年7月の検証時点では、返される `b64_json` は **`data:` プレフィックスのない生の base64** です。ファイルに書き込む場合はデコードし、レンダリングする前にご自身でプレフィックスを先頭に追加してください。なお、**以前のバージョンにはプレフィックスが含まれていました**。コード内に `startsWith('data:')` のチェックを追加してください。プレフィックスが存在する場合はその値を直接 `img src` として使用し、存在しない場合は先にデコードするかプレフィックスを追加します。これにより、二重プレフィックスの付与や、プレフィックス付き文字列をデコードして画像が破損することを防げます。
  </Accordion>

  <Accordion title="プロンプトで 1024x1024 と指定しているのに、異なるサイズになるのはなぜですか？">

  </Accordion>

  <Accordion title="入力画像を圧縮すべきですか？プロンプトに 4K や 8K と記述すると効果はありますか？">

    **圧縮による画質の低下を心配する必要はありません**。このモデルの出力解像度は入力サイズではなく、プロンプトの構図の言い回しによって決まります。入力を小さくすることは処理速度を向上させるだけです。

  <Accordion title="参照画像の最大サイズとサポートされている形式は何ですか？">

  </Accordion>

  <Accordion title="返された画像 URL の有効期限はどのくらいですか？ダウンロードする必要がありますか？">
    `url` モードのレスポンスの `url` フィールドは、**約1日（24時間）で期限切れになる R2 CDN リンク**です。それ以降のリクエストは 404 になります。

    **強く推奨**：生成後すぐに、生成された画像を**ご自身のオブジェクトストレージ（S3 / OSS / R2）、CDN、またはデータベース**にダウンロードして永続化してください。返された URL への長期的な直リンクは避けてください。

    **2つの推奨アプローチ**：

    * **サーバーサイドプロキシ**：レスポンス受信後すぐに `requests.get(url)` を行い、ご自身のストレージに保存して、独自の URL をフロントエンドに返します。
    * **`b64_json` の使用**：リクエストに `"response_format": "b64_json"` を追加して base64 画像データを直接取得します。クロスオリジンのダウンロードが1回減るため、フロントエンドでのレンダリングやファイルへの直接書き込みに最適です。

    短時間のプレビュー（単一セッション内での表示）であれば、永続化せずに R2 URL をそのまま使用できます。
  </Accordion>

  <Accordion title="ストリーミングはサポートされていますか？">
    いいえ。このモデルは画像を一度に返します。ストリーミングはサポートされていません。レイテンシが懸念される場合は、クライアント側で「生成中...」のような進行状況インジケーターを表示し、**300秒のタイムアウト**（保守的な設定）を設定してください。
  </Accordion>

  <Accordion title="公式の OpenAI SDK は使用できますか？">
    はい。`base_url` を `https://api.apiyi.com/v1` に向け、`api_key` を APIYI の token に設定してください。ただし、`client.images.generate()` はデフォルトで `size` / `n` を送信します。このモデルは両方のパラメータを拒否するため、`/v1/images/generations` および `/v1/images/edits` に対して `requests` / `fetch` を使用して生の HTTP 呼び出しを行うことを推奨します。
  </Accordion>

  <Accordion title="中国語と英語のプロンプトで大きな違いはありますか？">
    このモデルはネイティブに中国語をサポートしており、結果は同等です。中国語特有のシナリオ（書道、伝統的な祭りの要素など）では、中国語の表現の方がより自然に仕上がります。
  </Accordion>

  <Accordion title="/v1/chat/completions 経由で画像を生成することは引き続き可能ですか？">
    はい、エンドポイントは引き続き動作しますが、**現在は推奨されていません**。代わりに `/v1/images/generations` および `/v1/images/edits` を使用してください（より安定しており、公式リレーの `gpt-image-2` とも同じコードで動作します）。

    チャットベースの形式が適しているのは、マルチターンの反復編集、またはオンライン画像 URL を直接渡す場合の2つのシナリオのみです。画像の生成意図が曖昧な場合、モデルは画像の代わりにプレーンテキストを返す可能性がある点にご注意ください（プロンプトの先頭に「画像を生成してください：」のような固定プレフィックスを追加して強調してください）。

    完全なパラメータについては、[チャットベースの API リファレンス](/en/api-capabilities/gpt-image-2-all/chat-completions)を参照してください。
  </Accordion>
</AccordionGroup>
