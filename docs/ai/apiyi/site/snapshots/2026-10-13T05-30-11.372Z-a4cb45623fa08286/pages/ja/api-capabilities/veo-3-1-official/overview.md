# VEO 3.1 公式動画生成

> Google Veo 3.1 公式リレーチャンネルの完全ガイド: Google AI Studio への透過的なパススルー、リクエストごとの課金で $0.3 / $1.2、柔軟な 4 / 6 / 8 秒の長さ、720p / 1080p / 4k の階層、そして手間のないオンボーディング — グループや課金モードの切り替えは不要です。

## 概要

**VEO 3.1 Official** は、Google Veo 3.1 向けの APIYI による**公式リレーチャネル**です。Google AI Studio の `veo-3.1-generate-preview` / `veo-3.1-fast-generate-preview` 非同期エンドポイントへの透過的なパススルーであり、モデル ID、レスポンスフィールド、制約事項はすべてアップストリームと同一です。**リクエストごとの課金**に対応し、**`Default` グループで呼び出し可能** — 現在利用できる中で最も導入の手間が少ない、公式品質の Veo 3.1 チャネルです。

<Note>
  **🎬 ハイライト**: Google AI Studio への透過的なパススルー + ネイティブ同期オーディオ + 柔軟な 4 / 6 / 8 秒の動画長 + 3段階の解像度ティア（720p / 1080p / 4k）+ \$0.3 からのリクエスト単位課金 + **`Default` グループ + リクエスト単位課金または従量課金優先トークン**（専用グループは不要、純粋な従量課金は非対応）。**広告ショート動画、EC 用アセット、ソーシャルメディアコンテンツ、製品デモ**など、最もシンプルな導入方法で公式水準の品質を必要とする用途に適しています。
</Note>

<Warning>
  **⚠️ `/content` 経由でダウンロードし、自身で再ホストしてください**: `status: "completed"` になったら、エンドユーザーに配信する前に **`GET /v1/videos/{task_id}/content` を呼び出して MP4 バイナリを取得**し、ご自身の OSS / CDN に保存してください。完了レスポンスには `video_url`（認証不要の直接リンク）が含まれる**場合もあります**が、これは**約24時間後に期限切れ**となり（`expires_at` を参照）、**すべてのタスクで保証されているわけではありません**。そのため、一時的なプレビューにのみ使用し、永続的なアドレスとしては決して使用しないでください。詳細は以下の [API エンドポイント](#api-endpoints) を参照してください。
</Warning>

</Note>

<Prompt description="コーディングエージェントに VEO 3.1 Official のテキストから動画生成および画像から動画生成を統合またはトラブルシューティングさせます。Codex、Claude Code、Cursor および同様のツールにコピー＆ペーストしてください。" icon="bot" actions={["copy"]}>
  このプロジェクトで VEO 3.1 Official のテキストから動画生成および画像から動画生成を統合 / トラブルシューティングしてください。

  コードに手を触れる前にドキュメントを読んでください。このページのプレーンテキスト版として [https://docs.apiyi.com/en/api-capabilities/veo-3-1-official/overview.md](https://docs.apiyi.com/en/api-capabilities/veo-3-1-official/overview.md) を取得してください。より詳細なパラメータ情報については、同様にテキストから動画生成および画像から動画生成の各ページに `.md` を追加してください。

  要件：

  1. 同期的な待機ではなく、3ステップの非同期フローを使用してください。このチャネルは**非同期のみ**です。`POST /v1/videos` でジョブを送信して `task_id` を受け取り、その後 `status` が `completed` になるまで **8〜10秒** ごとに `GET /v1/videos/{task_id}` をポーリングし、`GET /v1/videos/{task_id}/content` からMP4をダウンロードします。**webhook は存在せず、ポーリングのみです**。コールバック設定を探さないでください。

  2. 動画の取得（**このモデルにおける最も重要な項目**）：MP4バイナリストリームの信頼できる情報源として `/content` エンドポイントを扱ってください。そのリクエストには\*\*`Authorization` ヘッダーを含める必要があります\*\*。そのため、フロントエンドは video タグ `src` に直接配置**できません**（認証ヘッダーなしのブラウザリクエストは401になります）。完了時のレスポンスには認証不要の `video_url` 直接リンクが含まれる**場合があります**が、約24時間後に期限切れとなり（`expires_at` を参照）、**すべてのタスクで保証されているわけではありません**。コード内でこれに依存しないでください。存在する場合は簡単なプレビューに使用し、それ以外は `/content` を経由してください。正しいアプローチ：**ステータスが `completed` になったら直ちにサーバー側でMP4をダウンロードし、独自のオブジェクトストレージまたはCDNで再ホストして**、独自 URL をエンドユーザーに提供してください。**リモートの動画は約24時間しか保持されないため、長期的なアドレスとして `task_id` に決して依存しないでください**。`/content` が400を返した場合は、4秒ごとに最大約30秒間リトライしてください。`status` が `completed` に切り替わった直後には、400を返す最大約20秒のウィンドウが存在します（エラー内容は `task status is IN_PROGRESS` です）。curl でダウンロードする場合は `-f --retry-all-errors` を追加する必要があります。そうしないと400がリトライされず、エラーの JSON が動画ファイルに書き込まれます。**`502` の場合は異なります**。プロバイダーがファイルを取得できず、リトライしても解決しないため、2回試行した後に停止し、タスクを失敗としてマークして `task_id` を記録してください。決して無制限のリトライループを書かないでください。

  3. 段階的なタイムアウト：POST送信には30秒を見込んでください（multipart の参照画像アップロードは遅くなる場合があります）。ポーリングの待機時間は解像度ごとに上限を設定してください（720p および 1080p は **3分**、4K は **10分**）。単一の値をハードコードするのではなく、設定項目として持たせてください。

  4. モデルとパラメータ：モデル名は `veo-3.1-fast-generate-preview`（安価で日常利用に適しています）または `veo-3.1-generate-preview`（標準ティア）のいずれかです。時間（秒数）フィールドは **`duration` ではなく `seconds`** であり、**文字列（`"4"` / `"6"` / `"8"`）である必要があります**。数値はサーバーによって拒否されます。**フィールド名を `duration` にしてもエラーは発生しません。警告なしに無視され、時間は4秒にフォールバックします**。「8秒を要求したのに4秒になった」というのはまさにこれが原因です。**時間と解像度は連動しています**。`1080p` と `4k` は両方とも **`"8"` のうち `seconds` のみ**を受け付け、`"4"` や `"6"` を渡すとエラーになります。3つの時間すべてを許可するのは `720p` のみです。そのため、UIで解像度と時間を一緒に選択させる場合は、不正な組み合わせを提示するのではなく、ペアとして制約をかけてください。さらに4Kにはモデル `veo-3.1-generate-preview` と10分のタイムアウトが必要です。4Kは1080pよりレンダリングに4〜6倍時間がかかり、ファイルサイズも約10倍になりますが、**呼び出しごとの課金は時間と解像度の両方に依存しません（4Kでも追加料金はかからず、安くもなりません）**。そのため、デフォルトは1080pにし、4Kはユーザーの明示的な選択にしてください。

  5. 画像から動画生成における3つの厳格な制約：リクエストは JSON ではなく **`multipart/form-data`** でなければなりません。画像フィールド名は**正確に `input_reference`** でなければなりません（`image`、`reference`、`input_image` はすべて無視されます）。そして**受け付けられる画像は1枚のみ**です（余分な画像は警告なしに無視されます）。リモート URL は**受け付けられない**ため、ファイルまたは base64 をアップロードしてください。受け入れ可能な形式は `image/jpeg`、`image/png`、`image/webp` です。また、このチャネルでは**最初/最後のフレーム（first/last-frame）およびマルチリファレンス（multi-reference）機能は提供されていない**ため、それらについて Google 自身の Veo 3.1 ドキュメントに沿って実装しないでください。multipart モードでは、`metadata.*` フィールドは `resolution`、`aspectRatio`、`seed` というプレーンなフォームフィールドにフラット化されます。

  6. **`generateAudio` を送信しないでください。** Veo 3.1 はネイティブに音声を生成しますが、そのパラメータを渡すとアップストリームが `INVALID_ARGUMENT` を返します。効果音、会話、環境音を制御するには、prompt にその意図を含めてください。このチャネルには音声フィールド自体が存在しません。

  7. 課金とエラー：**課金はモデル名ごとの呼び出し単位**であり、時間、解像度、参照画像を渡したかどうかには依存しません。非同期モードでは、**生成失敗、モデレーションによるブロック、過負荷エラーはすべて課金されません。`completed` ステータスのみが課金されます**。そのため、自動リトライを行っても重複課金のリスクはありません。エラーハンドリングについて：`PUBLIC_` プレフィックスの付いたエラーはアップストリームのモデレーションブロックであり、課金されず、prompt を調整した後に直接リトライできます。`5xx` や `INTERNAL` は一時的なアップストリームエラーであり、同じシードで1〜2回リトライする価値があります。`failed` になるタスクは通常、モデレーション、アップストリームのキャパシティ、または動画ファイルが取得不能であることが原因であり、同様に課金されません（課金が発生していても自動的に返金されます）。理由は `error.message` に記載されているため、ログに記録してください。

  8. 注意すべき token 設定：このモデルでは token が**呼び出しごとの課金**または**従量課金優先**に設定されている必要があります。**通常の従量課金はサポートされていません**。課金モードに関するエラーで呼び出しが失敗した場合は、コンソールで token を切り替えてください。

  9. キーは `APIYI_API_KEY` 環境変数から読み込み、ベース URL として [https://api.apiyi.com/v1](https://api.apiyi.com/v1) を使用してください。決してハードコードしたり、git にコミットしたりしないでください。

  10. 完了したら、テキストから動画生成と画像から動画生成の呼び出しを実際に1回ずつ実行し、生成された動画とそれら2回の呼び出しにかかった費用を示してください。
</Prompt>

## 料金

APIYIは**リクエストごとの従量課金**です — サポート対象の継続時間/解像度の組み合わせ内では定額で、**長時間出力や高解像度出力でも追加料金はありません**。`ai.google.dev/gemini-api/docs/pricing`の公開料金によると、Googleの公式Veo 3.1は秒単位で課金されます。以下の割引は**8秒動画**で計算しています。

| モデル | APIYI価格 | Google公式 8s 1080p | Google公式 8s 4K |
| - | - | - | - |
| `veo-3.1-fast-generate-preview` | **\$0.3 / req** | \$0.96<br />**68.8%オフ** | \$2.40<br />**87.5%オフ** |
| `veo-3.1-generate-preview` | **\$1.2 / req** | \$3.20<br />**62.5%オフ** | \$4.80<br />**75.0%オフ** |

<Info>
  **課金に関する注意**:

  * モデル名ごとに**リクエスト単位**で課金され、継続時間（4/6/8秒）、解像度（720p/1080p/4k）、または`input_reference`の有無に関係ありません — **4Kを選んでも720pと同じ料金です**
  * 非同期モードでは、生成失敗 / コンテンツポリシーによる拒否 / 容量エラーのいずれも**課金されません**
  * [Top-Up Promotions](/ja/faq/recharge-promotions) のチャージ特典ティアにより、実質コストはさらに下がります
  * 4Kはレンダリングが4〜6倍遅く、ファイルは約10倍大きくなります — 日常利用では**1080pをデフォルト**にしてください
  * Googleの公式4K料金は \$0.30/sec（fast）/ \$0.60/sec（standard）で、8秒あたり \$2.40 / \$4.80 です（出典: `ai.google.dev/gemini-api/docs/pricing`）
</Info>

## グループ設定

VEO 3.1 Official は `Default` グループで動作し（1x）、**専用グループへの切り替えは不要**です。Token の課金モードは **Pay-per-request** または **Pay-as-you-go Priority** である必要があります。**純粋な Pay-as-you-go はサポートされていません**（必要に応じて [console](https://api.apiyi.com/token) で Token モードを切り替えてください）。

<Tip>
  **導入時の手間が少ない**: VEO 3.1 Official は Default グループで動作し、Pay-per-request と Pay-as-you-go Priority の両方を受け付けます。専用グループの設定も不要です — **既存の Pay-per-request Token をそのまま使い、`base_url` を変更するだけの「ゼロ設定」導入に最適です**。
</Tip>

## API エンドポイント

| エンドポイント | メソッド | 用途 | Content-Type |
| - | - | - | - |
| `/v1/videos` | POST | 動画生成タスクの送信（テキストから動画 / 画像から動画、統合エンドポイント） | `application/json` または `multipart/form-data` |
| `/v1/videos/{task_id}` | GET | タスクのステータスと進捗の確認 | — |
| `/v1/videos/{task_id}/content` | GET | **生成されたMP4のダウンロード（バイナリストリーム）** | — |

<Warning>
  **⚠️ `/content` 経由でダウンロードしてください。`video_url` は一時的なプレビュー専用です**

  動画を取得する標準的な方法は **`GET /v1/videos/{task_id}/content` であり、MP4バイナリストリームを返します**（`Authorization: Bearer` ヘッダーが必要です）。

  留意事項：

  * 完了時のレスポンスには `video_url`（認証不要の直接リンク）および `expires_at`（約24時間後）が含まれる**場合があります**が、**すべてのタスクで保証されているわけではない**ため、コード側で存在しない場合を処理する必要があります
  * フロントエンドでは `/content` エンドポイントを `<video>` タグに直接設定**できません**。認証ヘッダーのないブラウザリクエストは401になります。期限切れになるまでは、`video_url` を一時的なプレビューに使用できます
  * **`status: "completed"` になったら直ちにMP4をダウンロードし、独自のOSS / CDNに保存した上で**、エンドユーザーには自社のURLを提供してください
  * リモート側のコピーは約24時間保持されます。動画の取得において、**リモートの `task_id` や `video_url` に長期的に依存しないでください**
</Warning>

<Tip>
  **エンドポイントの選択**: プライマリは `api.apiyi.com` です。バックアップゲートウェイ `b.apiyi.com` も同一の動作をします。
</Tip>

## 主要パラメータ

<Tip>
  **⚡ パラメータの完全リファレンス**: `model` / `prompt` / `seconds` / `size` / `metadata.*` の型、デフォルト値、制約を含む完全な表は、[テキストから動画 - パラメータリファレンス](/ja/api-capabilities/veo-3-1-official/text-to-video#parameter-reference) へ移動してください。このセクションでは、特に落とし穴になりやすい **3 つのパラメータ** のみを解説します。
</Tip>

### `seconds`（動画の長さ）

長さフィールドの名前は **`seconds`** であり（`duration` ではありません）、**文字列でなければなりません**（`"4"` / `"6"` / `"8"`）。数値を渡すと、次のようになります:

```
parse_request_failed: cannot unmarshal number into Go struct field ... duration of type string
```

| 値 | 720p | 1080p | 4k |
| - | - | - | - |
| `"4"` | ✅ | ❌ | ❌ |
| `"6"` | ✅ | ❌ | ❌ |
| `"8"` | ✅ (デフォルト) | ✅ (必須) | ✅ (必須) |

<Warning>
  **よくある落とし穴: フィールド名を `duration` にしても、黙って無視されます。** `duration` はこのチャンネルでは認識されないため → 破棄されるため → 長さはデフォルトの **4 秒** にフォールバックします:

  * 720p（および 4 秒を許可する他のティア）では: **エラーにはなりませんが、4 秒しか取得できません**（これがまさに「8s を送ったのに 4s になった」ケースです）
  * 1080p / 4k では: 4 秒は不正なので、`Resolution 1080p requires duration seconds to be 8 seconds, but got 4` でエラーになります

  **正しい使い方: 値 `"8"`（文字列）を持つ `seconds` フィールドを送信してください。**
</Warning>

パラメータの優先順位: `metadata.durationSeconds > seconds > 8`

### `metadata.resolution`（解像度ティア）

| 値 | ピクセル（横向き） | ピクセル（縦向き） | 備考 |
| - | - | - | - |
| `720p` (デフォルト) | `1280x720` | `720x1280` | 3 つの長さすべて |
| `1080p` | `1920x1080` | `1080x1920` | **`seconds="8"` のみ** |
| `4k` | `3840x2160` | `2160x3840` | **`seconds="8"` のみ**、レンダリングは 4〜6 倍遅くなります |

パラメータの優先順位: `metadata.resolution > size > 720p`

### ⚠️ `generateAudio` を渡さないでください

Veo 3 / 3.1 は**標準で音声対応**ですが、`generateAudio` パラメータは**渡してはいけません**。上流側で `INVALID_ARGUMENT` によって拒否されます。音声を制御するには、**意図を prompt に書き込んでください**:

> 「海岸の灯台、夕暮れ時。波、遠くの海鳥、弱い風の音、映画のような雰囲気」

## ベストプラクティス

<Steps>
  <Step title="用途に応じたモデルの選択">
    * **イテレーション／一括プレビュー** → `veo-3.1-fast-generate-preview` (\$0.3/リクエスト)
    * **最終納品／4K** → `veo-3.1-generate-preview` (\$1.2/リクエスト)
    * 両方を同じ prompt ＋ seed で実行し、目視で選択します
  </Step>

  <Step title="まずは4秒で検証">
    新しい prompt ごとに、まずは `seconds: "4"` から開始してカメラワークとスタイルを検証します（レンダリング時間：60〜90秒、\$0.3）。見た目が確定したら、8秒または1080pにスケールアップします。
  </Step>

  <Step title="同期待機ではなく非同期ポーリングを使用">
    公式チャンネルは**非同期のみ**です。POST で送信して `task_id` を取得 → `status: "completed"` になるまで8〜10秒ごとに `GET /v1/videos/{task_id}` をポーリング → `/content` からダウンロードします。**webhook はサポートされておらず、ポーリングのみ**となります。
  </Step>

  <Step title="ティア別クライアントタイムアウトの設定">
    * 720p / 1080p: ハードタイムアウト3分
    * 4K: ハードタイムアウト10分
    * POST 送信（multipart）: 最低30秒
  </Step>

  <Step title="完了後は速やかにダウンロード">
    `status` が `completed` に切り替わったら、**直ちに独自の OSS / CDN にダウンロードしてください**。リモート側のコピーは約24時間しか保持されないため、リモートの `task_id` に長期間依存しないでください。`/content` エンドポイントは、`status` が切り替わった直後に**時々 400 を返すことがあります**。その場合は4秒後に再試行してください（サンプルクライアントにはこの処理が組み込まれています）。同じエンドポイントからの `502` はプロバイダーがファイルを取得できないことを意味するため、再試行しても解決しません。
  </Step>

  <Step title="音声の意図を prompt に記述">
    **`generateAudio` は渡さないでください**（`INVALID_ARGUMENT` が返されます）。環境音、セリフ、BGM については、prompt 内で「waves, distant seabirds, low wind sounds」のように指定してください。
  </Step>

  <Step title="クライアント側でのレート制限">
    同時実行数の上限は公開されていませんが、実際には10件の同時送信がすべて正常にキューに入りました。**本番環境では処理中のリクエスト（in-flight）数を10件以下に制限**し、429 / 5xx に対しては指数バックオフを適用することをお勧めします。
  </Step>
</Steps>

## エラーコードとリトライ

| ステータス / 症状 | 意味 | 推奨される対応 |
| - | - | - |
| `400` + `parse_request_failed` | `seconds` が数値でした | 文字列の `"4"` / `"6"` / `"8"` を使用してください |
| 4秒のみ / `... but got 4` | フィールド名が `duration` でした（通知なしで無視され、4秒にフォールバックします） | `seconds` を値 `"8"`（文字列）で使用してください |
| `INVALID_ARGUMENT` | 1080p/4Kで `generateAudio` または8秒以外を指定しました | `generateAudio` を削除し、HD/4Kには `seconds="8"` を設定してください |
| `401` | 無効な token | `Authorization: Bearer <key>` を確認し（余分な空白がないか）、キーがまだ有効であることを確認してください |
| `429` | レート制限 / 残高不足 | 指数バックオフでリトライ、チャージして再試行してください |
| `5xx` / `INTERNAL` | アップストリームの一時的なエラー | 同じシードで1〜2回リトライしてください（課金されません） |
| `GET /content` が400（`task status is IN_PROGRESS`）を返す | `status` が `completed` に切り替わった直後（最大約20秒間） | 最大約30秒間、4秒ごとにリトライしてください。curl には `-f --retry-all-errors` が必要です |
| `GET /content` が `502` を返す | プロバイダーがその動画ファイルを取得できません（現在は稀です。以下のFAQを参照） | **リトライしても解決しません**（数時間後でも502のままです）。`task_id` を控えてお問い合わせいただき、課金を確認してください。通常は新しいタスクとして再送信すれば機能します |
| タスク `failed` | 生成に失敗しました（通常はコンテンツ審査、アップストリームの容量不足、または生成されたファイルを取得できなかったことが原因です） | `error.message` を参照し、prompt を調整してリトライしてください。**タスクは課金されず、請求が発生した場合は自動的に返金されます** |

<Info>
  **推奨されるクライアント設定**:

  * POST送信タイムアウト: **30秒**（multipartアップロードではさらに時間が必要な場合があります）
  * ポーリング間隔: **8〜10秒**、最大待機時間 720p/1080p は **3分**、4K は **10分**
  * 5xx および `failed` に対する指数バックオフリトライ（1〜2回の試行を推奨）
  * `/content` から400が返された場合は、最大約30秒間、4秒ごとにリトライ
  * **`/content` からの `400` と `502` は区別して処理**: `400` はリトライで解消されますが、`502` は解消されません — 2回試行した後に停止し、タスクを失敗としてマークして `task_id` を保持してください
</Info>

  <Accordion title="length フィールドは秒数ですか、それとも duration ですか？なぜ文字列である必要があるのですか？">

    * クライアントタイムアウト：720p/1080p は 3分、4K は 10分
  </Accordion>

  <Accordion title="GET /content が 400 または 502 を返します — これらは全く異なる処理が必要です">
    **`400`：待つだけで解決します。** `status` が `completed` に切り替わった直後は、動画ファイルの同期がまだ完了していないため、`/v1/videos/{task_id}/content` を呼び出すと一時的に 400 が返されることがあります。このウィンドウは最大約20秒間続くため、**約30秒間、4秒ごとにリトライしてください**（サンプルのクライアントはすでにこの処理を行っています）。curl の場合、デフォルトでは `--retry` は 400 をリトライしない点に注意してください — `-f --retry-all-errors` を追加してください。

    **`502`：リトライしても解決しません。** レスポンスボディは `{"error":{"message":"Upstream service returned status 502"}}` のようになります。生成自体は成功しており — `GET /v1/videos/{task_id}` は引き続き `status: "completed"` と `progress: 100` を返します — しかし**プロバイダーがその動画ファイルを取得できません**。弊社の実測では数時間後も 502 のままであるため、**自動的に回復することはありません**。これを無制限のリトライループとして記述しないでください。

    対処法：

    1. 最大2回リトライします。それでも 502 の場合は、そのタスクを失敗としてマークします
    2. **`task_id` を控えてお問い合わせください** — その生成はすでに課金されているため、弊社側で確認して対応いたします
    3. 新しいタスクとして再送信すれば通常は動画が生成されます。prompt を変更する必要はありません

    **これは現在では稀です**：ほとんどのタスクは `completed` と報告される前に動画ファイルが取得可能かどうかがチェックされます。ファイルを取得できない場合、タスクは `status: "failed"`（理由は `error.message` に記載）となり、**料金は自動的に返金される**ため、取得できない動画に対して課金されることはなくなりました。ただし完全に排除できるわけではありません — **`GET /v1/videos/{task_id}` が `completed` を返すことは、動画が取得可能であることを意味しません。** これらは2つの独立した成功確認として扱ってください。
  </Accordion>

  <Accordion title="動画の直接URLを取得できますか？フロントエンドから直接エンドポイントを叩けますか？">
    **可能な場合もありますが、一時的なものにすぎません**。完了したレスポンスには `video_url`（認証不要の直接リンク）と `expires_at`（完了から約24時間後のタイムスタンプ）が含まれている**場合があります**。これは**すべてのタスクで保証されているわけではなく**、有効期限が切れると機能しなくなるため、恒久的なアドレスとして配布しないでください。

    **動画を取得する標準的な方法**：`status: "completed"` の後、`GET /v1/videos/{task_id}/content` を呼び出して **MP4 バイナリストリーム**を取得します（`Authorization: Bearer` ヘッダーが必要です）。これはすべてのタスクで機能します。

    **標準的な本番パターン**：

    1. タスク完了後すぐにバックエンドで MP4 をダウンロード → 独自の OSS / CDN にプッシュ
    2. エンドユーザーには自社の CDN URL を提供
    3. **フロントエンドの `<video>` タグは `/content` を直接参照してはいけません** — ブラウザは認証ヘッダーを含めることができず、リクエストは 401 になります。`video_url` が存在する場合は、即時プレビュー用に使用できます
  </Accordion>

  <Accordion title="動画はサーバーにどのくらいの期間保持されますか？すぐにダウンロードする必要がありますか？">
    レスポンスの `expires_at` フィールドによると**約24時間**です（このフィールドがない場合は24時間と想定してください）。**完了後すぐにダウンロードしてローカルに保存することを強く推奨します** — リモートの `task_id` や `video_url` に長期的に依存しないでください。期限切れ後はどちらも利用できなくなります。
  </Accordion>

  <Accordion title="進捗状況（progress）が飛ぶのはなぜですか？">
    `progress` フィールドは大まかな粒度となっており、**いくつかの固定ステップ間でのみジャンプします**（0 / 10 / 30 / 50 / 100 など）。パーセンテージのプログレスバーには使用しないでください。スピナーを使用するか、ご自身で「経過時間 / 想定時間」を計算してください。
  </Accordion>

  <Accordion title="失敗した生成には課金されますか？">
    **いいえ**。**課金されるのは `status=completed` のタスクのみです**。`failed` / キャンセル / コンテンツポリシー違反による拒否 / パラメータエラーはすべて無料です。**実際の動画が出力されなければ課金されません**。
  </Accordion>

  <Accordion title="seed でまったく同一の動画を再現できますか？">
    **バイト単位で同一にはなりません**。実測値：同一の prompt ＋ 同一の seed（`88888`）＋ 同一のパラメータで fast を2回実行した場合 — ファイルサイズは 9.81 MB vs 9.25 MB、md5 は完全に異なり、レンダリング時間も異なります。

    **ただし seed は無意味ではありません**：同一 seed の出力は**まとまった傾向を示し**（5回実行テストでグループ内ファイルサイズのばらつきはわずか6%）、異なる seed では**体系的に変化します**（グループ間のばらつき +36.8%）。つまり：

    * 「安定したルック」が欲しい場合 → seed を固定
    * 「バリエーションを探索」したい場合 → prompt をいじるのではなく seed を変更
    * 「完全な再現」が欲しい場合 → あきらめて mp4 を保存
  </Accordion>

  <Accordion title="複数の参照画像を渡せますか？最初/最後のフレームは使えますか？">
    **現時点ではどちらもサポートされていません**。画像・動画生成（Image-to-video）は1枚の画像のみを受け付け、フィールド名は `input_reference` に固定されており、**ファイルまたは Base64 のみで、リモート URL には対応していません**。

    Google 上流の Veo 3.1 は複数参照 / 最初と最後のフレーム / 動画の延長をサポートしていますが、このチャンネルでは対応していません。**最初/最後のフレームを使用する場合は、[VEO 3.1 (リバース)](/en/api-capabilities/veo/overview) の `-fl` シリーズをご利用ください**。
  </Accordion>

  <Accordion title="同時実行数の制限は？QPS の上限はありますか？">
    10件の同時送信の実測では、すべてキューに入り成功し、拒否はありませんでした。正確な上限は公表されていません。**本番環境側では処理中のタスク（in-flight）を 10 以下に制限し**、429 / 5xx が発生した場合は指数バックオフを行うことを推奨します。
  </Accordion>

  <Accordion title="動画に透かし（ウォーターマーク）や出所のメタデータは含まれますか？">
    * 目に見えるウォーターマークはありません
    * ただし、MP4 のメタデータ内に埋め込まれた **Google C2PA コンテンツクレデンシャル**（Google C2PA Media Services 発行、フォーマット `urn:c2pa:...`）が含まれています。エンドユーザーには見えませんが、**C2PA ツール（例：Adobe Content Authenticity）により「Veo によって生成された」ことを検証できます**
    * 再配布シナリオではご注意ください。通常、動画の再生には影響しません
  </Accordion>

  <Accordion title="公式の OpenAI SDK を直接使用できますか？">
    部分的に可能です。インターフェースは OpenAI の規約（`Bearer` 認証 ＋ `/v1/...`）に従っていますが、OpenAI 公式 SDK には **`videos.create` メソッドが公開されていません**（`/v1/videos` はカスタムパスです）。OpenAI SDK の低レベルな `client.post()` または直接の HTTP を使用してください。**生の HTTP が最もシンプルです** — [Text-to-Video Playground](/ja/api-capabilities/veo-3-1-official/text-to-video) のコードサンプルをご覧ください。
  </Accordion>
</AccordionGroup>
