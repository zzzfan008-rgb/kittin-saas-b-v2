# Что нужно знать о настройках часового пояса в логах и экспорте данных?

> Установите часовой пояс аккаунта в соответствии с вашим местоположением (Asia/Shanghai для пользователей из Китая) и при необходимости примите предложение консоли о переключении часового пояса. Подробный список логов, график «Обзор данных вызовов», экспорт и «Сводка по тарификации» используют часовой пояс аккаунта, поэтому их данные согласованы между собой; только API запроса логов возвращает временные метки Unix.

<Info>
  **Смещение на графике было исправлено 2026/9/20 в 00:55 (UTC+8).** Ранее, когда часовой пояс аккаунта отличался от UTC, график 调用数据一览 (Обзор данных вызовов) в верхней части страницы «Логи» относил данные не к тому дню (например, столбец следующего дня появлялся во второй половине дня по пекинскому времени). Именно поэтому ранее мы рекомендовали оставаться на UTC+0 и закрывать диалоговое окно. Проблема устранена, и **эта рекомендация отозвана** — пожалуйста, выберите свой часовой пояс.
</Info>

### Смещение исторических данных

До этого исправления часовой пояс базы данных по умолчанию был UTC+8. В сочетании с выбранным пользователем часовым поясом Шанхая (UTC+8) это приводило к смещению данных на графике. Теперь часовой пояс базы данных по умолчанию изменен на UTC+0, поэтому график соответствует выбранному пользователем часовому поясу без дальнейших смещений.

Что затронуто: графики и Сводка по тарификации с группировкой по дням / часам **до 2026/9/20 00:55 (UTC+8)** могут иметь 8-часовое смещение даты. Общая сумма не затронута, а детализированные записи по отдельным вызовам не затронуты. Для сверки на уровне дней выполните экспорт заново.

Если вам необходимо сверить исторические данные, вы также можете получить записи по каждому вызову через [API запроса логов](/ru/api-capabilities/log-query) и агрегировать их самостоятельно; это надежнее, чем полагаться на сводные файлы, созданные до исправления.

<Tip>
  **Правило одной строкой**: всё, что вы **видите или экспортируете в консоли** (список детализации, график, файлы экспорта, Сводка по тарификации), использует **часовой пояс аккаунта**; то, что вы **получаете программным путем** (`created_at` через [API запроса логов](/ru/api-capabilities/log-query)), представляет собой **Unix-таймстемп в секундах**, не зависящий ни от какого часового пояса.
</Tip>

## Где проверить и изменить часовой пояс аккаунта

Часовой пояс аккаунта отображается и редактируется в разделе консоли 用户信息 (Информация о пользователе). Для новых аккаунтов по умолчанию установлен `UTC`; пользователям из Китая следует переключиться на `Asia/Shanghai`.

<Frame caption="The timezone setting in the console's User Info section — change it from the dropdown">
  <img src="https://mintcdn.com/apiyillc/ixJpriVUjc22GEKJ/images/console-user-info-timezone.png?fit=max&auto=format&n=ixJpriVUjc22GEKJ&q=85&s=94b725d2393ee1ff84eda7b4c1360743" alt="Настройка часового пояса в разделе консоли «Информация о пользователе»" width="892" height="332" data-path="images/console-user-info-timezone.png" />

Смена часового пояса **изменяет только отображение и группировку времени**. Ни одна запись вызова или списания не изменяется и не теряется, и вы можете в любой момент переключить его обратно.

## Примите переключение при появлении диалогового окна с предложением

Когда часовой пояс вашего аккаунта (например, `UTC`) отличается от текущего часового пояса вашего устройства (например, `Asia/Shanghai`), консоль открывает диалоговое окно «本地设置建议» (Рекомендация по локальным настройкам). **Просто нажмите кнопку переключения справа.** После этого список с подробными данными и график будут отображать пекинское время.

Если ваша финансовая служба выполняет сверку строго в UTC, вы можете закрыть диалоговое окно и остаться в UTC. Оба варианта теперь отображаются корректно, поэтому выберите тот, который подходит для вашего процесса сверки.

График «调用数据一览» (Обзор данных вызовов) в верхней части страницы Logs группирует данные по календарным дням в часовом поясе аккаунта:

## Какой экспорт выбрать?

На странице логов в правом верхнем углу находятся две кнопки: 导出 (Export) и 汇总账单 (Billing Summary).

<Frame caption="The Export and Billing Summary buttons in the top-right corner of the Logs page">
  <img src="https://mintcdn.com/apiyillc/ixJpriVUjc22GEKJ/images/console-log-export-buttons.png?fit=max&auto=format&n=ixJpriVUjc22GEKJ&q=85&s=d8f2d7b0359ddcf6aebdd66399bfcffe" alt="Панель инструментов страницы логов с кнопкой Export слева и кнопкой Billing Summary справа" width="650" height="212" data-path="images/console-log-export-buttons.png" />
</Frame>

| | 导出 (Export) | 汇总账单 (Billing Summary) |
| - | - | - |
| Базовый часовой пояс | **Часовой пояс аккаунта** | **Часовой пояс аккаунта** |
| Детализация | Отдельные записи вызовов (настраиваемые поля) | Расходы, агрегированные по часам, дням или месяцам |
| Объем данных | Большие объемы, может выполняться асинхронно | Небольшой, скачивается напрямую |
| Оптимально для | Сверка, аудит, пользовательский анализ | Быстрый просмотр общих расходов, налоговая отчетность |

Обе кнопки используют один и тот же базовый часовой пояс и различаются только детализацией и объемом данных. Выбирайте вариант, соответствующий вашим потребностям — отдельные записи или агрегированные итоги.

Например, если в аккаунте установлен часовой пояс `Asia/Shanghai`, то для вызова, совершенного в **2026-09-20 01:08 (UTC+8)**:

* отображается `2026-09-20 01:08` в **подробном списке на странице**
* также отображается `2026/9/20 1:08` в **файле экспорта**
* относится к `2026-09-20` в **Billing Summary** (по дням) и к 20 сентября на графике

<Tip>
  **Первые 14 цифр request ID — это время UTC.** Например, `20260919170811…` означает `2026-09-19 17:08:11` UTC, то есть `2026-09-20 01:08:11 (UTC+8)`. При проверке конкретного вызова со службой поддержки request ID является наиболее точным ориентиром.
</Tip>

### Экспорт → фоновый асинхронный экспорт (рекомендуется)

Если вам нужны построчные записи расходов, нажмите кнопку 导出 (Export) и выберите в диалоговом окне **后台异步导出 (background async export)**.

<Frame caption="The export dialog — select background async export for large volumes">
  <img src="https://mintcdn.com/apiyillc/ixJpriVUjc22GEKJ/images/console-log-async-export-dialog.png?fit=max&auto=format&n=ixJpriVUjc22GEKJ&q=85&s=09865097dc2f80581a82e2d7feb06f3c" alt="Диалоговое окно экспорта с выбором полей, вариантами экспорта текущей страницы или фонового асинхронного экспорта, форматами Excel и CSV, а также максимальным количеством записей" width="974" height="1312" data-path="images/console-log-async-export-dialog.png" />
</Frame>

Ключевые моменты:

* **Время указывается в часовом поясе аккаунта**, полностью совпадая с подробным списком на странице
* **Настраиваемые поля**: время использования, request ID, имя token, название модели и другие — выбирайте то, что требуется для вашей сверки
* **Режим экспорта**: для больших объемов выбирайте фоновый асинхронный экспорт; задача выполняется в фоновом режиме, не блокируя страницу, и рекомендуется при объеме более 10 000 записей
* **Формат**: Excel (`.xlsx`, файлы очень большого объема автоматически разбиваются на части и упаковываются в архив) или CSV (`.csv`, для небольших объемов)
* **Максимальное количество записей**: `0` означает без ограничений (сервер разделит данные на несколько файлов Excel и заархивирует их), с верхним лимитом в 50 миллионов записей
* **Ход выполнения**: после создания задачи отслеживайте ее прогресс и статус на странице 任务管理 (Task Management), а затем скачайте готовый файл

Подробное пошаговое руководство по экспорту и рекомендации по архивации см. в разделе [Сколько времени хранятся логи вызовов?](/ru/faq/log-retention-policy).

## Сверка на практике

<Steps>
  <Step title="Убедитесь, что обе стороны используют один и тот же часовой пояс">
    Файлы экспорта группируют даты по **часовому поясу экспортирующего аккаунта**. Когда сверку проводят несколько человек или когда вы сопоставляете данные с финансовой системой, сначала убедитесь, что все используют один и тот же часовой пояс (например, `Asia/Shanghai`); иначе вызовы, сделанные около полуночи, попадут на разные даты.
  </Step>

  <Step title="Самостоятельно конвертируйте временные метки API">
    `created_at` из [API запроса логов](/ru/api-capabilities/log-query) — это временная метка Unix в секундах; конвертируйте её в нужный вам часовой пояс. Для пекинского времени прибавьте **28800** (8 × 3600) и отформатируйте как UTC либо используйте библиотеку для работы с часовыми поясами вашего языка.
  </Step>

  <Step title="Указывайте ID запроса и часовой пояс при сообщении о проблеме">
    ID запроса содержит время UTC и является наименее подверженным ошибкам ориентиром; указывая время, всегда сообщайте часовой пояс, например `01:08 (UTC+8)`.
  </Step>
</Steps>

<Tip>
  Для задач сверки или аудита, требующих разбивки по *рабочим дням*, вы также можете использовать [API запроса логов](/ru/api-capabilities/log-query) с собственным скриптом, что дает больше контроля, чем файлы экспорта.
</Tip>

## Частые вопросы

<AccordionGroup>
  <Accordion title="Раньше в документации рекомендовалось оставаться в UTC+0 и закрывать диалоговое окно — нужно ли это по-прежнему?">
    Нет. Эта рекомендация была связана с тем, что на графике данные отображались не за тот день, если часовой пояс аккаунта отличался от UTC. Проблема была устранена 2026/9/20 00:55 (UTC+8). Теперь вы можете выбрать свой часовой пояс.
  </Accordion>

  <Accordion title="Я оставил UTC, как рекомендовалось, — стоит ли переключиться на пекинское время?">
    Мы рекомендуем переключиться на `Asia/Shanghai`, чтобы всё время в консоли отображалось по пекинскому времени и вам больше не приходилось прибавлять 8 часов вручную. Если ваш процесс сверки привязан к UTC, остаться на UTC тоже можно — теперь оба варианта отображаются корректно.
  </Accordion>

  <Accordion title="Приведет ли смена часового пояса к потере данных?">
    Нет. Часовой пояс влияет только на отображение времени и группировку по датам. Ни записи вызовов, ни списания не изменяются, и вы можете переключиться обратно в любой момент.
  </Accordion>

  <Accordion title="Точны ли файлы, экспортированные до исправления?">
    Каждая запись и сумма в построчном экспорте (кнопка «Экспорт») точны, а время указано в часовом поясе аккаунта на тот момент. Для файлов сводки по тарификации и данных графиков **до 2026/9/20 00:55 (UTC+8)** **группировка по дням или часам** может быть смещена на 8 часов, тогда как итоговые суммы не затронуты. Если вам требуется точная подневная сверка, выполните экспорт повторно.
  </Accordion>

  <Accordion title="Почему время на моей странице не совпадает со временем в экспорте коллеги?">
    Скорее всего, часовые пояса ваших аккаунтов различаются. В экспортируемых файлах используется часовой пояс учетной записи, выполнившей экспорт, — убедитесь в разделе «Информация о пользователе» (User Info), что в обоих аккаунтах выбран один и тот же часовой пояс.
  </Accordion>

  <Accordion title="Может ли Log Query API принимать параметр часового пояса?">
    Нет. API принимает и возвращает только временные метки Unix в секундах, которые по определению представлены в UTC. При необходимости выполняйте преобразование на стороне клиента.
  </Accordion>

  <Accordion title="Содержат ли экспортируемые файлы мои входные и выходные данные?">
    Нет. Экспортируемые поля соответствуют тому, что отображается в консоли: время, ID запроса, имя token, модель, количество tokens, сумма, статус — без prompt или выходных данных модели. См. [Сколько хранятся журналы вызовов?](/ru/faq/log-retention-policy).
  </Accordion>

  <Accordion title="Можно ли получать журналы программно вместо экспорта со страницы?">
    Да, см. [Log Query API](/ru/api-capabilities/log-query). Его параметры `start_timestamp`, `end_timestamp` и `created_at` представляют собой **временные метки Unix в секундах** и не зависят от настроек часового пояса в консоли, что отлично подходит для автоматической сверки.
  </Accordion>

  <Accordion title="Моя задача экспорта не завершается — что делать?">
    Сначала проверьте статус задачи на странице 任务管理 (Управление задачами). Для очень больших объемов (миллионы записей) серверу требуется время на разбиение и упаковку файлов; сузьте временной диапазон или установите разумное максимальное количество записей и экспортируйте данные частями.
  </Accordion>
</AccordionGroup>
