# GPT-Image-2-All Генерация/редактирование изображений

> Реверс-инжиниринговая модель генерации изображений GPT gpt-image-2-all (линейка веб-версии ChatGPT). Фиксированная тарификация $0.03/изображение за вызов, генерация примерно за 30–60 с. Поддерживает преобразование текста в изображение, редактирование с объединением нескольких изображений, редактирование на естественном языке, высокую точность рендеринга текста, удобна для prompt на китайском.

<Info>
  Все API генерации изображений являются **синхронными** — здесь нет task ID для опроса, и если ваш клиент отключится, результат будет потерян, хотя запрос все равно тарифицируется. Установите для этой модели увеличенный timeout; см. [Основы и лучшие практики Image API](/ru/api-capabilities/image-api-best-practices).
</Info>

## Обзор

**gpt-image-2-all** — это **обратно-инженеренная модель генерации изображений GPT** (линейка веб-версии ChatGPT), доступная на платформе APIYI. При чрезвычайно конкурентной цене **\$0.03/image** за запрос она генерирует изображения примерно за **30–60 секунд** и поддерживает **text-to-image / редактирование одного изображения / слияние нескольких изображений / редактирование на естественном языке** — с высокой точностью рендеринга текста и нативной поддержкой китайских prompt.

<Note>
  **🎨 Основные моменты**: Надежный обратнo-инженеренный канал с фиксированной ставкой \$0.03/image. Не нужно беспокоиться о параметрах size/quality/n — просто опишите размер и стиль в prompt. Использует стандартные эндпоинты OpenAI Images API: `/v1/images/generations` (text-to-image) и `/v1/images/edits` (image editing).

  **Нужно зафиксировать размер вывода или 4K?** Переключитесь на сестринскую модель [`gpt-image-2-vip`](/ru/api-capabilities/gpt-image-2-vip/overview) — тот же формат вызова, только одно дополнительное поле `size`.
</Note>

Для более детальной информации о параметрах добавьте `.md` к страницам text-to-image и image-edit таким же способом.

  Требования:

  1. Тайм-аут: увеличьте тайм-аут клиента до 360 секунд. Image APIs синхронные — идентификатора задачи нет, поэтому если клиент отключится, результат будет потерян, хотя запрос все равно тарифицируется. Лучше дождаться результата, чем завершить по тайм-ауту слишком рано. Обратным прокси, шлюзам и лимитам выполнения serverless тоже нужно увеличить значения: любой слой, время которого меньше времени генерации, оборвет запрос.

  2. Отображение ответа: по умолчанию используется base64 (`b64_json`, без префикса `data:`); можно также передать `response_format`, установив url, чтобы получить вместо этого ссылку на CDN. **Всегда явно указывайте `response_format`, а не полагайтесь на значение по умолчанию** — поведение по умолчанию в прошлом менялось в зависимости от group и нагрузки. Если вы получаете base64, отрендерите его и предложите действие сохранения на диск; если вы получаете URL, учтите, что он истекает примерно через 24 часа, поэтому скачайте и сразу заново разместите его на стороне сервера. Каждый элемент в `data[]` содержит только одно из двух полей, поэтому обрабатывайте оба варианта с защитой.

  3. Сжимайте перед загрузкой: перед вызовом `/v1/images/edits` (multipart) сжимайте каждое референсное изображение — обрабатывайте только файлы больше 1.5MB, уменьшайте длинную сторону до 2048px с сохранением пропорций (никогда не увеличивайте маленькое изображение), повторно кодируйте с качеством 0.9 и сохраняйте исходный формат. Держите общий размер ниже 6MB для запросов с несколькими изображениями, и ни одно отдельное изображение не должно быть больше 10MB. Если одно изображение не удалось сжать, вернитесь к исходному файлу и продолжайте — никогда не прерывайте весь запрос из-за сбоя сжатия.

  4. Жесткие ограничения по параметрам: эта модель **не** принимает `size`, `quality`, `n` или `aspect_ratio`. Ни один из них не отправляйте. Особенно две ловушки: если отправить `n` со значением 3, с вас спишут за 3 изображения, но вернется только 1; а метод `client.images.generate()` в OpenAI SDK по умолчанию отправляет `size` и `n`, поэтому **безопаснее здесь отправлять raw HTTP request**. Размеры вывода задаются префиксом prompt вместо этого (например, если начинать prompt с указания на альбомную ориентацию 16:9). На этой странице есть проверенная таблица соответствия prompt и разрешения — следуйте ей.

  5. Возьмите ключ из переменной окружения `APIYI_API_KEY` и используйте [https://api.apiyi.com/v1](https://api.apiyi.com/v1) как базовый URL. Никогда не зашивайте его в код и никогда не коммитьте его в git.

  6. Когда закончите, действительно выполните один вызов text-to-image и один вызов image-edit, затем покажите мне результаты и сколько стоили эти два вызова.

## Настройка группы

`gpt-image-2-all` находится в группе `Default` — **дополнительная группа не нужна**. В reverse-канале сейчас стабильное наличие, поэтому здесь нет сценария запасного перехода на enterprise-группу, как у official-relay `gpt-image-2`.

| Модель            | Группа       | Примечания                                                                                                                                        |
| ----------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `gpt-image-2-all` | `Default`    | ChatGPT-web, обратный канал, фикс. \$0.03/img, \~30–60 с                                                                                          |
| `gpt-image-2-all` | `image2_OSS` | **коэффициент тарифа 1x (без надбавки)**, детерминированный вывод URL — никогда не откатывается к base64, когда группа по умолчанию под нагрузкой |

### Нужен детерминированный вывод URL → переключитесь на группу `image2_OSS`

По измерениям в июле 2026 года в группе по умолчанию `gpt-image-2-all` (и `gpt-image-2-vip`) возвращают `b64_json`, когда `response_format` опущен; передайте `response_format: "url"` явно, чтобы получить URL изображения. Формат вывода группы по умолчанию **не гарантирован** — исторически он по умолчанию использовал `url` с откатом к `b64_json` при нагрузке и менялся между версиями канала.

Если ваш бизнес **зависит от вывода URL** (сохранение URL напрямую в вашу базу данных, frontend-рендеринг по URL, base64 не подходит), переключите группу вашего token на **`image2_OSS`** — группу, специально созданную для **детерминированного вывода URL**, с **коэффициентом тарифа 1x (без надбавки)**, которая действует для обеих reverse-моделей `gpt-image-2-all` и `gpt-image-2-vip`. Она гарантирует, что ответ всегда содержит URL изображения и никогда не откатывается к base64.

| **Дополнительный формат**      | `url` (ускоренная ссылка через R2 CDN, **срок действия \~1 день**, требуется явный `response_format: "url"`)               |

Для строго зафиксированных размеров вывода или 4K используйте [`gpt-image-2-vip`](/ru/api-capabilities/gpt-image-2-vip/overview) (реверс-версия Codex, 30 явных размеров, включая 4K). Для полного соответствия официальному API используйте [`gpt-image-2`](/ru/api-capabilities/gpt-image-2/overview).
</Warning>

<Warning>
  **⏰ Срок действия URL изображения: \~1 день (по умолчанию)**

  Поле `url` ответа в режиме `url` — это ссылка R2 CDN, которая **истекает примерно через 24 часа** — после этого запросы будут возвращать 404. Для изображений, которые нужно хранить долгое время (товарные фото, пользовательские работы, архивные записи и т. д.), **скачайте и сохраните их в своем хранилище как можно скорее** после генерации.

  Два распространенных подхода:

  * **Скачивание на стороне сервера**: сразу после получения ответа используйте `requests` / `fetch`, чтобы загрузить изображение и сохранить его в S3 / OSS / R2 / на локальный диск
  * **Используйте формат ответа `b64_json`**: вы получаете изображение сразу в виде base64-данных, без дополнительной cross-origin-загрузки — идеально для рендеринга на фронтенде или прямой записи в файл
</Warning>

<Tip>
  **Используйте OpenAI Images API** (`/v1/images/generations` + `/v1/images/edits`), по двум причинам:

  1. **Более стабильно**: upstream-ресурсов для канала Images API больше, поэтому вероятность успешного вызова выше
  2. **Совместимо с официальным релеем для удобного переключения**: способ вызова и такие параметры, как `size`, полностью совместимы с official-relay [`gpt-image-2`](/ru/api-capabilities/gpt-image-2/overview) — если на обратном канале возникают проблемы с риск-контролем, **просто замените имя `model`** без каких-либо изменений в коде

  Также есть эндпоинт на основе chat (`/v1/chat/completions`, больше не рекомендуется) — см. FAQ ниже.
</Tip>

<Tip>
  **Варианты домена**: `api.apiyi.com` — основной домен. Вы также можете использовать альтернативные домены шлюза, такие как `b.apiyi.com` / `vip.apiyi.com`. Поведение ответов одинаковое.
</Tip>

## Управление размером и соотношением сторон (описывайте в prompt)

`gpt-image-2-all` не имеет параметра `size` — размер задается в prompt. Если вам нужны строго фиксированные размеры вывода (hero-изображения для e-commerce, шаблоны постеров, обои 4K), используйте [`gpt-image-2-vip`](/ru/api-capabilities/gpt-image-2-vip/overview) вместо этого.

## Коды ошибок и повторные попытки

| Статус  | Значение                                                                              | Рекомендация                                          |
| ------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `401`   | Недействительный token                                                                | Проверьте Bearer Token                                |
| `429`   | Лимит запросов / квота исчерпаны                                                      | Повторная попытка с экспоненциальной задержкой        |

  * Используйте **экспоненциальную задержку** для 5xx и таймаутов (рекомендуется 2–3 повторные попытки)

  <Accordion title="Если контент отклонён или модель отвечает «Я не могу этого сделать», тарифицируется ли это?">
    Это реверс-инженерный канал, использующий **синхронные ответы в стиле chat**. Результаты делятся на два случая с **разными правилами тарификации**:

    **1) Возвращён HTTP 5xx → НЕ тарифицируется**

    Когда upstream жёстко блокирует запрос по политике контента, вы увидите примерно такое:

    ```json theme={null}
    {
      "error": {
        "message": "Image was not generated as expected. Please adjust the prompt and retry (traceid: 0672821c6951af183dbf847130caaf16)",
        "localized_message": "Unknown error",
        "type": "invalid_request_error",
        "param": "",
        "code": null
      }
    }
    ```

    Эти жёсткие ошибки **не тарифицируются**. Попросите пользователя скорректировать prompt и повторить попытку.

    **2) HTTP 200 с текстовым «мягким отказом» → ТАРИФИЦИРУЕТСЯ**

    Когда модель мягко отказывает внутри диалога (например, «Я не могу этого сделать», «Извините, этот запрос затрагивает…»), на уровне протокола это выглядит как обычный chat completion, поэтому **это тарифицируется**. Реверс-канал не может надёжно отличить «текст отказа» от «вывода изображения» на уровне протокола.

    **Почему мы не можем просто отменять мягкие отказы**

    Автоматическая отмена каждого мягкого отказа означала бы, что платформа берёт на себя каждый неудачный upstream-вызов. Что ещё важнее, **частое срабатывание upstream-защиты контента также повышает риск блокировки аккаунта у поставщика** — это реальная издержка со стороны поставки, которую мы не можем полностью устранить.

    **Рекомендации для интеграторов**

    * ✅ **Предварительно фильтруйте и предупреждайте пользователей**: добавьте фильтр по ключевым словам/сценариям на фронтенде или шлюзе (имена реальных людей, защищённые авторским правом персонажи, чувствительные темы) и выводите подсказку в интерфейсе вроде «Темы со знаменитостями / IP могут не пройти и всё равно быть тарифицированы по политике upstream». Это резко сокращает лишние списания.
    * ✅ **Ежемесячная компенсация для consumer-продуктов**: мы понимаем, что consumer-facing продуктам невозможно полностью ограничить пользовательский ввод. Если ваши ежемесячные расходы достаточно велики (**\$1000+/месяц**), вы можете **ежемесячно пакетировать логи** (запросы с низкой задержкой обычно являются мягкими отказами) и обратиться в поддержку за разовой ручной компенсацией — не нужно подавать обращение по каждому вызову.

    📖 Связано: [Ошибки 500 обычно связаны с политикой контента (не тарифицируются)](/en/live/2026-04/gpt-image-2-all-500-content-policy)

    **Два рекомендуемых подхода**:

    * **Прокси на стороне сервера**: сразу `requests.get(url)` после ответа, сохраняйте в своё хранилище и возвращайте на фронтенд собственный URL;
    * **Используйте `b64_json`**: добавьте `"response_format": "b64_json"` в запрос, чтобы получить base64-данные изображения напрямую — на одну кросс-доменную загрузку меньше, идеально для рендеринга на фронтенде или записи сразу в файл.

  <Accordion title="Можно ли по-прежнему генерировать изображения через /v1/chat/completions?">
    Да, endpoint по-прежнему работает, но **больше не рекомендуется** — вместо этого используйте `/v1/images/generations` и `/v1/images/edits` (так стабильнее, и тот же код работает с `gpt-image-2` официального релея).

    Формат на основе chat имеет смысл только в двух сценариях: многоходовое итеративное редактирование или передача онлайн-URL изображений напрямую. Учтите, что если намерение изображения неоднозначно, модель может вернуть обычный текст вместо изображения (добавьте к prompt фиксированный префикс вроде «Сгенерируйте изображение:», чтобы усилить намерение).

    Полный список параметров см. в [справке по API на основе chat](/en/api-capabilities/gpt-image-2-all/chat-completions).
  </Accordion>
</AccordionGroup>
