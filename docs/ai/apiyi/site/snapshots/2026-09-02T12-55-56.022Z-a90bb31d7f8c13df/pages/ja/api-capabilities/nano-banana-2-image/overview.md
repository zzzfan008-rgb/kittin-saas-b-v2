<Prompt description="コーディングエージェントに Nano Banana 2 のテキストから画像生成と画像編集を統合またはトラブルシューティングさせます。Codex、Claude Code、Cursor などのツールにコピー＆ペーストしてください。" icon="bot" actions={["copy"]}>
  このプロジェクトで Nano Banana 2（`gemini-3.1-flash-image`）のテキストから画像生成と画像編集を統合またはトラブルシューティングしてください。

  コードに触る前にドキュメントを読んでください: このページのプレーンテキスト版を取得するため、[https://docs.apiyi.com/en/api-capabilities/nano-banana-2-image/overview.md](https://docs.apiyi.com/en/api-capabilities/nano-banana-2-image/overview.md) を取得してください。より細かなパラメータの詳細については、テキストから画像生成ページと画像編集ページにも同じように `.md` を付けてください。

  要件:

  1. タイムアウト: `POST https://api.apiyi.com/v1beta/models/gemini-3.1-flash-image:generateContent` の Gemini ネイティブ形式を呼び出し、クライアントのタイムアウトを 360 秒に引き上げてください。画像 API は同期処理なので task ID はありません。そのため、クライアントが切断されると、リクエストの課金が継続していても結果は失われます。リバースプロキシ、ゲートウェイ、サーバーレス実行制限もすべて広げる必要があります。生成時間より短い層が1つでもあれば、リクエストは途中で切断されます。Node では、undici に 3 つの独立したタイムアウト設定があり、SDK の `timeout` オプションではそれらをカバーできない点に注意してください。

  2. レスポンスのパース（**最も簡単に間違えやすい点です**）: 画像は base64 で、`inlineData.data` の `candidates[0].content.parts[]` 内にあります。ただし、`parts` は長さと順序が保証されない**異種混在の配列**です。テキスト部分が先に来ることがあり、その場合は画像が 0 ではなく 1 番目のインデックスになります。このモデルは推論テキストを返せるため、特にその傾向があります。したがって、`parts[0]` や `parts[1]` を絶対にハードコードしないでください。2つの間で切り替えても解決しません。正しい方法は、`parts` を走査し、`inlineData` を持つすべてのエントリをフィルタし、**最後**のものを採用することです（複雑なタスクでは途中の下書きが複数返り、最後のものだけが最終版です）。`mimeType` も、`image/png` を前提にせずレスポンスから読み取ってください。その後、画像を表示し、ディスクに保存する操作を用意してください。

  3. アップロード前に圧縮する: 編集では、参照画像を `inlineData` 内の base64 として渡します。まず圧縮してください。1.5MB を超えるファイルだけを処理し、アスペクト比を保ったまま長辺を 2048px に縮小し（小さい画像は絶対に拡大しない）、品質 0.9 で再エンコードし、元の形式を維持します。複数画像リクエストでは、合計サイズを 6MB 未満にしてください。ハード制限は 画像1枚あたり 7MB、1リクエストあたり最大 14 枚です。そこに base64 変換が加わると約3分の1ほど膨らむため、余裕を持たせるなら各画像を 5MB 未満に収めることを目指してください。1枚の画像の圧縮に失敗した場合は、元のファイルにフォールバックして処理を続けてください。また、**1つの part には `text` か `inlineData` のどちらか一方だけが入ります。両方は入りません**。正しい構造は、テキストパート 1 つと画像パート N 個です。

  4. 解像度パラメータ: **必ず送信する** `generationConfig.imageConfig.imageSize`（`512` / `1K` / `2K` / `4K`、デフォルト `1K`）と `aspectRatio`（このページには 14 個の有効なアスペクト比が載っています）です。従量課金では**解像度が単価を直接決める**ため、デフォルトに頼るとコストが予測しづらくなります。UI では両方ともドロップダウンとして公開してください。また、コードではモデル名は必ず `gemini-3.1-flash-image` を使い、**`-4k` サフィックス付きの変種は使わないでください**（そちらはチャットクライアント向けです）。4K にするには、`imageSize` を適切に設定するだけで十分です。このモデルは `tools` 経由の Google Search グラウンディングをサポートしていないため、送信しないでください。

  5. エラーハンドリング: コンテンツモデレーションがリクエストをブロックした場合でも HTTP ステータスは 200 のままですが、`candidates[0].content.parts` は空で返ります。まず `candidatesTokenCount` が 0 かどうかを確認し、次に `finishReason` が `STOP` 以外かどうかを確認してください。`IMAGE_SAFETY` のようなブロックは**課金されません**し、同一入力を1回か2回再試行すると成功することがよくあります。自動リトライを組み込んでください。

  6. キーは `APIYI_API_KEY` 環境変数から読み取り、`Authorization` ヘッダーに `Bearer` プレフィックス付きで送信してください。絶対にハードコードせず、git にコミットしないでください。

  7. 作業が終わったら、実際にテキストから画像生成を1回と画像編集を1回実行し、その結果とその2つの呼び出しにかかった費用を見せてください。
</Prompt>

## 課金に影響する3つのパラメータ

以下の数値は、2026-08-27 に本番ゲートウェイに対して実施したライブテストに基づきます（各条件12～20回実行、いずれも推定ではなくコンソールに記録された実際の課金額に基づいています）。これらが課金に与える影響は2桁違うため、示した順に最適化してください。

| パラメータ                          | 1回あたりの影響                                | 調整する価値はある？   |
| ------------------------------ | --------------------------------------- | ------------ |
| `imageConfig.imageSize`        | 1K \$0.033 → 4K \$0.064、**+90%**        | ✅ 最大の打ち手     |
| `thinkingConfig.thinkingLevel` | デフォルト \$0.033 → `high` \$0.052、**+54%** | ✅ 必要なときだけ有効化 |
| `responseModalities`           | −2.8%、統計的に有意ではありません                     | ❌ 何も節約できません  |

### thinkingLevel: デフォルトはすでに最小で、high はさらに50％増しです

`gemini-3.1-flash-image` は thinking-level の制御をサポートします（Pro にはありません）。同じ prompt を使い、それぞれ20回実行しました。

| 設定        | 出力 tokens 平均 | `thoughtsTokenCount` | 1回あたりの課金     | レイテンシ中央値 |
| --------- | ------------ | -------------------- | ------------ | -------- |
| 省略（デフォルト） | 1548.7       | フィールドなし              | \$0.0335     | 13.3s    |
| `minimal` | 1546.0       | フィールドなし              | \$0.0334     | 13.6s    |
| `high`    | 1557.5       | 中央値 784.5            | **\$0.0516** | 20.7s    |

* **デフォルトは `minimal` と同一です** — 統計的に区別できず（p=0.64）、`minimal` を明示的に渡しても何も得られません。
* `high` のときだけ `thoughtsTokenCount` が独立したフィールドとして現れ、`completion_tokens` に折り込まれて画像生成レートで課金されます。
* **複雑な prompt でコストが上がるのは `high` がオンのときだけです**: デフォルトレベルでは、3-token の prompt と 98-token の reasoning prompt で出力 tokens に有意差はありませんでした（p=0.37）。`high` では、reasoning prompt が thinking tokens を **126% 多く**使い、1回あたりの課金は **38% 増** でした。

<Tip>
  日常的な生成ではこのパラメータはそのままにしてください。`high` を有効にするのは、構図ロジック、画像内テキストのレイアウト、またはチャートの比率精度に厳しい要件がある場合だけです。その代わり、支出は+54%、レイテンシは+55% になります。
</Tip>

### Google Search グラウンディング: 動作しますが、検索クエリごとに課金されます

天気カード、マーケットチャート、イベントポスターのように、正確さのために最新情報が必要な画像には、`googleSearch` ツールを付けてください。グラウンディングは12/12回で発生しました。

```json theme={null}
{
  "contents": [{ "parts": [{ "text": "A weather card poster for Tokyo today" }] }],
  "tools": [{ "googleSearch": {} }]
}
```

**output tokens への影響はごくわずかです**（検索料金を除くと、ツールなしのコントロール比で −2.1%、有意差なし）。コスト全体は検索呼び出し自体によるもので、1回 \$0.014 です。

| 条件                 | グラウンディング発生 | クエリ中央値 | 1回あたりの課金           |
| ------------------ | ---------- | ------ | ------------------ |
| ツールなし              | 0/12       | 0      | \$0.036            |
| `googleSearch: {}` | 12/12      | 2      | **\$0.062 (+73%)** |

<Warning>
  **何回検索するかはモデルが決めます。事前に設定はできません。** テストでは、1回の画像リクエストが自動的に1～3件のクエリを発行したため、このツールを有効にすると1回あたりの課金は **\$0.050～\$0.078** の範囲になり、固定値ではありません。予算は上限で見積もってください。
</Warning>

### Image Search グラウンディング: Nano Banana 2 専用で、現時点では無料

`searchTypes.imageSearch` を使うと、モデルは Google Image Search から視覚的な参照を取得できます。これは「実写写真からコラージュを作る」や「実物をそのまま描く」といった用途に便利です。

```json theme={null}
{
  "tools": [{ "googleSearch": { "searchTypes": { "imageSearch": {} } } }]
}
```

| 条件               | グラウンディング発生 | 課金された検索料金 | 1回あたりの課金    |
| ---------------- | ---------- | --------- | ----------- |
| ツールなし            | 0/12       | 0/12      | \$0.036     |
| `imageSearch` のみ | 7/12       | **0/12**  | **\$0.032** |

* `imageSearchQueries` が `groundingMetadata` に現れ、`["current weather in Tokyo"]` のような値を示すことで確認されました。
* **現時点では追加課金はありません** — 1回あたりの課金は、ツールなしのコントロールよりわずかに低い結果でした。
* 12回中7回で発生しました: **検索するかどうかはモデルが決めます**。毎回問い合わせるわけではありません。
* Web search と image search は**同時に有効化できます**が、どちらを使うかはモデルが選ぶため、コストは予測不能になります。

<Warning>
  **`searchTypes` は配列ではなくオブジェクトでなければなりません。**

  ✅ `{"searchTypes": {"imageSearch": {}}}` — 動作します

  ❌ `{"searchTypes": ["imageSearch"]}` — **エラーは出ず、200 が返り、画像も取得できますが、image search は一度も発火しません。** レスポンス本文にはそれが何も示されません。配列形式に対する上流エラーは `Proto field is not repeating, cannot start list` です。
</Warning>

### responseModalities: 何も節約できませんが、不要なテキストを除去します

`responseModalities: ["IMAGE"]` は画像のみを希望することを示します。各20回実行しました。

| 設定                 | 出力 tokens 平均 | 1回あたりの課金 |
| ------------------ | ------------ | -------- |
| 省略（デフォルト）          | 1548.7       | \$0.0335 |
| `["IMAGE"]`        | 1535.0       | \$0.0332 |
| `["TEXT","IMAGE"]` | 1542.8       | \$0.0333 |

* **3つとも互いに1%以内**で、`["TEXT","IMAGE"]` はフィールドを省略した場合と完全に同じです（p=0.90）。
* 通常の生成 prompt では、**60/60 のレスポンスがすでに1つの image part だけを含み、テキストは一切ありませんでした**。そのため、このモダリティ切り替えには作用対象がありません。推論 prompt（インフォグラフィック、データチャート）の場合だけ、約3分の1の確率で要約段落が付加されます。そこでは `["IMAGE"]` がそれを抑制し、約 **2.8%** 節約できます（p=0.09、有意ではありません）。

<Info>
  **節約できるものがない理由**: output tokens は「image + text」ではなく、**画像用の1120 tokens に加えて、目に見えない約400 tokens のオーバーヘッド**だからです。そのオーバーヘッドは `candidatesTokensDetails` のどのフィールドにも現れませんが、**正規レートで課金され、1回あたりの課金の28%を占めます**。また、prompt 長によって変動しません。テキストの量はそれに比べればごくわずかです。

  つまり、1120 tokens から1画像あたりのコストを見積もると **約28% 過小評価** になります。代わりに `candidatesTokenCount` または `totalTokenCount` と突き合わせてください。
</Info>

## グループ設定

Nano Banana 2 には APIYI 上で 2 つのグループが用意されています。ダッシュボード → **Token 設定** で切り替えます:

| グループ                   | レート  | 使用する場面                                                           |
| ---------------------- | ---- | ---------------------------------------------------------------- |
| `Default`              | 1.0x | ベース レーン。料金表に一致します。推奨デフォルトです                                      |
| `NanoBananaEnterprise` | 1.4x | フォールバック レーン — デフォルトが逼迫したとき、またはタイムアウトが急増したときに手動で切り替えます。キャパシティ優先です |

**なぜ 1.4x なのですか?** 1.4x でも、価格は Google の定価の約 50% で、公式価格を大きく下回ります。これは高同時実行数のワークロードや予期しない上流のリスク制御イベント向けのフォールバック レーンであり、エンタープライズのお客様に高可用性保証を提供します。デフォルト グループが逼迫したら、スパイクをやり過ごすために Token を `NanoBananaEnterprise` に切り替えてください。

**推奨課金モデル**: `Pay-as-you-go Priority` を選んでください — Nano Banana 2 の token ベース課金と Nano Banana Pro の呼び出しごとの課金の両方をカバーし、**シリーズ全体で Token 1 つ**。

<Tip>
  **さらに進める場合**: Token が他の画像モデル（例: GPT-image-2）もカバーする場合は、より安定している `Default` を主要グループとして、`NanoBananaEnterprise` をフォールバック枠に入れてください — 主要グループで 429 が発生しても、token の切り替えなしでエンタープライズ グループへ自動フェイルオーバーします。
</Tip>

## FAQ

<AccordionGroup>
  <Accordion title="Nano Banana 2 と Nano Banana Pro の違いは何ですか？">
    **Nano Banana 2** (`gemini-3.1-flash-image-preview`) は Gemini 3.1 Flash ベースで、**Nano Banana Pro** (`gemini-3-pro-image-preview`) は Gemini 3 Pro ベースです。主な違いは次のとおりです:

    * ✅ **速度**: Nano Banana 2 のほうが高速です（Flashティアの速度）
    * ✅ **価格**: Nano Banana 2 の token ベース課金のほうが安価です（\$0.025 から、対して \$0.09）
    * ✅ **アスペクト比**: Nano Banana 2 は 14 種類に対応しています（4 つ多い）
    * ✅ **画像検索グラウンディング**: Nano Banana 2 のみ対応
    * ⚠️ **最高品質**: Nano Banana Pro のほうがなおわずかに優れています
  </Accordion>

  <Accordion title="Nano Banana Pro から Nano Banana 2 に切り替えるべきですか？">
    **おすすめです！** Nano Banana 2 は、より低価格で高速、かつ Pro に近い品質を提供します。極端に高い品質要件がない限り、Nano Banana 2 のほうが適しています。

    モデル名を `gemini-3-pro-image-preview` から `gemini-3.1-flash-image-preview` に変更するだけです。
  </Accordion>

  <Accordion title="gemini-3.1-flash-image-preview と -4k サフィックス版のどちらを使うべきですか？">
    **コード / API 呼び出しでは、`-4k` サフィックスなしの汎用モデル名 `gemini-3.1-flash-image-preview` を、`gemini-3.1-flash-image-preview-4k` ではなく常に使用することをおすすめします。**

    * **公式名に `-4k` はありません**: Google の公式モデル名は `gemini-3.1-flash-image-preview` です。ここは私たちが最も多くのリソースを投じて維持している汎用チャネルでもあるため、最も高い安定性と互換性を備えています。
    * **`-4k` の由来**: `gemini-3.1-flash-image-preview-4k` はもともと、Chatbox のような会話型クライアントにおける「チャットから画像生成」シナリオ向けに用意された設定でした。つまり、メッセージング UI のチャットから直接画像を生成する用途です。
    * **コード + Gemini ネイティブ形式では汎用名が有利です**: コード経由で Gemini ネイティブ形式（`/v1beta/models/.../generateContent`）を使う場合、通常のモデル名 `gemini-3.1-flash-image-preview` のほうがより安定しています。

    4K 出力が必要な場合も、`-4k` のモデル名に頼る必要はありません。リクエストパラメータで 4K 解像度を指定するだけで大丈夫です（上記の「対応解像度とアスペクト比」を参照してください）。
  </Accordion>

  <Accordion title="Image Search Grounding とは何ですか？">
    Image Search Grounding は Nano Banana 2 専用機能です。Google 画像検索から視覚的コンテキストを取り込み、実世界の対象によりよく一致する画像を生成します。たとえば、実在するランドマークの画像を生成する場合、検索結果を参照して精度を向上できます。
  </Accordion>

  <Accordion title="Thinking Mode は何をしますか？">
    Thinking Mode では、画像生成前にモデルが推論と分析を行い、複雑な prompt の精度を向上させます。`high` に設定すると最良の結果が得られますが、生成時間は少し長くなります。正確な構図、文字レンダリング、複雑なシーンを要するタスクに最適です。
  </Accordion>

  <Accordion title="画像生成にはどのくらい時間がかかりますか？">
    生成時間は解像度と Thinking Mode によって異なります:

    * **1K 解像度**: 約 5〜10 秒
    * **2K 解像度**: 約 10〜15 秒
    * **4K 解像度**: 約 15〜25 秒
    * 高い Thinking Mode を有効にすると、さらに数秒増えます

    まれな遅延やピーク時の混雑に備え、より長いタイムアウト（少なくとも 360 秒）を設定することをおすすめします。
  </Accordion>

  <Accordion title="同時実行数の制限はありますか？ API はシリアル処理ですか？ 20 人のユーザーが同時に呼び出す必要がある場合はどうなりますか？">
    **API には同時実行数の制限がなく、シリアル処理もしません。** ご自身で同時リクエストを安全に送信できます。リクエスト同士がキューに入ったり、相互にブロックしたりすることはありません。20 人のユーザーが同時に呼び出す場合は、単純に 20 件の同時リクエストを送れば大丈夫です。追加のクォータ申請やスロットリングは不要です。

    Google AI Studio とは異なり、APIYI チャネルには厳格な RPM/RPD 制限がないため、企業向けバッチ生成やピークトラフィックも線形にスケールします。

    **実際に重要なのは `timeout` です**: 画像生成（特に 4K やピーク時の混雑下）は 1 リクエストあたり時間がかかることがあるため、**クライアントのタイムアウトを 360 秒に設定**して、通常処理中のリクエストが途中で切断されないようにしてください。

    <Tip>
      まれに 429（高同時実行数によるスロットリング）を受ける場合は、トークンのフォールバックグループとして `NanoBananaEnterprise` を追加してください（上記の「グループ設定」を参照）。主要グループが飽和した際に自動でフォールバックするため、高同時実行数下での成功率がさらに向上します。
    </Tip>
  </Accordion>

  <Accordion title="入力画像として対応している形式は何ですか？">
    `image/png` と `image/jpeg` 形式に対応しています。base64 エンコードまたは Files API 経由でアップロードできます。
  </Accordion>

  <Accordion title="出力画像に透かしは入りますか？">
    すべての出力画像には SynthID の不可視デジタル透かし（Google の AI 生成コンテンツ識別技術）が付与されます。肉眼では見えず、利用にも影響しません。
  </Accordion>

  <Accordion title="なぜ connection reset by peer / write_response_body_failed (500) が発生するのですか？">
    完全なエラーは次のとおりです:

    ```text theme={null}
    [&{{write tcp ip:port->ip:port: write: connection reset by peer Unknown error shell_api_error  write_response_body_failed} 500 }]
    ```

    これは **通常、画像アップロードのサイズが大きすぎることが原因です。リクエストボディが大きくなりすぎて、接続が切断されます**。次のベストプラクティスに従ってください:

    * **画像枚数を制限する**: 公式ルールの範囲内（1 prompt あたり最大 14 枚）に収め、参照画像を詰め込みすぎないでください。
    * **画像ごとのサイズを制限する**: 各画像は 5MB 未満にしてください。公式の1枚あたり上限は 7MB ですが、base64 エンコードでサイズが約 1/3 増えるため、余裕を持たせてください。
    * **アップロード前にフロントエンドで圧縮する**: API に送る前に、フロントエンド（またはサーバー側の中継）で画像を圧縮してください。一般的には、長辺を制限し、JPEG/WebP に変換し、quality パラメータを調整します。
    * **URL 入力に切り替える**: Gemini ネイティブ形式では、画像 URL を `fileData.fileUri` 経由で渡せるため、サイズが大きすぎる base64 リクエストボディを完全に回避できます。詳細は [Nano Banana 開発ガイド](/ja/api-capabilities/nano-banana-dev-guide) をご覧ください。
  </Accordion>
</AccordionGroup>
