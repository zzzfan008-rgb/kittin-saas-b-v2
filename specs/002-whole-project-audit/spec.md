# Feature Specification: Garment Canvas 全量逻辑与代码审计整改

**Feature Branch**: `002-whole-project-audit`

**Created**: 2026-09-04

**Status**: Draft

**Input**: User description: "重新梳理整个项目逻辑和代码，找出不对或可优化的地方，并按风险分批整改。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 确认候选变更是否具备发布资格 (Priority: P1)

维护者可以从当前工作树、`origin/main`、运行环境、数据库事实源和外置证据开始复核，得到可复现的审计基线。任何发布阻断、有效安全问题、数据一致性问题、权限问题或证据缺口都会保持 fail-closed。

**Why this priority**: 没有可信基线就无法区分用户已有改动、历史证据和本轮整改，也不能判断是否可以发布。

**Independent Test**: 在包含已跟踪和未跟踪改动的工作树执行离线检查、定向测试和发布门禁，验证基线完整、变更未被覆盖、有效发现会阻断发布。

**Acceptance Scenarios**:

1. **Given** 工作树包含用户改动、外置证据和未跟踪文件，**When** 维护者建立审计基线，**Then** 所有对象按业务代码、测试、文档、证据和生成物分类，并记录当前提交及差异统计。
2. **Given** 任一 P0-P3 发现没有充分证据或回归测试，**When** 维护者执行发布门禁，**Then** 门禁失败且不会把缺口报告为通过。
3. **Given** API易 相关改动需要重新核对模型、参数、提示词、Provider 或证据，**When** 维护者执行对应本地知识门禁，**Then** 只读契约检查与外置 `/v1/models` 原始导出核对失败时保持 fail-closed；普通非 API易 审计不重复执行该校验。

### User Story 2 - 修复核心业务与安全边界 (Priority: P1)

维护者可以按入口、状态转换、持久化点、失败语义和并发边界修复登录授权、文档快照、DAG/队列、Provider 请求、结果持久化和历史恢复链路，并为每个 P0/P1 问题保留最小可重复回归测试。

**Why this priority**: 这些链路直接影响越权、重复计费、数据丢失、错误结果回写和发布安全。

**Independent Test**: 使用假 Provider 和隔离 PostgreSQL，覆盖鉴权、对象所有权、异步文档边界、队列租约/重试、未知结果、迁移和结果恢复场景。

**Acceptance Scenarios**:

1. **Given** 用户、项目、文件或运行记录不属于当前操作者，**When** 调用写入或读取接口，**Then** 请求被拒绝且不会改变不属于该操作者的数据。
2. **Given** 同一项目有多个标签页或文档 epoch，**When** 异步保存、上传、运行或结果回写返回，**Then** 只有匹配 `tabId + projectId + documentEpoch` 的上下文可以提交状态。
3. **Given** Provider 请求发生超时、连接中断或响应不确定，**When** Worker 恢复任务，**Then** 结果标记为 `outcome_unknown`，不自动重放可能重复计费的请求。
4. **Given** 真实评估或发布证据缺少授权、原始目录或精确代码身份，**When** 系统尝试运行或发布，**Then** 请求被阻断并记录具体缺失项。

### User Story 3 - 以兼容方式降低复杂度并改善可靠性 (Priority: P2)

维护者可以在保留旧接口、旧数据读取和回滚路径的前提下拆分职责过重的 Store、数据库迁移、运行队列、Runner 和评估脚本，减少重复规则和隐式状态，同时用性能和可靠性指标验证改动。

**Why this priority**: P2 结构问题会放大后续 P0/P1 修复的回归面，但不能在安全边界尚未闭合时优先重写。

**Independent Test**: 对拆分前后的入口和持久化格式执行契约测试、迁移测试、定向性能测试和构建检查，确认旧数据仍可读且行为不漂移。

**Acceptance Scenarios**:

1. **Given** 旧版本项目、模板和运行记录，**When** 新实现读取或迁移，**Then** 原数据可读、缺失字段保守处理、失败可定位且可回滚。
2. **Given** 队列、数据库或 Provider 负载达到目标范围，**When** 执行 P2 基准，**Then** p95、请求数、内存和构建包体不超过计划中的阈值。
3. **Given** 任何共享领域规则被抽取，**When** 浏览器、服务端和脚本同时调用，**Then** 它们使用同一规则来源，不产生第二份可漂移的业务事实。

### User Story 4 - 保持桌面工作台可验证且可维护 (Priority: P3)

维护者可以在不复制业务状态的前提下优化 UI 巨型组件、控件一致性、键盘焦点、错误状态和异步反馈，并在 1024、1280、1440 CSS px 桌面尺寸上完成可重复验收。

**Why this priority**: UI 改动风险较低但可见性高，必须建立在行为边界稳定后进行。

**Independent Test**: 运行桌面 E2E 和手动验收，检查核心工作流、键盘焦点、错误反馈、异步回写和不同窗口尺寸下无重叠或截断。

**Acceptance Scenarios**:

1. **Given** 登录用户处于工作台，**When** 完成项目打开、节点运行、结果查看和错误恢复，**Then** UI 状态与服务端事实一致且无不可解释的空白状态。
2. **Given** 浏览器窗口为 1024、1280 或 1440 CSS px，**When** 执行核心工作流，**Then** 关键控件可见、可聚焦、文本不溢出且错误状态可读。

### Edge Cases

- 当前 `HEAD` 与 `origin/main` 相同但工作树有大量未提交改动时，审计必须以工作树候选为范围，不得误报为空差异。
- API易 `/v1/models` 原始导出缺少任一现役 ID、原始字节 SHA 或规范化 ID 集合 SHA 不匹配时，保持发布阻断，并生成可直接发送给 API易 支持的差异说明。
- 运行期间项目、用户、素材或模型状态发生变化时，已启动任务继续使用不可变快照，新的变更只影响下一次运行。
- PostgreSQL 迁移中途失败、重复执行或旧 SQLite 导入不完整时，事务必须可回滚且不得产生半迁移状态。
- 历史结果缺少旧版字段、第三方临时 URL 失效或 provider 原始图片未落盘时，历史接口必须返回可解释的缺失状态，不得伪造完整证据。
- 目录、模板或证据文件出现符号链接、路径越界、未知字段、重复 ID 或非法哈希时，门禁必须拒绝。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 记录当前工作树、`HEAD`、`origin/main`、运行环境、数据库事实源和变更统计，并区分代码、测试、文档、证据和生成物。
- **FR-002**: 每个审计发现 MUST 使用统一的 `AuditFinding` 结构，包含严重级别、位置、主张、证据、影响、处置、整改批次和验证方式。
- **FR-003**: 每条核心链路 MUST 输出入口、状态转换、持久化点、失败语义、并发边界、现有测试和缺失场景。
- **FR-004**: 所有写入路由 MUST 完成权限覆盖、对象所有权、响应 shape 和调用影响核对。
- **FR-005**: 认证、会话替换、注销、密码变更、管理员权限和资源所有权 MUST 在失败路径中保持最小权限和可验证的一致语义。
- **FR-006**: 文档保存、撤销/重做、恢复和异步回写 MUST 使用明确的项目、标签页和 epoch 边界，禁止旧请求覆盖新文档。
- **FR-007**: DAG、队列、租约、重试、未知结果、恢复和幂等 MUST 具备可观察状态转换，未知 Provider 结果不得自动重放。
- **FR-008**: Provider 请求 MUST 使用经审查的模型契约和参数档案，产品模型 ID 与上游请求 ID 必须分离，缺少契约证据时失败关闭。
- **FR-009**: PostgreSQL 迁移、历史数据兼容和删除保护 MUST 具备事务边界、重复执行安全性和回滚验证。
- **FR-010**: 结果查看、对比、下载、设为输入和跨项目恢复 MUST 保留所有权校验、来源证据和不可用状态。
- **FR-011**: 任何 API易 相关模型、参数、提示词、Provider、证据或发布改动 MUST 通过本地知识库门禁；普通非 API易 审计不因全局 gate 重复执行知识库校验。
- **FR-012**: API易 当前五个现役模型的只读 `/v1/models` 原始导出 MUST 保留精确原始字节 SHA 和规范化 ID 集合 SHA；缺少任一现役 ID时 MUST 保持 fail-closed 并输出支持差异说明。
- **FR-013**: P0/P1 发现 MUST 有最小回归测试、修复证据和可重复的验证命令；未闭环发现不得标记为通过。
- **FR-014**: P2/P3 重构 MUST 提供旧接口映射、数据/文档迁移、兼容期、回滚方式和对证据闭包的影响说明。
- **FR-015**: 桌面 E2E MUST 在 1024、1280、1440 CSS px 检查核心工作流、键盘焦点、错误状态和异步回写。
- **FR-016**: 发布候选 MUST 通过定向测试、`npm run lint`、`npm run check`、`npm run build`、`git diff --check`、GitNexus 检查和 `npm run gate:codex -- --base origin/main`；任何有效 P0-P3、证据缺失或不可重复测试 MUST 阻断发布。

### Key Entities

- **审计基线**: 某一明确时间点的 Git、环境、数据库、测试和外置证据状态。
- **审计发现**: 对代码、契约、证据或流程缺口的可追踪判断。
- **整改批次**: P0 发布与安全、P1 核心边界、P2 性能可靠性或 P3 可维护性与 UI。
- **证据记录**: 可由复核者重新执行或校验的命令输出、哈希、测试结果和人工复核结论。
- **发布闭包**: 代码身份、模型目录、评估证据、运行时投影、权限和门禁结果的联合状态。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 的 P0/P1 发现有唯一 ID、至少一条证据、处置结论、整改批次和可重复验证命令。
- **SC-002**: 所有写入路由的权限和响应 shape 复核覆盖率达到 100%，不得存在未解释的高风险缺口。
- **SC-003**: 认证、文档边界、DAG/队列、Provider、迁移、结果恢复定向测试全部通过，且无真实付费 Provider 调用。
- **SC-004**: 当前五个现役模型的只读目录核对在原始字节、精确 ID 和契约引用三个层面一致；任意缺失均以 fail-closed 结果交付。
- **SC-005**: 发布门禁在工作树、外置证据或 GitNexus 状态不满足要求时 100% 失败，不允许通过叙述性结论绕过。
- **SC-006**: P2 重构后旧项目、旧模板和旧运行记录的读取兼容率为 100%，迁移失败可回滚且无半迁移数据。
- **SC-007**: 桌面 E2E 在 1024、1280、1440 CSS px 均完成核心路径，关键控件无重叠、截断或不可聚焦状态。

## Assumptions

- PostgreSQL 18 是生产事实源，SQLite 只用于兼容迁移验证。
- 当前工作树中的用户改动、外置证据和未跟踪文件全部保留，不执行清理、重置或覆盖式整理。
- 自动化 Provider 测试使用假 Provider；本轮不调用图片生成或编辑端点。
- API易知识库是 API易 相关变更的按需证据边界，不是普通审计的固定步骤。
- 重新设计必须先完成契约、迁移、回滚和证据验证，不能直接替换现有实现。

## Out of Scope

- 新增图片生成或编辑模型、供应商、计费方式或真实付费验收。
- 自动修改或删除用户已有工作树改动、外置证据、历史文档和生成物。
- 与审计发现无关的产品需求、品牌重做或未经确认的 UI 交互重设计。
- 用静态告警替代人工复核；`server/routes/usage.ts` 的 CSV 输出告警必须结合实际响应语义判断。
